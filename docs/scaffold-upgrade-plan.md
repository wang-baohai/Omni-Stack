# Omni-Stack 高效率脚手架下一阶段升级计划

> 计划状态：提案
> 编制日期：2026-08-17
> 当前基线：全功能审查 32/32 项已关闭，项目成熟度 90/100；作为可复用脚手架的成熟度约 86/100。

## 1. 升级目标

下一阶段不再以“增加更多业务页面”为主，而是把当前可运行的企业应用底座升级为：

1. 能通过命令快速创建新服务、新业务模块和标准 CRUD。
2. 能按项目类型裁剪不需要的业务能力。
3. 将租户、安全、数据权限、XSS、内部调用等重复代码沉淀为公共 Starter。
4. 让业务管理员无需理解模型版本 ID、半开区间等技术概念即可完成配置。
5. 具备可直接用于新项目交付的多语言文档、全流程截图和首次使用指南。
6. 具备正式环境需要的日志、指标、追踪、告警和质量门。

目标成熟度：脚手架复用成熟度由约 86/100 提升到 92～95/100。

## 3. R-01：请购审批规则业务化 UI 设计

### 3.1 定位与命名

- 菜单名称由“审批路由”调整为“请购审批规则”。
- 页面标题使用“请购审批规则”。
- 页面副标题明确说明：“系统根据物料品类和请购金额，自动选择对应的审批流程。”
- “路由编码”“模型版本 ID”“半开区间”等技术信息不再作为主要操作概念。
- 技术信息仅在“高级信息”中展示，供实施和排障人员使用。

### 3.2 页面信息架构

页面按业务人员的使用顺序组织：

1. **规则原理说明**：用一行流程说明“提交请购 → 匹配具体品类 → 匹配金额 → 启动审批流程 → 默认规则兜底”。
2. **匹配测试器**：选择品类并输入金额，不创建真实数据即可查看会命中哪条规则、经过哪些审批步骤。
3. **规则清单**：直接展示规则名称、适用品类、业务化金额范围、审批步骤、流程名称和状态。
4. **规则配置向导**：分“适用条件 → 审批流程 → 确认启用”三步完成配置。
5. **覆盖性提示**：显示金额断档、缺少默认规则、停用后无兜底等问题。

### 3.3 字段业务化

| 当前字段 | 新界面表达 | 设计规则 |
|---|---|---|
| `routeCode` | 规则编号 | 根据规则名称自动生成；仅在高级信息中允许有权限的管理员调整 |
| `categoryCode` | 适用物料品类 | `*` 显示为“所有未单独配置的品类（默认规则）” |
| `minAmount` | 最低金额（包含） | 显示为“金额 ≥ X”或“X ≤ 金额” |
| `maxAmount` | 最高金额（不包含） | 显示为“金额 < X”；留空显示“无上限” |
| `modelVersionId` | 使用审批流程 | 选择器显示流程名称、已发布版本和审批步骤，不直接展示数字 ID |
| `priority` | 列表排序 | 从主表单移除；如仍保留则放入高级设置，明确它不能解决金额区间冲突 |
| `status` | 是否启用 | 停用前提示停用后可能影响的品类与金额范围 |

### 3.4 规则清单设计

默认列：

- 规则名称，例如“IT设备 · 中额采购”。
- 适用品类，例如“IT设备”或“默认规则”。
- 金额范围，例如“10,000 ≤ 金额 < 100,000”。
- 审批流程，例如“部门负责人 → 财务负责人”。
- 流程名称与已发布版本，例如“请购标准审批 · v5”。
- 状态、查看和编辑操作。

不在主列表显示纯数字流程模型版本 ID 和 `[0, 10000)` 形式的区间。

### 3.5 新建/编辑向导

**步骤 1：适用条件**

- 输入业务化规则名称。
- 选择一个具体品类或默认规则。
- 输入最低金额和最高金额。
- 即时提示金额格式、上下界关系和已有规则覆盖情况。

**步骤 2：审批流程**

- 仅展示当前租户已发布的流程。
- 展示流程名称、版本、发布时间和审批步骤预览。
- 如果用户缺少 Workflow 查看权限，提供清晰的权限说明，不降级为要求输入数字 ID。

**步骤 3：确认启用**

- 用完整业务句子复述配置，例如：“IT设备，金额达到 10,000 元且低于 100,000 元时，依次由部门负责人和财务负责人审批。”
- 保存前校验品类有效、区间不重叠、流程已发布以及默认路由覆盖情况。

### 3.6 匹配测试器

匹配测试器是只读能力，输入物料品类和请购总金额后返回：

- 命中的规则名称。
- 命中条件。
- 是否使用默认规则。
- 对应流程名称与版本。
- 可理解的审批步骤。
- 无匹配时给出可操作建议，而不是仅显示 409 错误。

匹配结果必须使用与请购提交完全相同的服务端规则解析逻辑，禁止前端复制一套可能漂移的算法。

### 3.7 空态与异常态

- 首次进入且没有规则时，展示“先发布审批流程，再创建第一条默认规则”的两步引导。
- 缺少默认规则时显示持续可见的风险提示。
- 规则存在金额断档时明确显示缺失范围。
- 工作流版本已失效或不存在时，规则标记为“需要修复”，并禁止误认为可正常使用。
- 所有失败信息保留 Trace ID，并提供重试或前往相关配置页的入口。

### 3.8 权限与审计

- 查看、创建、更新、删除继续使用现有 `procurement:approval-route:*` 权限体系。
- 匹配测试只需要查看权限，不创建业务数据。
- 创建、修改、启停和删除写入操作日志，记录修改前后条件和流程版本。
- 已经启动的审批实例继续使用原模型版本，不因规则更新而改变。

### 3.9 验收场景

1. 创建 IT设备 0～10,000、10,000～100,000、100,000 以上三条规则。
2. 测试金额 0、9,999.99、10,000、99,999.99、100,000 的边界命中结果。
3. 测试具体品类优先于默认规则。
4. 测试缺少规则、金额断档、区间重叠、流程未发布和权限不足。
5. 验证保存后的匹配测试结果与真实请购提交使用同一条路由。
6. 验证桌面端、平板和 390×844 移动端布局。

## 4. R-05：项目裁剪预设与维护说明

项目裁剪预设除了能够生成正确工程，还必须提供面向使用者和维护者的说明文档，避免预设成为只能由原作者维护的黑盒功能。

### 4.1 文档交付物

- 提供项目预设快速选择指南，说明 `core`、`workflow`、`crm`、`supply-chain` 和 `full` 的适用场景、包含能力及资源需求。
- 提供项目预设维护手册，覆盖模块增删、自定义预设、依赖联动、升级兼容、验证和故障排查。
- 提供可检索的预设依赖矩阵，明确每个预设包含的后端模块、前端菜单与路由、权限种子、配置、Compose 服务、端口、消息和数据库依赖。
- 提供至少一个从标准预设复制并维护为自定义预设的完整示例。
- 文档提供中文、英文、日文和韩文版本，并纳入 R-09 的统一文档检查。

### 4.2 使用说明必须覆盖

1. 根据业务范围、机器资源和部署复杂度选择预设。
2. 创建项目的命令、参数、默认值和生成目录说明。
3. 每个预设保留与移除的服务、页面、菜单、权限和基础设施。
4. 项目生成后的首次启动、初始化、登录及健康检查步骤。
5. 从较小预设扩展新模块以及从较大预设安全移除模块的方法。
6. 常见生成失败、端口冲突、缺少依赖、菜单缺失和种子数据不一致的处理方法。

### 4.3 维护说明必须覆盖

- 预设定义文件的结构、字段含义、继承或组合关系及命名规范。
- 新增、修改和废弃预设时需要同步更新的 Maven 模块、Gateway 路由、Nacos 配置、Compose、前端路由、菜单、权限、国际化、测试和文档。
- 模块依赖的必选、可选、互斥和传递关系，以及错误组合的校验规则。
- 预设版本、兼容范围、废弃周期、升级说明和已有项目迁移策略。
- 生成结果验证方法，包括构建、启动、数据库初始化、权限登录和核心冒烟流程。
- 失败后的回滚方式以及如何定位生成器、预设清单或模块本身的问题。

### 4.4 防止文档与实现漂移

- 使用机器可读的预设清单作为模块组合的单一事实来源，说明文档和依赖矩阵应尽可能由该清单生成。
- CI 校验预设清单、生成器可选项、README 导航和四语言文档中的预设名称及版本一致。
- 每个正式预设至少生成一个黄金样例，并验证 Maven 构建、前端构建、Compose 配置和种子数据引用。
- 预设内容变化必须在同一提交中更新维护手册、依赖矩阵、测试快照和升级说明。

### 4.5 验收标准

1. 第一次使用者不阅读源码即可选择合适预设、生成工程并完成首次启动。
2. 维护者只依赖维护手册即可新增一个自定义预设并通过全部质量门。
3. 任意模块的加入或移除都能从依赖矩阵查到所有联动修改点。
4. 文档中的命令、目录和生成结果由 CI 自动验证，不存在失效示例。
5. 四语言版本章节结构和功能边界一致。

### 5.3 README 更新要求

同步更新 `README.md`、`README.en.md`、`README.jp.md` 和 `README.kr.md`：

- 最新技术版本和运行要求。
- 当前真实模块清单及能力边界。
- 一张清晰的系统架构图和端到端业务链路图。
- 不包含明文默认密码的首次启动说明。
- 最小启动、完整启动和健康检查命令。
- 主要模块截图入口。
- 四语言文档导航表。
- 构建、测试、E2E 和依赖安全的真实结果。
- 开发环境与生产环境边界说明。
- 新服务生成器和项目预设的使用入口（对应 R-02、R-05）。

### 5.4 截图覆盖范围

截图必须覆盖完整操作流程，而不是只截最终列表页：

1. **公共与认证**：登录、注册、CAPTCHA、社交登录、设备码授权、登录失效恢复。
2. **系统管理**：租户、组织、用户、角色、权限、菜单、字典、OAuth2、在线用户、登录记录、审计和 XSS。
3. **Workflow**：创建模型、设计 BPMN、配置审批人、发布、发起、待办审批、会签、完成和实例跟踪。
4. **Scheduling**：任务类型、创建任务、调度、手工触发、暂停、恢复和执行日志。
5. **CRM**：线索创建、线索转化、客户 360、联系人、商机阶段推进和活动记录。
6. **SRM**：供应商邀请、Portal 注册、入驻审批、激活、评价、风险管理和供应商报价。
7. **Procurement**：物料、请购审批规则配置与匹配测试、请购提交审批、RFQ、报价、比价、PO 和收货。
8. **Asset**：收货建卡、资产分配、接收、归还、调拨审批、处置审批和资产概览。
9. **MQ 与监控**：消息状态、失败重试、死信处理、操作日志和 Trace ID 排障。
10. **权限与异常**：普通员工、采购管理员、供应商三类角色的可见范围，以及 403、404、菜单失败和接口失败状态。

每个流程至少包含：入口、关键填写、提交确认、处理中、成功结果和典型失败六类画面；无对应状态时可省略，但必须在截图清单中说明。

### 5.5 截图生产规范

- 新增独立 Playwright 文档截图套件，与断言式 E2E 分离，但复用稳定测试数据和登录能力。
- 提供统一命令，例如 `npm run docs:screenshots`，自动生成截图并更新清单。
- 桌面截图统一使用 1440×900；供应商门户和关键表单补充 390×844 移动端截图。
- 不截取真实密码、CAPTCHA、JWT、内部 Token、个人隐私或生产数据。
- 使用固定租户、固定角色和可重复数据，避免时间、随机编号和分页导致截图漂移。
- 截图文件名包含模块、流程编号、步骤编号和语言，例如 `procurement-requisition-03-submit.zh-CN.png`。
- 为每张截图维护角色、路由、语言、视口、前置数据、步骤说明、预期结果和生成脚本来源。
- CI 检查文档引用缺失、孤立图片、截图清单遗漏和四语言章节不一致。

### 5.6 多语言截图策略

- 当前前端已有中文和英文语言资源，首先生成 `zh-CN` 与 `en-US` 两套界面截图。
- 为真正实现四语言一致体验，计划补充 `ja-JP`、`ko-KR` 前端语言包和语言切换入口，再生成日文与韩文截图。
- 在日/韩 UI 语言包完成前，日/韩文档可以临时引用英文截图，但必须标明临时状态和替换任务，不得视为最终完成。

### 5.7 新手手册组织方式

每个主要流程采用一致结构：

1. 这个功能解决什么业务问题。
2. 哪个角色可以操作。
3. 操作前需要准备什么。
4. 按编号排列的截图步骤。
5. 每一步的预期结果。
6. 常见错误、原因和处理方法。
7. 与上下游模块的关系。
8. 对应 API、权限码和技术设计文档入口。

目标是让第一次接触 Omni-Stack 的用户不阅读源码，也能完整理解并走通主要业务流程。

## 6. R-10：交付收尾与临时脚本清理

R-10 是所有功能、测试、文档和截图完成后的强制后置操作，不得在各阶段开发过程中提前执行破坏性清理。

### 6.1 清理范围

- 本阶段为了排查、迁移、修复、验证、截图、数据回填或格式转换而临时创建的脚本。
- 以前任务遗留且已经没有正式入口、测试引用或运行时依赖的脚本。
- 临时数据库脚本，包括一次性迁移、修复、回填、诊断、核对和演示数据脚本。
- 临时 Python、JavaScript、TypeScript、Shell、PowerShell、Batch 等辅助脚本。
- 临时日志、导出文件、调试数据、截图中间文件、缓存、备份副本和重复生成物。
- 已经被正式代码、测试工具或最终文档替代的旧版本文件。

### 6.2 清理原则

1. 清理前生成“保留白名单”和“拟删除清单”，逐项检查源码、Compose、CI、测试和文档引用。
2. 有长期复用价值的能力必须先归并到正式 CLI、测试套件、文档截图工具或模块源代码中，再删除临时实现。
3. 不删除应用启动、数据库初始化、自动化测试、CI、E2E、文档截图和脚手架生成器实际依赖的正式文件。
4. 仓库中供人工执行和维护的 SQL 脚本最终只保留规范化、可重复执行的种子数据；一次性迁移、修复、回填和诊断 SQL 在验证完成后删除。
5. 数据库建表和结构升级能力在删除一次性 SQL 前必须纳入正式、可重复的结构管理机制，且通过全新数据库初始化和已有数据库升级验证。
6. 清理历史遗留文件时保留 Git 历史作为追溯来源，不为“可能以后使用”继续保留无入口脚本。
7. 删除后同步修正文档、命令、CI 配置和脚本引用，禁止出现失效路径。

### 6.3 最终保留规则

- 保留生产源码、正式测试、构建与部署配置、最终文档、最终截图、生成器模板和稳定自动化工具。
- 保留的每个独立脚本都必须具备明确入口、用途说明、维护归属和至少一个实际调用方。
- SQL 只保留最终种子数据，不保留带日期或任务编号的一次性 SQL 文件。
- 不保留 `tmp`、`temp`、`debug`、`check`、`fix`、`backup`、`old`、`draft` 等语义的任务残留文件；正式工具不得使用此类临时命名。

### 6.4 清理验收

1. 对仓库进行扩展名、临时命名、未跟踪文件和无引用脚本扫描，并人工复核结果。
2. 从空数据库完成结构初始化和种子数据导入，所有服务可以正常启动。
3. 对已有数据库完成正式升级验证，不依赖已删除的一次性脚本。
4. 后端构建、前端构建与 lint、E2E、文档截图和链接检查全部通过。
5. `git status` 中不包含任务产生的临时文件、中间产物或本地调试配置。
6. 形成最终清理记录，列明删除、归并和保留文件及其原因，随交付审查一并确认。

## 8. 横向质量门

每个阶段都必须满足：

- 后端 `./mvnw clean install` 成功。
- 前端 `npm run build` 和 `npm run lint` 成功。
- 生成器提供快照或黄金样例测试，生成结果可以独立编译。
- 项目预设清单、依赖矩阵、生成器选项和四语言维护说明保持一致。
- 核心用户流程同时具有断言式 E2E 和文档截图脚本。
- 新增或变化的 API、架构、权限和流程同步更新四语言文档。
- 截图和说明与当前发布版本一致，不允许复用已过时图片。
- 所有示例不包含真实密钥、固定弱密码或生产数据。
- 最终交付执行临时文件扫描和脚本保留白名单检查，SQL 只保留规范化种子数据。

## 10. 最终完成定义

下一阶段只有同时满足以下条件才可认定完成：

1. 新项目可以通过 CLI 和预设创建，生成结果通过全量质量门。
2. 新业务模块可以通过 CRUD 生成器建立，再按领域逻辑增量开发。
3. 业务人员可以理解并独立配置请购审批规则。
4. 中文、英文、日文、韩文 README 与主要模块文档内容一致。
5. 主要端到端流程都有最新、可重放、无敏感信息的步骤截图。
6. 第一次使用者能够只依赖 README 和用户手册完成启动、登录、权限配置及至少一条完整业务流程。
7. 正式环境具有可观测性模板，并能通过 Trace ID 定位跨服务失败。
8. 后端、前端、E2E、文档和依赖安全质量门全部通过。
9. 新旧临时脚本及中间产物已经清理，正式能力已经归并到稳定入口，仓库中的人工维护 SQL 只保留最终种子数据。
10. 项目裁剪预设具备四语言使用说明、维护手册和依赖矩阵，使用者与维护者均无需阅读生成器源码即可完成标准操作。
