此约束适用于全部 WP、全部预设、教程示例、构建、测试、截图和故障排查，不因命令来自旧脚本而豁免。

### 6. 持久进度与断点恢复

在仓库根目录使用已有 `*.local` 忽略规则覆盖的 `wiki-workspace-ux.progress.local` 保存 JSON 进度；固定 `wiki-workspace-ux.records.local/` 只保存私有台账、脱敏日志和导出的证据。两个位置不承载项目副本、构建产物、运行配置或业务数据，不进入 Git 或正式 Wiki。浏览器原始输出先保存在 Docker 验证卷；令牌、Cookie 和私有配置不导出到报告。

进度至少包含：`run_id`、`branch`、`initial_head`、`baseline_changes`、`current_wp`、`current_step`、`plan_lock_sha256`、`contract_sha256`、`environment_fingerprint`、每步的 `status/changed_files/commands/exit_codes/evidence_paths/input_hashes/blockers/next_step/items`，以及台账修订记录。`steps` 的键只能使用锁文件中已有的 150 个 S；`items` 以文章路径或功能库存 ID 记录处理对象，不赋予新的步骤编号。

状态含义：

- `TODO`：未开始。
- `DOING`：正在做，不能当作完成。
- `PASS`：该步要求的检查真实通过。
- `READY_FOR_REVIEW`：实现或译文已就绪，仍缺指定审校或外部验收；不等于 PASS。
- `BLOCKED`：有具体证据说明当前步骤不能继续；不等于已完成或范围豁免。

多篇文章或多个功能在所属固定 S 的 `items` 逐项记录；所有适用对象满足这个 S 的条件后才能把该 S 标为 PASS。不能完成第一篇就覆盖整个章节，不因记录对象而增加 S，也不在进度文件复制和改写原步骤正文。

每个对象完成、长命令开始/结束、每个 S 结束和中断前都落盘；S 内尚有对象未完成就保持 DOING，不必等全集完成才保存断点。新一轮或上下文恢复时先用用户启动消息中的摘要重新校验计划锁，再读本提示词与进度、核对唯一 Docker 环境、实际文件和差异；验证已存在产物后接着做，不重开计划、不重置计数、不重做所有已通过任务。进度丢失时从产物与证据重建，不能凭对话记忆填写 PASS。

不要绕过真实验证码、伪造第三方登录结果、增加生产认证后门或修改权限来方便取证。受控测试 fixture 的结果与真实用户登录必须分别说明。

模型能力兜底：对照实际源码、文档和错误完成合理排查后，若当前模型仍无法提出有依据的修复、解释失败机制或证明结果正确，必须承认未解决。相同失败继续遵守前述尝试上限；明显存在数据、权限或范围风险时应更早停止，不能为凑次数继续试错。任务大、需要耐心、额度估算或尚未读取必要依据，不能单独作为能力不足的理由。

无法解决时，当前原 S 保持 BLOCKED，在 blockers 中区分模型能力、环境、外部输入、授权范围和依赖阻塞；译文仅缺指定审校时仍使用 READY_FOR_REVIEW。说明“已经确认什么、仍不知道什么、为什么现有证据和允许手段不足以继续”，根因未知就明确写未知，不能编造一个已确认原因，也不能假称修复或 PASS。

保存当前原 S 与对象、复现条件、实际命令/cwd/退出码、脱敏错误、已尝试办法及各自结果、相关文件/符号/摘要和差异、环境/镜像身份、未完成部分及影响范围。指出哪些依赖步骤不能继续、建议接手者先验证什么以及从哪里恢复；建议只是研究入口，不是新增 WP/S。已知有副作用的未完成修改需说明现状，只处理能明确归属的本步内容，不覆盖用户或之前的有效成果，不遗留失控验证任务。

继续完成手册允许且不依赖该问题的独立工作；不能绕过依赖、偷偷换方案或降低验收。所有可独立推进的工作完成后，可以交付本轮执行结果和待接手事项，但存在必做项未完成时整个 Goal 仍未完成，不得将“交接清单已完成”冒充“改造已完成”。不自动创建会话或向 Codex 发消息，由用户决定人工处理或交给 Codex 深入研究。

必须持续维护 `wiki-workspace-ux.records.local/unfinished-tasks.md`，最终汇总原 150 个 S 中全部非 PASS 项及其未完成对象，包括失败、能力不足、环境/授权/人工/审校依赖，以及因前置阻塞尚未尝试的步骤。未尝试项明确写“未尝试及其依赖”，不能谎称排查后无法解决。每项按手册 A6 的字段记录，且与进度一致；确实没有剩余项时明确写 0 项并引用最终验收证据。

### 8. 翻译审校的现有授权

先读取 `docs/adr/0003-authorized-ai-translation-review.md` 与 `docs/docs-manifest.yaml` 当前策略。当前指定审校工具为 Codex；Qwen3.8-Flash 的实施与自检不能冒用这个身份。

你可以写译文、逐项自检、修正问题、运行内容检查并提交待审材料。未获新的明确授权时，不能改审校策略，不能署名 Codex，不能伪造 HUMAN_REVIEW，不能只计算摘要就补 approved/synchronized。

文档新增或修改后，将受影响的源、译文和实际复核状态正确更新；过期签核不沿用。自检完成但指定审校未完成的步骤为 READY_FOR_REVIEW，后续仅依赖已就绪内容的工作可以继续。源仓最终指定审校与严格门仍是 Goal 的完成条件。整理逐篇材料交给用户指定的 Codex；收到真实审校结果后核对当前摘要，复用有效记录。审校后只重跑被变更影响的检查；五种生成物按 G7 保持自己的裁剪后状态，禁止为了取得发布绿色手改 scaffold.lock 或审校策略。

### 9. 执行顺序与首次动作

按手册 WP-00 至 WP-29 推进，每个 WP 的 S 从小到大执行；仅在手册已明确允许的阻塞情形中推进其中写明的独立内容，保留原阻塞步骤，不重排原计划。正文逐篇处理，不能一次生成整个 Wiki 后笼统宣布全部完成。

首次先核验用户消息中的锁文件 SHA-256，核对保护文件、30 个 WP 和 150 个 S；通过后报告 WP-00.S01 的实际检查结果和下一步，然后继续已授权工作。不要复述整份需求、再次向用户索要实施方案，或直接跳到首页重写。

正常进度简报只包含：当前 WP/S、具体变化、检查结果、阻塞、下一步。最终提供逐需求与逐 WP 的证据索引、实际命令结果、遗留项及恢复路径；把“等待指定复核”与“全部完成”分开。
