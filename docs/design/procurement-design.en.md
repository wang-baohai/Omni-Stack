# Procurement Execution Architecture and Implementation Baseline

> Engineering translation draft. Human review is required; stable API values, permission codes, and state names are not translated.

## 1. Scope and boundaries

`omni-procurement` owns material categories/materials, requisitions, approval rules, RFQs, quotation comparison, purchase orders, goods receipts, and procurement overview. Workflow owns Flowable runtime, SRM owns supplier identity/portal, and Asset owns asset cards. Procurement must not depend on Flowable or `omni-common-workflow`.

The MVP runs Material → Requisition → Approval → RFQ → Quotation → Comparison → Purchase Order → Goods Receipt. Contracting, invoicing, settlement, advanced sourcing, and warehouse inventory remain outside the module.

## 2. Data and state machines

Aggregate roots are Material/Category, ApprovalRoute, Requisition, RFQ, PurchaseOrder, and GoodsReceipt. Every `proc_*` table is tenant-bound; child rows inherit access through their root. Tenant-shared configuration tables—material/category/approval route/config—do not use per-owner DataScope.

Requisition status is command-driven from draft/submitted through approval result and downstream sourcing. RFQ controls invitation, quotation deadline, comparison, award, and close. Purchase Order and Goods Receipt have explicit lifecycle commands, optimistic versions, and immutable business evidence. Money and quantities use `BigDecimal` with declared precision; approval amount intervals are `[minAmount,maxAmount)` and the upper bound may be unlimited.

## 3. Business-friendly requisition approval rules

The UI is named “Requisition Approval Rules,” not “Approval Routing.” Business users maintain rule name, material category, inclusive minimum amount, exclusive maximum amount, and a current published procurement workflow. `routeCode` is generated by the server as `APR-{ULID}` and cannot be edited. Exact categories take precedence over the default category; priority is an internal compatibility field, not the normal business control.

Only the current published Workflow model with `category=purchase` can be selected for new rules. Existing legacy references are reported, not silently rewritten. The module provides real match testing, gap/overlap/default-rule analysis, unavailable/invalid workflow markers, safe node preview, and deactivate/delete impact analysis. Rule changes use tenant uniqueness, pessimistic/optimistic concurrency as applicable, and audit before/after snapshots.

## 4. Tenant, RBAC, and DataScope

TenantLine applies only to `proc_*`; `sys_mq_message` remains outside interception. DataScope mappings are aggregate-specific: requisition uses requester user/unit, RFQ/PO/GR use owner user/unit, and children inherit through the root. Material, category, approval rule, and config are tenant-shared.

The trust chain is Gateway identity → tenant filter → `@PreAuthorize` → permission-aware scope → MyBatis tenant/scope → row AccessGuard. Missing tenant/scope/internal token fails closed. Writes validate tenant, visibility, state, version, and command-specific permission; invisible IDs return 404.

## 5. Workflow and cross-service consistency

`RequisitionWorkflowCoordinator` resolves a rule, persists the local submission/start request, and starts Workflow idempotently outside the business transaction. Completion events arrive through Inbox and atomically change local state. Procurement never lets Flowable update its tables.

SRM supplies tenant-restricted active suppliers and receives RFQ invitations. Supplier portal quotation submissions carry request ID and expected version; duplicates are idempotent and uncertain results can be retried unchanged or refreshed. Goods Receipt publishes an explicit event for Asset. Asset creation is asynchronous and must not block receipt confirmation.

All domain messages use Transactional Outbox with explicit tenantId. Consumers validate tenant and atomically store Inbox plus business mutation. Duplicate and out-of-order events do not create duplicate quotations, orders, receipts, or asset triggers.

## 6. API, UI, and persistence

Controllers return `R<T>` / `R<PageResult<T>>`; write endpoints use `@PreAuthorize`. Frontend pages live under `views/procurement/`; buttons use matching `v-permission`; stable states/codes remain separate from localized labels. Approval rules support 1440×900, 1024×768, and 390×844 without horizontal page scrolling.

Structure migrations live in `database/changelog/procurement/`; idempotent defaults and permissions live in `scripts/sql/seed/procurement.sql` and `scripts/sql/seed/auth.sql`, with seed manifest checksums/assertions updated together.

## 7. Verification

Tests cover all legal/illegal transitions, approval rule precedence/gaps/overlaps/boundaries, legacy models, workflow outage/retry/events, tenant and every DataScope mapping, supplier quotation concurrency, PO/receipt idempotency, Outbox/Inbox duplicate/order behavior, Asset event contract, permissions, XSS/audit, responsive UI, and the complete browser flow.
