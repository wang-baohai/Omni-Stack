# 1. 통합 MQ 관리: “나중에 처리하기” 이해하기

작업 기록을 공통 조회 서비스로 전달하는 일처럼 사용자를 오래 기다리게 하지 않아도 되는 후속 작업이 있습니다. 메시지 큐(MQ)는 생산자가 할 일을 남기고 다른 쪽이 나중에 처리하게 합니다. 양쪽이 같은 순간에 실행될 필요는 줄지만 대기, 실패, 중복, 추적 문제는 설계해야 합니다.

## 택배에 비유해 보기

| 용어 | 비유 | 이 프로젝트의 예 |
|---|---|---|
| 생산자 | 할 일을 만드는 발송인 | 업무 서비스 또는 작업 로그 생산자 |
| Broker | 받아서 전달하는 중간 기지 | RocketMQ |
| 소비자 | 받아서 일을 처리하는 쪽 | Base의 작업 로그 소비자 |
| Outbox | 발송인 자신의 발송 대기 목록 | 각 서비스의 로컬 sys_mq_message |
| 중계 | 목록에서 받아 실제 발송하는 담당자 | XXL-JOB이 실행하는 메시지 중계 |

Outbox는 Broker 내부의 큐가 아니며 관리 화면도 실제 전송 통로가 아닙니다. 전송 기록, 재시도, 데드레터를 볼 수 있지만 업무 완료 여부는 소비 결과를 확인해야 합니다.

## 의도를 먼저 기록하는 이유

업무 저장 후 바로 MQ를 호출하면 업무는 커밋됐는데 전송이 실패할 수 있습니다. 먼저 전송하면 메시지가 전달된 뒤 업무가 롤백될 수 있습니다. Outbox는 하나의 유효한 로컬 트랜잭션에서 업무와 발송 의도를 함께 저장하고 나중에 전송합니다.

전제는 같은 데이터 소스, 유효한 트랜잭션, 올바른 프록시 호출입니다. send라는 메서드를 호출했다는 사실만으로 원자성이 증명되지 않습니다. 작업 로그 생산자는 전송 예외도 잡으므로 모든 업무 경로에 대한 보장으로 사용할 수 없습니다.
