# 2. 設計の選択：アプリが記録し、ツールが運ぶ

アプリから遠隔の収集先へ直接送る方法と、標準出力へ書き、収集器が読み取る方法があります。本工程は後者です。各業務メソッドにLokiクライアントを組み込む必要はなく、コンテナの置換後もDockerのメタデータから対象を再発見できます。

## 四つの役割

| 役割 | 本工程のツール | 担当しないこと |
|---|---|---|
| イベントの生成 | Spring Bootのログ機構 | 集中保存 |
| 発見と収集 | Alloy | 業務監査や権限判断 |
| 保存と検索 | Loki | 業務データベースの代替 |
| 検索と関連付け | Grafana | 未収集データの生成 |

Lokiではラベルでログの流れを絞ってから内容を検索します。ユーザー名、注文番号、リクエストごとに異なる番号をラベルにすると、値の種類が増えて管理コストが高まります。必要な関連番号はログの項目に残し、内容の検索で探せます。

## 構造化出力の設定

正式なアプリCompose環境にある設定です。

<!-- omni:source path="compose.apps.yaml" -->
```yaml
      LOGGING_STRUCTURED_FORMAT_CONSOLE: ${STRUCTURED_LOGGING_FORMAT:-ecs}
```

Spring Bootは対応するログプロパティを読み、既定でECS（Elastic Common Schema）JSONを使います。ECSは項目の約束で、別のメッセージキューでも自動マスキングのスイッチでもありません。別の起動方法では、その方法の有効な設定を確認します。

## すべてを一つのDBに入れない理由

実行ログと業務テーブルでは、書き込み量、保存期間、検索方法が異なります。操作監査にはテナントと閲覧権限も必要です。一つの表に混ぜると性能と責任の境界が曖昧になるため、実行ログとDBの操作記録・安全イベントを分けています。

この方式にも収集、保存、保持方針、検索権限の保守が必要です。収集器の故障中には遅延や欠落が起こり得ます。本番ではアクセス制御、容量、バックアップを評価します。ローカルのひな形があるだけでは、それらの条件を満たした証拠になりません。
