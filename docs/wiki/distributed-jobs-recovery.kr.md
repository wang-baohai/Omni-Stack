# 7. 복구와 확장: 어느 계층에서 실패했는지 먼저 확인하기

작업이 실행되지 않았다는 말에는 아직 시간이 안 됨, 배정 실패, 업무 실패, 결과 미도착이 포함됩니다. 복구 경로가 다르므로 버튼을 반복하는 것으로 진단을 대신하지 않습니다.

## 증거를 따라 계층별 확인

| 관찰한 상태 | 먼저 확인할 것 | 바로 하지 말아야 할 것 |
|---|---|---|
| 시스템 목록에 없음 | 두 애너테이션, 배포, 실행기 스위치 | 모든 개인 처리기에 시스템 메타데이터 추가 |
| 미등록 표시 | 원격 조회 성공 여부, 그룹, handler | 표시만 보고 없다고 판단해 재등록 |
| 배정 실패 | 주소, 통신, 인증, handler 이름 | 업무 상태 수정, 근거 없는 재시도 |
| 배정 성공·실행 실패 | 해당 실행 로그, 입력, 업무 상태 | 배정 성공을 업무 성공으로 간주 |
| 오래 진행 중 | 처리 시간, 중복 요청 정책, 시간 초과, 콜백 | 인터럽트가 모든 부수 효과를 취소했다고 추측 |
| 개인 로그 없음 | 배정, 인수 해석, DB 저장 | 성공 시각을 만들어 넣기 |
| 생성·삭제 결과 불명확 | 양쪽 ID, 신뢰할 수 있는 연결, 전체 조회 | 이름으로 추측해 일괄 정리 |

정확한 시각과 시간대, 테넌트, 로컬 ID, 실행기 그룹, 원격 ID, 로그 ID를 남깁니다. 비밀번호, Cookie, 민감한 전체 인수는 공개 보고서에 넣지 않습니다.

## 등록 오류 후 로컬 행을 보존하는 이유

조회나 정리까지 실패했을 때의 실제 분기입니다. 원격 결과가 불명확한데 로컬 행을 지우면 복구에 필요한 연결을 잃습니다.

## 개인 작업 종류 추가하기

사용 목적, 입력, 중복 방지를 먼저 정의합니다. 기존 UserJobHandler를 구현하고 Bean 이름을 목록의 종류 코드와 정확히 일치시키며 입력 정의도 유지합니다. 실제 물 마시기 처리기는 이렇게 선언합니다.

메시지에 tenantId가 명시되므로 HTTP 스레드의 테넌트 문맥에 의존하지 않습니다. 업무 쓰기는 권한, 상태 전이, 트랜잭션, 멱등성을 설계하고 사용자가 입력한 번호를 신뢰한 인가로 취급하지 않습니다.

종류 초기 데이터, 인수 템플릿, 검증을 함께 관리하고 구조 변경에는 전방 마이그레이션을 사용합니다. 드롭다운만 바꾸면 부족합니다. 이 내용은 확장 절차이며 새로운 종류나 스케줄링 기능을 구현했다는 뜻은 아닙니다.

## 시스템 유지보수 작업 추가하기

두 애너테이션을 쓰고 이해할 수 있는 이름, 기본 주기, 인수, 라우팅을 제공합니다. 데이터량, 배치, 동시성, 멱등성, 실패 후 상태를 평가한 뒤 주기적으로 호출합니다. 서비스별 AppName은 유지합니다.

## 제대로 작동하는지 검증하기

동일한 로컬 Docker 환경에서 전용 테스트 계정으로 생성, 수정, 중지, 수동 실행, 재개, 실제 주기 실행, 성공·실패 로그, 다른 사용자·다른 테넌트 거부, 삭제 후 원격 잔여 없음까지 확인합니다. 대조 실패와 복구도 실제 기록으로 남깁니다.

원문 일치, 단위 테스트, 실제 Cron 실행, 이미지 검토는 각각 다른 증거입니다. 등록과 정리에는 정상 경로뿐 아니라 응답 유실과 결과 불명확도 검증합니다. 제약은 [스케줄링 사실 문서](../scheduling.kr.md), 다시 읽기는 [이 장의 시작](distributed-jobs-principles.kr.md)을 참고하세요.
