# 7. 权限、退出与排障：拿到令牌之后还有哪些检查

小李能够登录，并不意味着申请审批、跨部门数据或供应商门户都会对他开放。这一篇把凭据、业务权限、数据范围和退出后的状态放在一起，帮助你在正确的一层定位问题。

## 带着令牌发请求，后面还有几道检查

| 环节 | 回答的问题 | 项目怎样处理 |
|---|---|---|
| 网关验证凭据 | 这份访问凭据是否可信、仍有效 | 验证签名、有效期和令牌标识的黑名单状态 |
| 传递内部身份 | 下游看到的身份是谁确认的 | 清理客户端身份头，注入核验后的身份和网关签名断言 |
| 服务端动作授权 | 这个人能不能执行这项操作 | 控制器的权限检查或专用归属校验 |
| 数据范围 | 这个人能看到哪些记录 | 结合角色、组织、本人范围和领域聚合关系限制查询 |
| 业务规则 | 这张单据现在能不能这样操作 | 在业务状态、版本及其他约束满足时执行 |

例如，网关已经认出小李，审批接口仍可拒绝他审批别人的单据。经理有审批权限，业务服务也仍需限制他能处理哪些记录。页面有菜单、按钮能显示，只是用户界面的一部分，不能替代这些服务端检查。

客户端自己填写一个身份请求头，也不能因此指定自己的租户或管理员身份。网关会处理外来身份头；下游还需要验证网关断言，不能把任意外部文本当作内部可信身份。

## 需要排查时，再认识令牌中的字段

普通密码登录的 JWT 使用 RS256 签名。常用字段各有职责：

| 字段 | 含义 |
|---|---|
| sub | 当前主体的标识 |
| tenant_id | 这份身份声明所属的租户 |
| username | 用户名 |
| roles | 角色信息 |
| scope | 签发时写入的权限信息 |
| jti | 这一个令牌的标识，用于区分和撤销检查 |
| iat、exp | 签发时间与过期时间 |

权限信息是令牌签发时的快照。修改了岗位角色，并不等于浏览器里已经拿到一张内容更新的令牌；排查时需要同时检查新授权和当前凭据。

## 验证签名为什么不需要拿到私钥

签发方用私钥签名，验证方用公钥检查。公开公钥不等于允许别人签发凭据；能够读到令牌中的字段，也不等于修改之后仍能通过签名检查。因此，令牌内不应装入密码等秘密。

本项目网关通过 JwkKeyProvider 从 Auth 的 JWKS 端点获取 RSA 公钥并缓存。下面是决定“用缓存还是重新获取”的连续工程原文：

<!-- omni:source path="omni-backend/omni-gateway/src/main/java/com/omni/gateway/config/JwkKeyProvider.java" -->
```java
    public Mono<RSAPublicKey> getPublicKey() {
        // 缓存命中且未过期，直接返回（快速路径）
        if (cachedPublicKey != null && !isExpired()) {
            return Mono.just(cachedPublicKey);
        }
        // 缓存未命中或已过期，发起远程请求
        return fetchJwkSet();
    }
```

缓存可用就直接返回；没有缓存或缓存已过期，再请求公钥集合。缓存时间由配置控制。网关会检查业务请求的签名，并不等于每次请求都要重新从网络下载公钥。

这段代码也不是“所有密钥轮换场景都已经无缝处理”的证明。连接地址、缓存、签名密钥和旧令牌的兼容，需要结合实际配置与测试核对。

网关核验后向下游传递 X-User-Id、X-Tenant-Id、X-User-Name、角色/权限和 X-Gateway-Assertion，并移除传入的 Bearer。业务服务按自己的预认证规则验证断言，再继续处理请求。

不要把完整令牌、密码或 Cookie 贴到问题单、教程截图或公开解码网站。排查通常可以先记录时间、入口、错误提示和经过脱敏的请求关联信息。

## 本地退出、管理员踢出、协议撤销不是同一个动作

点击本项目菜单里的退出，前端会清理 token、权限状态和动态路由。它没有通过一个项目自有的 /api/auth/logout 接口，让此前签发的所有普通 JWT 立刻失效。因此，“我的浏览器回到了登录页”和“那份旧凭据在服务器上被撤销”需要分开看。

管理员踢出在线用户时，项目在授权检查后删除相应在线记录，并把该会话的 jti 放入 24 小时黑名单。该凭据之后访问受保护资源，会经过相应黑名单检查。这也不等于撤销同一用户在所有系统、所有设备上的任意凭据。

Spring 授权服务器还提供 OAuth2/OIDC 协议层的撤销和退出处理。这些机制有自己的授权记录与会话边界，不能因为框架有相应端点，就把它们写成普通密码 JWT 的全局退出实现。

## 供应商门户为什么还多一道检查

供应商门户复用本地密码认证。通过密码检查，只说明这份账号凭据能够登录。

访问供应商资料、评估或报价等门户功能，还需要 SUPPLIER 角色与有效的供应商门户关联。管理员身份并不会自动代替供应商身份。准备资料或接入新功能时，需要分别核对角色、关联和该业务的状态条件。

自助注册也是另一件事：注册成功并不自动登录，也不等于已经获得业务管理权限。新建用户路径会尝试分配默认 USER 角色；角色分配失败按当前设计记录警告，不能把“用户已创建”误写成“所有授权都已到位”。

## 当前能力的边界

- 项目自有的账号密码接口不是 OAuth2 password grant，当前没有把这种许可登记成项目支持的登录方式。
- 前端虽然有可选 refresh_token 响应字段，当前只保存访问令牌，没有自动刷新流程。客户端许可配置与前端已经实现续期，不能混为一件事。
- 门户登录复用已有密码入口，没有一套单独的门户密码凭证协议。
- 当前实际社交入口是 GitHub、Google 和 Gitee，没有 WeChat 的前端入口或后端适配器。
- 源码片段说明实现责任；运行测试、受控协议测试和真实第三方账户授权分别记录，不能互相冒充。真实第三方账号实联仍单独列为未验范围。

设备篇还列出了当前轮询与拒绝按钮的具体限制。了解限制之后再接入真实设备，不能只看到一个“成功”字样就认定已经完成业务访问。

## 遇到问题，按停下来的环节查

| 看到的现象 | 先确认什么 | 怎样继续 |
|---|---|---|
| 普通登录失败 | 企业是否可选、验证码是否已消费、账号是否锁定、密码是否正确 | 根据提示取得新验证码或处理账号状态，不连续重放旧材料 |
| 企业 SSO 回到登录页 | 会话是否建立，本次 state 和原件是否仍在，回调和客户端是否匹配 | 从原入口重新发起，避免继续使用已经清理的交换材料 |
| 设备一直等待 | 用户是否确认、授权是否过期，轮询返回的是等待还是永久错误 | 按设备页和协议错误处理，不把等待当成功 |
| 社交登录失败 | 外部平台是否拒绝、回调材料是否齐全、state 是否有效、本地绑定是否冲突 | 从该提供方入口重新发起；保留脱敏错误信息 |
| 登录后没有业务入口 | 当前身份的角色和权限、令牌是否更新、目标入口是否适用 | 检查授权和当前凭据，不让别人共用管理员账号 |
| 有功能权限却查不到某条数据 | 租户、组织、本人范围、单据归属和当前业务状态 | 按领域的数据范围规则核对，不通过改身份头绕过 |
| 门户登录后仍被拒绝 | SUPPLIER 角色、有效门户关联和供应商业务状态 | 核对入驻与关联结果，不把管理员当作供应商替身 |

普通密码登录默认的站内入口、授权码回调的控制台入口和门户入口，当前由不同前端分支处理。排查回跳时，应先确认使用的是哪一条链，再看它保存和消费了什么目标，而不是把所有登录方式看成同一次跳转。

如果你准备修改认证代码，先从对应的项目实践子篇继续。需要理解“这条身份为什么只能看本企业、本部门的数据”，再进入多租户章节。
