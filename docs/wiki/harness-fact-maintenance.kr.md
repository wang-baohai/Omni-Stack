# 사실 유지와 무효화: 문서를 코드에 맞추기

Harness의 "사실"은 장식용 설명이 아니라 실행과 검증이 함께 의존하는 현재 정보입니다. 사실이 낡으면 모델은 옛 규칙으로 코드를 만들고, 검사는 잘못된 전제에서 통과합니다. 이 글은 Omni-Stack이 현재 사실을 어떻게 기록, 갱신, 무효화하는지와 사람의 판단이 남는 지점을 설명합니다.

## 사실에 최소한 필요한 네 가지

"구매 요청서는 `proc_*` 테이블을 쓰고 테넌트는 인터셉터가 처리한다"를 예로 들면, 유지 가능한 기록에는 다음이 필요합니다.

1. **적용 범위**: 어느 모듈, 테이블, 신원에 적용되는가.
2. **현재 동작**: 마땅히 그래야 한다가 아니라 코드가 실제로 어떻게 동작하는가.
3. **증거 진입점**: 소스, 마이그레이션, 테스트, 실행 기록의 위치.
4. **무효화 조건**: 테이블 이름, 차단 범위, 권한 코드 변경 등 언제 사실이 아니게 되는가.

하나라도 빠지면 독자는 추측할 수밖에 없습니다. 특히 무효화 조건은 다음 변경 때 누가 사실을 갱신해야 하는지를 정합니다.

## 사실의 세 매체

| 매체 | 적합한 내용 | 유지 방법 |
|---|---|---|
| 사실 문서 | 아키텍처 경계, API 계약, 모듈 규칙 | 코드 변경 시 동기화하고 적용 가능한 품질 게이트 실행 |
| 문서 매니페스트 | 소스, 번역, 검토 상태, 증거 | 소스 변경으로 다이제스트 갱신과 검토 대기 발생 |
| 테스트와 검사 | 자동 판정 가능한 제약 | 실패를 피드백으로 삼고 기억에 의존하지 않음 |

세 매체는 서로 대체할 수 없습니다. 문서가 좋아도 매니페스트 상태가 참은 아니며, `synchronized`라도 본문이 소스와 일치한다는 뜻은 아니고, 테스트 통과가 모든 사실을 덮지도 않습니다.

## 소스 변경 후 일어나는 일

`refresh-source-digests.mjs`는 중국어 사실 소스의 SHA-256을 계산해 `docs/docs-manifest.yaml`의 기록과 비교합니다. 차이가 있으면 다음을 합니다.

1. 소스 다이제스트를 갱신합니다.
2. 영향을 받는 번역을 `present-unverified`로 되돌립니다.
3. 오래된 검토 완료 소스 다이제스트를 삭제하고 이력 검토 기록은 보존합니다.
4. `docs-review-queue.mjs`가 검토 대기를 다시 생성하게 합니다.

즉 중국어 본문 수정이 오래된 번역 서명을 조용히 재사용할 수 없습니다. 실제 예로 이번 변경에서 README와 `docs/wiki/index.md` 편집이 두 소스 다이제스트 차이를 일으켰습니다. 갱신 후 소개 장의 번역 세 편은 다른 영향 항목과 함께 검토 대기에 들어갔고, 그 시점의 대기열은 9건 대기, 129건 완료, 3건 중국어 전용을 보였습니다(이후 장이 추가되며 대기 수는 다시 달라졌습니다). 어느 것도 곧바로 `synchronized`로 바꾸지 않았습니다.

## 소스 발췌를 검사하는 이유

원리 글은 Java나 TypeScript를 인용합니다. 코드를 Markdown에 복사만 하면 소스 변경을 글이 알지 못합니다. `docs/scripts/source-excerpts.test.mjs`는 `omni:source` 표시가 있는 원리 페이지를 재귀적으로 찾아 로컬 발췌를 저장소의 실제 파일과 비교합니다. 상류 발췌는 `repository@commit` 형식의 출처 표시를 검사합니다. 이 검사는 상류 원문을 내려받거나 대조하지 않으므로 내용은 별도로 확인해야 합니다.

다음 경우 실패합니다.

- 발췌가 한 줄 변조됨.
- 소스 파일이 없음.
- 적용 언어 버전이 빠짐.
- 상류 발췌에 추적 가능한 버전이 없음.

실패는 "문서 테스트가 너무 엄격하다"가 아닙니다. 글이 오래된 코드를 현재로 제시하고 있다는 신호입니다. 표시를 지우거나 비교를 느슨하게 하지 말고 발췌를 갱신하고 결론을 다시 확인합니다.

## 오래된 증거가 무효가 되는 때

파일이 남아 있어도 다음은 오래된 증거를 무효화합니다.

- 본문이나 번역이 바뀜: 오래된 검토가 새 문구를 덮지 않습니다.
- 소스가 바뀜: 인용, 동작 설명, 스크린샷이 부정확해질 수 있습니다.
- 설정이나 포트가 바뀜: 시작 절차가 일치하지 않습니다.
- 의존성이나 버전이 올라감: 빌드 명령과 기대 결과가 달라질 수 있습니다.
- 환경이 바뀜: 오래된 실행 기록은 현재 환경을 증명하지 못합니다.

증거 재사용 여부는 날짜가 가까운지가 아니라 입력 다이제스트 비교에서 시작합니다. 오래된 수용 기록은 당시를 설명할 수 있지만 현재 단계의 검증을 대체할 수 없습니다.

## 유지 순환

완전한 사실 유지에는 다음이 포함됩니다.

1. 코드나 본문 변경.
2. 영향받는 사실 문서 갱신.
3. 소스 다이제스트 갱신, 무효화된 번역 확인.
4. 링크, 내용, 빌드, 영향받는 실행 검사 수행.
5. 결과와 미완료 항목 기록.
6. 지정 검토가 필요하면 대기 상태를 유지하고 서명을 위조하지 않음.

3단계에서 많은 번역이 무효화되어도 대기열을 정리하려고 일괄 동기화로 바꾸지 마세요. 대기열은 미완료 검토를 보이게 하기 위해 존재합니다.

## 사람의 판단이 남는 부분

자동 검사는 다이제스트 불일치, 발췌 변조, 죽은 링크를 찾지만 다음은 판단하지 못합니다.

- 새 동작이 업무 의도에 맞는가.
- 번역이 자연스럽고 용어가 일관되는가.
- 스크린샷이 현재 화면을 설명하는가.
- 제안을 실행할 가치가 있는가.

이들은 사람, 또는 명시적으로 권한을 받은 검토자가 실제 신원과 증거를 매니페스트에 기록해 수행합니다. 도구가 대신 서명할 수 없습니다.
