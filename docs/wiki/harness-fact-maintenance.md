# 事实维护与失效：让文档跟着代码走

Harness 里的“事实”不是漂亮说明，而是执行和验证共同依赖的当前信息。事实一旦过时，模型会按旧规则生成代码，检查也会在错误前提上通过。本文讲 Omni-Stack 当前怎样记录、刷新和失效事实，以及哪些情况仍然需要人工判断。

## 一条事实至少写清四件事

以“采购申请单使用 `proc_*` 表，租户由拦截器处理”为例，可维护的记录应包含：

1. **适用范围**：哪个模块、哪些表、对哪些身份生效。
2. **当前行为**：不是“应该”，而是代码现在实际怎么做。
3. **证据入口**：源码、迁移、测试或运行记录的位置。
4. **失效条件**：什么改动会让这条事实不再成立，例如表名、拦截器范围或权限码变化。

缺少任一项，读者只能猜。尤其是“失效条件”，它决定了下一次改动时谁会去更新这条事实。

## 事实的三种载体

| 载体 | 适合记录 | 维护方式 |
|---|---|---|
| 事实文档 | 架构边界、API 契约、模块规则 | 代码变更时同步，运行适用质量门 |
| 文档清单 | 源、译文、审校状态、证据 | 源变化触发摘要刷新与待审 |
| 测试与检查 | 可自动判断的约束 | 失败即反馈，不靠记忆 |

三者不能互相替代。文档写得好，不代表清单状态真实；清单是 `synchronized`，不代表正文仍与源码一致；测试通过，也不代表所有事实都被覆盖。

## 源变化后会发生什么

Omni-Stack 的 `refresh-source-digests.mjs` 会计算中文事实源的 SHA-256，与 `docs/docs-manifest.yaml` 中记录的值比较。发现漂移时：

1. 更新源摘要；
2. 把受影响译文的状态置回 `present-unverified`；
3. 删除旧的已复核源摘要，保留历史复核记录；
4. 由 `docs-review-queue.mjs` 重新生成待复核清单。

这意味着“改了中文正文”不会悄悄沿用旧译文的签核。真实例子：本次改造中，README 与 `docs/wiki/index.md` 的内容调整触发了 2 个源摘要漂移；刷新后，介绍章的 3 篇译文与其他受影响条目一起进入待复核队列，当时队列显示 9 篇待复核、129 篇已完成、3 篇仅中文（随后新增章节，待复核数继续变化）。这里没有把任何一篇直接改成 `synchronized`。

## 源码片段为什么也要校验

原理文章经常引用 Java 或 TypeScript 片段。如果只把代码复制进 Markdown，源码改了文章不会知道。`docs/scripts/source-excerpts.test.mjs` 会递归发现带 `omni:source` 标记的原理页，把本地片段与仓库实际文件逐段比较；对上游片段，它检查 `repository@commit` 形式的版本来源标记。这项标记检查不会下载或比对上游原文，上游内容仍须另行核对。

测试对以下情况失败：

- 片段被篡改一行；
- 源文件不存在；
- 适用的语言版本缺失；
- 上游片段没有可追溯的版本。

失败不是“文档测试太严”，而是提醒：文章正在把旧代码当现状。正确做法是更新片段并重新核对结论，而不是删除标记或放宽比较。

## 旧证据什么时候失效

以下变化会让旧证据失效，即使文件还在：

- 正文或译文内容变化：原审校结论不再覆盖新文字。
- 源码变化：引用片段、行为描述和截图可能失真。
- 配置或端口变化：启动教程的实际步骤不再一致。
- 依赖或版本升级：构建命令和预期结果可能改变。
- 环境变化：旧运行记录不能证明当前环境可用。

因此，判断“能不能复用旧证据”要先比较输入摘要，而不是看日期近不近。旧验收记录可以说明当时发生过什么，不能替代当前步骤的验证。

## 维护闭环

一次完整的事实维护至少包含：

1. 改代码或正文；
2. 更新受影响的事实文档；
3. 刷新源摘要，确认哪些译文失效；
4. 运行链接、内容、构建和受影响的运行检查；
5. 记录结果与未完成项；
6. 需要指定审校时保持待审，不伪造签核。

如果第 3 步发现大量译文失效，不要批量改成已同步来“清理队列”。队列的意义就是让未完成的复核保持可见。

## 仍然需要人工判断的部分

自动检查能发现“摘要不一致”“片段被改”“链接失效”，但不能判断：

- 新行为是否符合业务意图；
- 译文是否自然、术语是否一致；
- 截图是否仍能说明当前页面；
- 一个建议是否值得实施。

这些判断要么由人完成，要么由被明确授权的审校完成，并在清单中记录真实身份和证据。工具不能替它们签字。
