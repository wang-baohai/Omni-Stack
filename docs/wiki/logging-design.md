# 2. 方案选择：让应用记录，让工具搬运

把日志集中起来有两种常见思路：应用自己向远端发送，或者应用先写标准输出，由采集器统一读取。本工程采用后者。应用不需要在每个业务方法里接入 Loki 客户端；容器重建时，采集目标由 Docker 元数据重新发现。

## 四个角色各做一件事

| 角色 | 在本工程中的工具 | 不负责什么 |
|---|---|---|
| 产生事件 | Spring Boot 日志框架 | 不负责集中存储 |
| 发现与搬运 | Alloy | 不负责业务审计与权限判断 |
| 存储与检索 | Loki | 不代替业务数据库 |
| 查询和关联 | Grafana | 不会凭空生成尚未采集的数据 |

Loki 通过标签先缩小日志流，再过滤内容。不要把用户名、订单号或每次都不同的请求编号做成标签：值越多，管理成本越高。需要精确排查的编号可以留在必要的日志字段里，通过查询内容找到它。

## 项目怎样开启结构化输出

下面这一行来自正式应用 Compose 环境配置：

<!-- omni:source path="compose.apps.yaml" -->
```yaml
      LOGGING_STRUCTURED_FORMAT_CONSOLE: ${STRUCTURED_LOGGING_FORMAT:-ecs}
```

Spring Boot 读取对应的日志属性，默认使用 ECS（Elastic Common Schema）JSON 格式。它是一种字段约定，不是另一套消息队列，也不是自动脱敏开关。直接在其他方式下运行服务是否使用同样格式，要看那个运行入口的实际配置。

## 为什么不直接把一切写进数据库

运行日志写得频繁，保留时间和查询方式与业务表不同；业务操作审计还需要明确的租户和访问权限。把两者混到一个表，会让性能、权限和维护职责都变得模糊。当前工程把运行日志与数据库中的操作记录、安全事件分开维护。

这套方案也有成本：要维护采集、存储、保留策略和查询入口；采集服务故障期间可能出现延迟或缺口。正式生产部署仍需评估访问控制、容量和备份。仓库提供本地模板，不代表这些生产条件已经满足。
