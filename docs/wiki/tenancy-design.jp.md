# 2. 設計の考え方：会社ごとのデータをどう分けるか

A 社と B 社のデータを隔離するには、二台の機械に置く必要があるでしょうか。

必ずしもそうではありません。別のデータベース、同じ DB 内の別空間、または会社識別子を持つ共有テーブルを使えます。どの方式でも正しい認可が必要で、物理的に分けてもログイン、権限、キャッシュが自動で正しくなるわけではありません。

## 三つの代表的な配置

| 方式 | イメージ | 利点 | 引き受けること |
|---|---|---|---|
| テナントごとに DB | 会社ごとに資料室がある | バックアップ、移動、資源を個別に扱いやすい | DB、更新、接続、運用対象が増える |
| 独立 schema を使える DB 内で空間を分離 | 一つの建物に別の部屋 | オブジェクトと管理範囲をある程度分ける | DB 対応と移行ツールが必要で、行き先の誤りにも注意 |
| テナント識別子を持つ共有表 | 共有の棚で各書類に会社を記す | 配置と一括更新を集約しやすい | 読書き、キャッシュ、バックグラウンドで境界を守る |

取捨選択を理解する表で、今 DB を作ったり配置を変えたりする手順ではありません。規模、規制、復旧方法、運用能力も選択に影響します。

共有表では列を一つ追加するだけで終わらず、以後のアクセスが帰属を尊重する必要があります。

## 現在のプロジェクトの方式

業務表には所属会社を示す tenant_id を保存し、サーバーの身元、明示的クエリー、テナントプラグイン、ドメインのデータ範囲でアクセスを扱います。

マイクロサービスごとにも DB を分けています。認証とある業務サービスのデータは責任が異なります。これは**サービスごとの分離**であり、会社ごとに同じ数の新しい DB を作る意味ではありません。

二つの軸を分けましょう。

- サービスは、認証、基盤、ワークフローなどを誰が管理するか。
- テナントは、その業務記録がどの会社に属するか。

一つのサービスの DB に複数会社のデータが入り、一社の業務が複数サービスを通ることもあります。

## MyBatis-Plus を再利用する理由

MyBatis は Java の DB アクセスをマッピングします。MyBatis-Plus は共通操作とプラグイン機構を加え、プロジェクトの多くの表で使われています。

プラグインは DB アクセスの特定の段階に処理を差し込む仕組みです。後述する common-service は複数の業務サービスで使う共通支援コードです。サービスが導入して対象機能を有効にして初めて、そのチェーンを使えます。別に起動する業務サービスではなくライブラリーです。

対象の DB 文へ会社条件を加えることで、開発者が同じ制限を手書きする反復を減らします。データ範囲プラグインは本人や組織のドメイン規則を接続します。

これは現在の依存関係と実装から読める取捨選択で、過去の選定会議を創作していません。操作権限、状態変更、子記録の帰属、メッセージの会社はプロジェクト側の責任です。

次のページで実際の 3.5.16 のソースを使って機構を説明します。

## 「共通」で混同しやすい三点

**共通ログインでも認可は個別です。** 入口で人を識別しても、各業務サービスの会社と操作は確認が必要です。

**共通プラグインでも全サービスが同じ設定とは限りません。** Auth は明示的なテナント条件、common-service のドメインは有効化したプラグイン、Workflow は業務表とエンジン表の別処理を使います。

**共有キャッシュも帰属を区別します。** 一つの Redis でも鍵、読取、無効化が会社を区別する必要があります。

一般的な標語より、この処理がどの経路かを先に確認します。

## 全体共有の内容にも保護が必要な理由

テナント一覧、全体の権限コード一覧、個人ジョブ種別、Nacos/XXL-JOB の基盤は、一社の通常業務記録とは異なります。

共有とは管理境界の違いであり、匿名や通常の業務リクエストによる無制限の読書きを意味しません。中継が複数テナントを走査しても、通常クエリーの横断を正当化しません。
