# Harness의 다섯 구성 요소

Harness는 단일 부품이 아닙니다. 구매 요청서에 "예산 과목"을 추가하고 권한을 검증하는 같은 작업을 나눠 보면, 최소 다섯 부분이 협력해야 합니다. 하나라도 빠지면 어느 지점에서 검증 가능성을 잃습니다.

## 1. 문맥: 지금 무엇이 사실인지 모델에 알리기

문맥은 저장소 전체가 아니라 작업과 관련된 현재 사실입니다.

- 스키마: 구매 요청서는 `proc_*` 테이블에 있고 테넌트 필드는 인터셉터가 처리합니다.
- 모듈 경계: 승인은 `omni-workflow`에서 실행되고, 구매 서비스는 Flowable을 추가하지 않습니다.
- 기존 API: 요청과 응답은 `R<T>`, 페이지네이션은 `R<PageResult<T>>`를 따릅니다.
- 오류 의미: 권한 부족, 입력 오류, 데이터 범위 거부가 각각 어떤 상태에 대응하는지.

Omni-Stack에서 이 사실은 `AGENTS.md`, `docs/architecture.md`, `docs/api-contract.md`, 각 모듈 문서에 있습니다. 문맥의 질은 양이 아니라 "현재인가"로 결정됩니다. 오래된 사실은 없는 사실보다 위험합니다.

## 2. 도구: 행위를 실제로 일으키기

모델에는 텍스트 출력만이 아니라 엔지니어링 행위 실행이 필요합니다.

- 빌드와 테스트: Maven Wrapper, 프런트엔드 `npm run build` / `npm run lint`.
- 생성기: `tools/omni-cli`가 서비스, CRUD, 축소된 프리셋 프로젝트를 생성합니다.
- 데이터베이스: Liquibase 마이그레이션과 통제된 시드.
- 실행 환경: 로컬 Docker의 서비스, 브라우저, 로그.

도구는 "돌아갈 것 같다"를 "실제로 돌았다"로 바꿉니다. 없으면 검증은 읽기가 되고, 읽기는 포트 충돌, 마이그레이션 순서, 실제 로그인 실패를 찾지 못합니다.

## 3. 제약: 커밋 전에 오류 노출하기

제약은 저장소에 적혀 사람과 모델 모두 읽을 수 있는 규칙입니다.

- 쓰기 작업은 `resource:action` 권한 코드를 선언하고 시드와 프런트엔드 `v-permission`을 동기화합니다.
- 테넌트 차단은 모듈 테이블에만 적용하고 `sys_mq_message`는 전체 스캔 대상으로 유지합니다.
- 금액 필드는 십진 문자열을 쓰고 JSON 숫자로 보내지 않습니다.
- 데이터 권한 인터셉터는 페이지네이션 인터셉터보다 먼저 등록합니다.

제약의 가치는 자유 제한이 아니라 암묵적 경험을 검사 가능한 조건으로 바꾸는 데 있습니다. 구두 리뷰에만 있는 규칙은 모델에도 자동화에도 효력이 없습니다.

## 4. 검증: 완료에는 증거가 필요

검증은 여러 계층을 덮습니다.

| 계층 | 예 | 찾는 것 |
|---|---|---|
| 단위·구조 | 서비스 테스트, 프리셋 구조 단언 | 로직 오류와 모듈 잔여 |
| 빌드 | Maven reactor, 프런트엔드 build/lint | 컴파일, 타입, 스타일 규칙 |
| 문서 | 링크, 4개 언어 일관성, 소스 발췌 | 죽은 링크, 번역 드리프트, 오래된 예 |
| 실행 | 컨테이너 상태, 실제 로그인, 화면 조작 | 설정, 권한, 데이터 범위 |
| 납품 | 생성물 자체 빌드와 축소 | 이 저장소에 대한 암묵 의존 |

검증은 "가장 편한 명령 하나 실행"이 아닙니다. 변경은 영향을 받는 가장 높은 계층에서 확인해야 하며, 낮은 계층 통과만으로 높은 계층의 정확성을 증명할 수 없습니다.

## 5. 피드백과 체크포인트: 다음 실행을 가능하게

긴 작업은 반드시 중단됩니다. 사람이 떠나고, 모델 턴이 바뀌고, 환경이 막습니다. Harness는 네 가지 흔적을 남깁니다.

- 현재 상태: 어느 단계, 어느 대상이 끝났는지.
- 실패 증거: 명령, 종료 코드, 로그 위치, 실제 현상.
- 미완료 목록: 미시도, 차단, 리뷰 대기.
- 다음 진입점: 복귀 시 먼저 확인할 것과 재개할 행동.

흔적은 "바꾼 기억이 있다"가 아니라 검증 가능해야 합니다. Omni-Stack에서는 매니페스트 검토 상태, 소스 다이제스트 무효화, 증거 파일, 미완료 목록이 이 역할을 맡습니다.

## 다섯 요소의 관계

다섯 요소는 일직선 공정이 아니라 순환입니다.

1. 문맥이 모델이 제안할 선택지를 결정합니다.
2. 도구가 선택지를 실제로 착지시킵니다.
3. 제약이 경계를 넘는 것을 막습니다.
4. 검증이 결과를 증명하거나 실패를 드러냅니다.
5. 피드백이 실패를 다음 문맥에 되씁니다.

하나라도 빠지면 순환이 끊깁니다. 문맥이 없으면 바퀴를 재발명하고, 검증이 없으면 오류를 완료로 보며, 피드백이 없으면 다음이 0에서 시작합니다.

## 경계

부품이 많다고 더 좋은 Harness는 아닙니다. 도구나 검사를 늘릴 때마다 유지, 실행 시간, 오탐 처리 비용이 듭니다. 판단 기준은 어떤 실제 실패를 더 이르고 안정적으로 드러내는가뿐입니다. 이 질문에 답하지 못하는 부품은 쌓지 말고 제거해야 합니다.
