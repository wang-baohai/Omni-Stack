# 7. 復旧と拡張：失敗した層を先に特定する

「実行されない」には、まだ時刻でない、割り当て失敗、業務失敗、結果が戻らない場合があります。復旧入口はそれぞれ違い、連打は診断になりません。

## 手掛かりを順に追う

| 見えている状態 | 最初の確認 | すぐ行わないこと |
|---|---|---|
| システム一覧にない | 両アノテーション、配置、実行器スイッチ | 全個人処理器へシステムアノテーションを追加 |
| 未登録表示 | 遠隔照会の成否、グループ、handler | 表示だけで不在と判断して再登録 |
| 割り当て失敗 | アドレス、通信、認証、handler 名 | 業務状態の変更、根拠のない再試行 |
| 割り当て成功、実行失敗 | 実行ログ、入力、業務状態 | 割り当てを業務成功と扱う |
| 長時間進行中 | 時間、同時実行時の待機方針、タイムアウト、結果の返送 | 割り込みで全副作用が消えたと推測 |
| 個人ログなし | 割り当て、解析、DB 保存 | 成功時刻を作る |
| 作成・削除の結果不明 | 両 ID、信頼できる関連、全件照会 | 名称で推測して一括クリーンアップ |

正確な時刻とタイムゾーン、テナント、ローカル ID、実行器グループ、遠隔 ID、ログ ID を残します。パスワード、Cookie、機密を含む全引数は公開しません。

## 登録失敗後にローカル行を保持する理由

照会やクリーンアップも失敗した実際の分岐です。遠隔結果が不明なままローカル行を消すと復旧の対応関係を失います。

<!-- omni:source path="omni-backend/omni-base/src/main/java/com/omni/base/service/impl/UserJobServiceImpl.java" -->
```java
        } catch (Exception cleanupFailed) {
            // 查询/清理失败：无法确认远端，保留本地可恢复关联与停止责任，绝不删本地
            log.error("{}：调度中心反查/清理失败，保留本地待恢复记录 localId={}, executorParam={}, 需对账",
                    action, localId, executorParam, cleanupFailed);
            throw new BusinessException(500, "调度中心注册结果未知且清理失败，已保留本地待恢复记录(id="
                    + localId + ")，请联系运维对账: " + cleanupFailed.getMessage());
        }
```

既知の正確な遠隔 ID、またはグループ、共通 handler、テナントとローカル ID を含む引数で照合します。名称は重複や変更があるため削除の根拠ではありません。種子同期の再起動も結果不明の照合を代替しません。

## 個人ジョブの種別を追加する

目的、入力、重複防止を先に定義し、既存 UserJobHandler を実装します。Bean 名を種別コードと完全一致させ、入力定義も維持します。実際の水分補給ハンドラーはこう宣言されています。

<!-- omni:source path="omni-backend/omni-base/src/main/java/com/omni/base/job/handler/DrinkWaterRemindHandler.java" -->
```java
@Slf4j
@Component("Task-00001")
@RequiredArgsConstructor
public class DrinkWaterRemindHandler implements UserJobHandler {
```

メッセージに tenantId が明示されるため、HTTP スレッドへ依存しません。業務書き込みには権限、状態遷移、トランザクション、冪等性を設計し、入力された番号を信頼済み認可と扱いません。

種子、パラメータ定義、検証を同期し、構造変更には前向き移行を使います。選択肢だけの追加では不足です。これは拡張手順の説明で、新しい種別やスケジューリング機能を実装したものではありません。

## システム保守ジョブを追加する

二つのアノテーションを使い、分かる名称、既定周期、引数、ルーティングを示します。量、バッチ、並行性、冪等性、失敗後の状態を評価してから周期起動します。サービスごとの AppName は維持します。

## 有効性をどう確かめるか

同じローカル Docker 環境で専用テスト ID を使い、作成、編集、停止、手動実行、再開、本物の周期実行、成功・失敗ログ、他人・他テナントの拒否、削除後の遠隔残存なしを確認します。照合の失敗と復旧も実記録を残します。

原文一致、単体テスト、本物の Cron、画像審読は別証拠です。登録とクリーンアップでは順調な経路だけでなく応答消失と結果不明を確認します。制約は[定期実行の事実](../scheduling.jp.md)、読み直しは[章の入口](distributed-jobs-principles.jp.md)を参照してください。
