# 6. 请求之外：缓存、消息、后台任务与新功能接入

请求中的企业身份有了，并不表示一切都自动完成。数据库之外还有缓存、在线状态、消息和定时任务，它们也要知道正在处理哪一家企业的数据。

## 缓存怎样区分企业

假设甲公司和乙公司都有一个“客户等级”字典。如果缓存只按“客户等级”取值，先读过的一家公司可能影响另一家公司。

当前字典选项使用 dict:type:{tenantId}:{typeCode}。所属企业和字典类型一起组成键。DictDataServiceImpl 开头的实际片段如下，其中 CACHE_KEY_PREFIX 的值为 dict:type:。

<!-- omni:source path="omni-backend/omni-base/src/main/java/com/omni/base/service/impl/DictDataServiceImpl.java" -->
```java
    public List<SysDictData> listEnabledData(Long tenantId, String typeCode) {
        String cacheKey = CACHE_KEY_PREFIX + tenantId + ":" + typeCode;

        // 优先从 Redis 读取
        String cachedJson = stringRedisTemplate.opsForValue().get(cacheKey);
```

tenantId 是方法的显式参数，不是从缓存里猜出来的。读取、回源查询、写缓存、修改后的失效，都需要保持同一套归属规则。

前端 useDictOptions 的缓存键也包含租户。XSS 设置使用 xss:enabled:{tenantId} 与 xss:rules:{tenantId}，修改后要失效对应键。共用一个 Redis 不等于共用一份配置。

## 并非所有键都长得一样

在线状态的键是 online:{userId}，值保存 username|jti。它本身不携带完整租户信息，列表与踢出服务还要查用户表，核对企业和组织范围。

JWT 黑名单按 jti 标识具体令牌，不是为每家企业各建一张同名门禁卡。判断隔离不能只看键名，还要看关联标识、回源和操作时的授权。

## 后台线程为什么不能自动知道租户

HTTP 请求通常在一个工作线程里运行。ThreadLocal 可以理解为“这个线程暂存的小纸条”，但把工作放进线程池、消息队列或定时任务后，执行者可能已经换了线程，甚至换了服务。

因此，不能指望后台代码自动拿到浏览器请求的小纸条。该带的企业标识必须作为消息、任务或方法参数明确传过去。

可靠消息接口就要求显式的 tenantId：

<!-- omni:source path="omni-backend/omni-common-core/src/main/java/com/omni/common/core/mq/ReliableMessageRelay.java" -->
```java
    void send(String bindingName, Object payload, Long tenantId);
```

这表示调用方有责任提供归属，而不是让中继从当前线程猜。实现把消息写入本地 Outbox 后，再由后台投递。Outbox 可以先理解为业务数据库里的一份待发送清单。

个人任务的消息也有明确字段：

<!-- omni:source path="omni-backend/omni-common-core/src/main/java/com/omni/common/core/job/UserJobMessage.java" -->
```java
    /** 租户 ID，用于多租户隔离，确保任务在正确的租户上下文中执行 */
    private Long tenantId;
```

拿到这个字段还需要验证与使用它。只是给 DTO 增加一个属性，不会自动使所有处理器都正确隔离。任务路由、参数校验、业务查询和清理仍各有责任。

## 跨租户后台工作为什么不是漏洞的通行证

MQ 中继会扫描各租户的待发消息，这是基础设施需要履行的职责。消费方根据事件中的企业标识校验和处理业务，结合领域的接收去重清单 Inbox 避免重复执行；不能依赖生产者线程的上下文。

系统归档、迁移或其他运维任务也可能处理多个租户。它们有明确入口和职责，不是普通业务接口可以照搬的例外。对外消息查询仍要按 tenantId 限制。

| 内容 | 当前边界 |
|---|---|
| sys_tenant | 受控租户目录 |
| sys_permission | 全局权限码目录；角色授权仍按租户 |
| sys_user_job_type | 共享的个人任务类型目录；任务实例有自己的租户与创建人 |
| Nacos、XXL-JOB 等基础设施 | 管理面规则，不能推出业务数据任意可见 |
| MQ Relay | 有意跨租户扫描 Outbox，普通查询仍受限 |
| Flowable ACT_* | 引擎自身租户与专用查询校验，不交给领域 TenantLine 一概处理 |

“共享”说明归属方式不同，不表示可以取消身份与权限检查。

## 新增一个功能时，按一条完整路径检查

1. 先确定数据属于哪个租户，表是否有正确的租户字段，以及谁负责带入它。
2. 再确认这次查询经过哪条路径：显式 SQL、租户插件、原始 JDBC 或引擎 API。插件外的路径要单独检查。
3. 区分操作权限与数据范围。本人按申请人、负责人还是当前使用人？组织范围用哪一列？
4. 明细通过哪个主记录继承可见性？没有 owner 列时，不要凭空拼一个条件。
5. 检查缓存的键、回源和失效是否保持企业归属；在线状态等特殊键要检查关联校验。
6. 消息和定时任务显式携带企业标识，验证消费方、去重和异常重试，不依赖原请求的线程。
7. 在请求或方法结束的 finally 中清理身份与范围。写操作再核对归属、状态、版本和影响行数。

这是一条接入思路，不是要求你修改所有服务，也不是说加上一个权限注解或一个租户插件就全部完成。

## 遇到问题，先找停在哪一层

| 现象 | 先检查什么 | 恢复方向 |
|---|---|---|
| 同名账号登录到错误预期 | 登录选的企业、对应用户和当前凭据 | 从正确企业入口重新登录，不只改浏览器租户头 |
| 有菜单但看不到记录 | 操作权限、当前企业、角色范围、主组织和负责人 | 查真实归属与范围配置，不先移除筛选条件 |
| 范围服务拒绝或不可用 | 参数、权限授予、当前用户/租户、上游服务 | 按实际 403/503 等分支处理，不降级成全量查询 |
| 缓存显示另一份配置或旧值 | 键是否含必要归属、回源条件、失效是否对应 | 修正归属或失效路径后重新取得数据 |
| 后台找不到企业 | 消息/任务参数、消费者建立与清理上下文 | 显式传递并校验，不回退到猜测的企业 |
| 流程扩展表缺上下文 | 对应入口、TenantInfoHolder 与当前回退行为 | 按专门流程路径排查，不把默认 1 当安全方案 |

上述说明来自当前源码。读懂机制与真实跑过全部跨租户场景是两件事；本章没有把截图或静态片段写成所有隔离用例已通过。

后续可以优先改进缺少租户时的处理一致性、专用查询的明确归属和更完整的跨租户负例。它们需要独立的复现与验证，不能为了让文档整齐而在这里扩成业务重构。
