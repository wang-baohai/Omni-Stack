# 改良方向：先给收益、代价和验证方式

本文列的是建议，不是当前能力。每条都按“解决什么问题 → 收益 → 代价 → 如何验证 → 当前状态”写。没有验证方式的建议不进入清单，因为那只是愿望。

## 建议一：补齐多组织行业案例

**问题**：当前行业实践只有 Anthropic 一份可核验材料（2025-11-26），无法比较不同组织的取舍。

**收益**：能区分“某厂商的实现”与“多种实现都收敛的做法”，减少把单点经验当规律。

**代价**：需要网络授权、时间与人工阅读；每份材料都要记录发布日期、访问日期、支持和不支持的结论。

**验证方式**：至少两份来自不同独立组织的一手材料；每条外部主张能追溯到具体来源；文章不再出现“行业共识”这类无证据措辞。

**当前状态**：未完成。本次环境的外部检索被拦截，已记录在待核实项，未用替代材料填充。

## 建议二：扩大源码片段校验的覆盖

**问题**：`omni:source` 机制已覆盖原理页的 Java/TypeScript 片段，但并非所有带代码的文章都使用该标记。

**收益**：减少“文章仍引用旧代码”的失真，尤其是在重构后。

**代价**：每段代码都要确定唯一来源；上游片段还要记录版本；维护成本随覆盖面上升。

**验证方式**：对新增覆盖页运行 `docs/scripts/source-excerpts.test.mjs`；故意篡改一行应失败；缺源、缺语言、无版本上游也应失败。

**当前状态**：机制已存在，覆盖范围有限。建议逐章增加，而不是一次性全量搬运。

## 建议三：让复核队列按变更影响排序

**问题**：源变化会让多篇译文同时进入待复核，队列目前不区分“只改了一个链接”和“改了行为结论”。

**收益**：审校者先处理语义变化大的条目，降低等待成本。

**代价**：需要定义影响级别，并保证分级不能成为跳过复核的借口。

**验证方式**：构造两类变更（链接修正、结论变更），确认队列分级正确；分级低的条目仍保留待复核状态，不自动签核。

**当前状态**：未实现。现有队列只按状态列出，不推断影响级别。

## 建议四：把断点模板做成可复用资产

**问题**：长任务中断时，不同执行者的记录格式不一致，恢复成本高。

**收益**：恢复时能快速找到当前步骤、失败证据、未完成对象和下一步。

**代价**：模板必须足够短，否则填写本身成为负担；还要避免把模板当成“已完成”的证明。

**验证方式**：用一次真实中断恢复演练：只读模板和仓库，能否在不询问原作者的情况下继续；恢复后检查是否重复了已完成的动作。

**当前状态**：仓库已有 `ai/prompts` 与工作流资产，但统一的断点模板尚未作为产品能力提供。建议先在 `ai/prompts` 试验，不直接改执行规则。

## 建议五：为 Harness 本身建立最小度量

**问题**：没有度量时，只能凭感觉判断“加了检查是否更好”。

**收益**：能比较改动前后的返工、失败发现时间和恢复成本。

**代价**：度量容易变成数字游戏；样本少时结论不稳定；采集本身需要额外记录。

**验证方式**：先定义三个可手工采集的指标（例如首次验证通过前的返工次数、失败从发生到被发现的步骤数、中断后恢复所需动作数），连续记录若干任务后再决定是否自动化。

**当前状态**：未实现，也没有可信基线。任何“提升百分比”都不应现在写入文档。

## 不建议做的事

- 不要为了“更自动”让代理直接提交、发布或操作生产环境；权限与责任边界必须先明确。
- 不要用更多提示词替代缺失的工具或验证；提示词不能产生真实运行证据。
- 不要为了队列变绿而批量把译文改成已同步；这会破坏事实与审校的对应关系。
- 不要把单份厂商材料写成行业标准；来源的数量和独立性必须与结论强度匹配。

## 选择顺序

如果只能做一件，先做建议四：断点模板成本最低，能直接减少重复工作。建议一受外部条件限制，建议二和三需要维护投入，建议五应最后做——没有稳定流程前，度量只会记录噪声。
