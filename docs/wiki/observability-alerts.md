# 5. 告警与服务目标：亮红灯和通知送达是两件事

发现异常只是第一步。告警规则决定什么时候值得提醒，Alertmanager 再决定怎样分组、何时重复和送往哪里。还有人要根据业务影响处理，不能把“页面有告警”当成“值班人已经收到”。

## 看一条真实规则，不先背查询语言

仓库的服务不可用规则如下：

<!-- omni:source path="observability/prometheus/alerts.yml" -->
```yaml
      - alert: OmniServiceDown
        expr: up{job="omni-platform"} == 0
        for: 2m
        labels: {severity: critical}
        annotations:
          summary: "Omni 服务不可用（示例阈值，发布前校准）"
```

up 来自 Prometheus 抓取结果。条件为零持续两分钟后，这条规则进入触发状态，severity 是配置的严重程度。两分钟和标签都是当前示例，不是对所有业务的承诺；它检查的是采集目标，并不能独自判断整条业务是否可用。

HTTP 5xx 比例、P95/P99、连接池、Outbox 积压或死信、工作流与调度失败、磁盘、容器重启、内存和死锁也有对应规则。不要只改图上的颜色，而不理解规则的时间窗口和分母。

## 默认接收器明确不会发送真实通知

标准模板是：

<!-- omni:source path="observability/alertmanager/alertmanager.yml" -->
```yaml
route:
  receiver: local-null
  group_by: [alertname, service_name]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

receivers:
  - name: local-null
```

local-null 没有外部通知通道。即使看到告警，默认配置也不证明发了邮件、短信或 webhook。group_wait 等待初次分组，group_interval 控制后续组更新的间隔，repeat_interval 控制重复提醒；它们也不是外部接收方确认成功的凭据。

项目的四语 Alertmanager 界面代理同一个后端，宿主标准入口为 127.0.0.1:9093，语言路径为 zh-CN、en-US、ja-JP、ko-KR。换语言不会多开一套告警后端，协议标签与接收器名也不翻译。

## 在实际网页中读告警，而不是只认红灯

![Alertmanager 当前告警页：语言、筛选、分组和真实空列表](../images/zh-CN/monitor-alertmanager.png)

顶部“告警”看当前列表，“静默规则”查看已有临时屏蔽，“状态”查看后端状态，“设置”是界面选项。筛选器用于缩小标签范围，分组用于把相关告警放在一起；接收器筛选决定当前看哪一路通知对象。

图中没有告警组，这是拍摄时的真实结果，没有注入虚假告警。空列表只说明当前筛选下没有匹配项，不代表告警规则一定正确，更不代表邮件已送达。还要检查筛选器、是否显示已静默或受抑制的项目，以及 Prometheus 的规则状态。

“新建静默”会改变一段时间内的通知行为，不能当作清除故障。排查前先了解标签和有效期，避免误屏蔽其他问题。本次截图没有创建静默、改接收器或发送外部消息；默认 local-null 的无外发边界仍然成立。

## SLI、SLO 和错误预算，用一个例子分开

SLI 是衡量方式，例如“有效请求中非 5xx 的比例”。SLO 是期望目标，例如某个用户旅程在三十天内达到约定成功率。错误预算是这个目标允许的不成功部分。

假设采用按时间衡量的可用性，三十天 99.9% 对应四十三分十二秒不可用预算；如果按请求数衡量，预算应按失败请求数量计算，不能直接套这个分钟数。两种口径必须先说清楚。

仓库中的 99.9%、延迟目标和告警倍数都是模板值，并非本项目已经作出的服务承诺。不要把本地低流量下的一次绿灯当成生产 SLO 达成。

## 阈值怎样变得有用

先定义具体用户旅程和有效请求集合，再观察代表性流量、日周变化和下游限制。根据这些数据分别校准服务的错误率、耗时与积压阈值，指定负责人和复核时间。

还要验证不可用、5xx、死信和通知接收失败时会发生什么。配置语法通过、规则触发、通知送达、业务恢复，应分别留下证据。当前默认接收器没有真实通知，这是明确的边界，不能用虚构截图补齐。
