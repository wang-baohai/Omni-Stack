# CRM プリセット：基盤プラットフォームと販売パイプライン

CRM プリセットは core の認証・基盤プラットフォームに顧客関係管理サービスを加えます。見込み客、顧客、連絡先、商談、フォローアップ記録が必要で、SRM、購買、資産、承認フローはまだ不要なチーム向けです。本ページのモジュール、サービス、ポートは現在の `scaffold/presets/crm.yaml`、`scaffold/catalog/modules.yaml`、`preset explain crm` の実際の解析結果です。実行結果は「検証済み/未検証」に分けて示し、構造解析を起動成功とは書きません。

本ページの実行結果はカバレッジ絞り込みの不具合修正前の段階別記録で、現行版の結果ではありません。初期の失敗や未完了は残し、その後の成功で過去の段階に遡って合格を付けません。旧 G7 の通過は現行版の全要件を証明できず、公開時は全適用要件を保持した G6/G7 と必要な G11 で再検証します。

## 誰に向くか

- 「見込み客 → フォローアップ → 顧客/連絡先 → 商談 → 受注/失注」の販売チェーンをまず動かしたいチーム。
- テナント分離、機能権限、データ範囲、PII マスキングが必要で、サプライチェーンやワークフローは同時に導入したくないプロジェクト。
- CRM を業務例として使い、その後で見込み客、顧客、商談の実装を自社のドメインモデルに置き換える開発者。

向かない場面：サプライヤ、購買、資産の連携、BPMN 承認、スケジューリングセンターによる定期実行が必要な場合。CRM プリセットには SRM、購買、資産、workflow、RocketMQ、`xxl-job` は含まれません。CRM モジュールは catalog で RocketMQ/xxl-job を任意依存として挙げていますが、本プリセットはそれらを選択していません。そのため「非同期メッセージ中継やスケジューリングが利用可能」という前提で受け入れ条件を設計しないでください。

## 明示 5 から閉包 8 へ

`scaffold/presets/crm.yaml` の明示モジュール：

```text
crm, gateway, mysql, redis, nacos
```

`preset explain crm` が現在解析する閉包：

```text
platform, auth, base, crm, nacos, gateway, mysql, redis
```

`crm` は `base`、`base` は `auth`、`auth` と `nacos` は `platform`、`gateway` は `base` に依存します。`auth`/`base` を明示しなくても、ログイン、権限、組織、辞書、ログ、基盤管理が閉包に残る理由です。CRM はそれらの上に加わり、置き換えるものではありません。

## 実際のサービスとポート

8 モジュールは 9 つの Compose サービスに対応します。

| サービス | 由来モジュール | 役割 |
|---|---|---|
| `mysql` | mysql | 基盤と CRM の業務データ |
| `redis` | redis | キャッシュとトークン関連データ |
| `nacos` | nacos | サービス発見と設定センター |
| `omni-db-migrator` | platform | 一度きりのスキーマ移行とシード初期化 |
| `omni-auth` | auth | ログイン、テナント、RBAC、組織、辞書、監査 |
| `omni-base` | base | 基盤管理、ログ、ワークベンチ、タスク API |
| `omni-crm` | crm | 見込み客、顧客、連絡先、商談、フォローアップ、販売パイプライン |
| `omni-gateway` | gateway | 統一入口とルーティング |
| `omni-frontend` | platform | Vue フロントエンド |

catalog が宣言するポートは合計 18 個です。

| モジュール | 宣言ポート |
|---|---|
| platform | 80, 3000 |
| auth | 8100, 19900, 9900 |
| base | 8101, 19901, 9901 |
| crm | 8104, 19904, 9904 |
| gateway | 8102, 19902 |
| nacos | 8080, 8848, 9848 |
| mysql | 3306 |
| redis | 6379 |

フロントエンドは platform が宣言する 3000 番でアクセスし、CRM バックエンドは 8104 番です。ポートが使用中の場合は、占有を解除するか配備ドキュメントに従ってローカルマッピングを調整してください。競合を避けるためにプリセットの閉包を変えたり、ランダムなポート偏移を使ったりしないでください。

## 利点とコスト

利点は境界が明確なことです。認証、テナント、RBAC、基盤管理はプラットフォームから提供され、CRM は自身のサービス、権限ツリー、ロール、テーブルだけを追加します。販売パイプライン、見込み客の変換、顧客の所有ルールは `omni-crm` に集中するため、個別に置き換えたり削減したりできます。

コストは core より構成と運用面が明らかに大きいことです。JVM サービスが 1 つ増え、CRM の移行とシードが 1 組増え、4 つの CRM ロールと `crm:*` 権限コード群が加わります。データ範囲は本人、部門、テナントの 3 種類にまたがり、PII 項目はマスキング規則の対象です。catalog の各モジュール `resourceHints` を合計すると、閉包の最小メモリ目安は 3840 MB、推奨は 6400 MB です。これは計画上の目安であり実測上限ではありません。実際の使用量は `docker stats` で確認してください。

## 前提と設定

- **Docker とポート**：3000、8100、8101、8102、8104、3306、6379、8080、8848、9848 が空いている必要があります。
- **プライベート `.env`**：データベース、Redis、Nacos 認証、ゲートウェイ断言などの秘密値。実値をコミットせず、サンプル値を利用可能な秘密として扱わないでください。
- **Nacos 設定**：`omni-common.yml`、`omni-auth.yml`、`omni-base.yml`、`omni-crm.yml`、`omni-gateway.yml`。Nacos 認証を有効にする場合、全クライアントが同じ `NACOS_USERNAME` / `NACOS_PASSWORD` を使います。
- **移行とシード**：`omni-db-migrator` が実行します。共有データベースが初期化済みの場合は、再インポート、移行の再実行、クリアを行わないでください。
- **ログイン主体とロール**：`auth.sql` がテナント、管理者、ロール/権限シードを提供します。CRM ロールは `CRM_ADMIN`、`SALES_MANAGER`、`SALES_REP`、`CRM_VIEWER` です。シードアカウントが CRM メニューを見られるかは、そのロールに `crm` と `crm:*` 権限が付与されているかで決まります。

### 認証シードと業務サンプルデータは別物

- **認証/基盤シード**（`scripts/sql/seed/auth.sql`、`base.sql`、`nacos.sql`）は、テナント、ユーザー、ロール、権限、組織、辞書など「ログインでき、認可できる」基盤データを担当します。
- **CRM 業務シード**（`scripts/sql/seed/crm.sql`）は、既定の販売パイプラインとステージ、CRM テナント設定、テナント 1 のデモ用見込み客、顧客、連絡先、商談、フォローアップ記録、変換記録を担当します。
- 業務サンプルデータは初回アクセスで空にならないための例であり、CRM 起動の必須条件ではありません。見込み客や顧客がない場合は、まず「業務データが空」なのか「サービス/権限の故障」なのかを判断してください。デモのためにデータベース状態を直接変更しないでください。
- 他のテナントはテナント作成イベントで CRM ロール、権限、既定設定を受け取ります。デモ業務記録は正式シードが対象とするテナント 1 にのみ存在します。テナントをまたいで見えないのは分離が機能しているためで、メニュー欠落ではありません。

## 経路 1：ソースから CRM を起動する

### クリーンなデータベースへの初回インストール

共有データが未初期化の独立環境で：

```bash
docker compose --parallel 1 --profile crm up -d --build
docker compose ps
```

期待結果：`omni-db-migrator` が実行後に終了し、mysql/redis/nacos/auth/base/crm/gateway/frontend が起動し、`docker compose ps` のアプリケーションサービスが healthy になり、フロントエンド 3000 にアクセスできます。この経路は移行とシードを実行するため、空のデータベースまたは初期化が明示的に許可された環境だけに使います。

### 既存共有環境での原位サブセット

データベースが full で初期化済みの場合は、migrator を再実行しません。今回のソースイメージをビルドし、CRM 閉包外の業務アプリケーションを停止してから、CRM アプリケーションだけを置き換えます。

```bash
docker compose --parallel 1 -p omni-stack build omni-auth omni-base omni-crm omni-gateway omni-frontend
docker compose -p omni-stack stop omni-workflow omni-srm omni-procurement omni-asset xxl-job-admin rocketmq-broker rocketmq-namesrv
docker compose -p omni-stack up -d --no-build --no-deps --force-recreate omni-auth omni-base omni-crm omni-gateway omni-frontend
docker compose -p omni-stack ps
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/
```

- `docker compose --parallel 1 ... build`：CRM 閉包内の 5 アプリケーションだけのイメージをビルドします。migrator を起動せず、mysql/redis/nacos も再構築しません。
- `docker stop`：CRM 閉包外の業務アプリケーションを停止し、同じ環境に複数の業務実行面が併存しないようにします。基盤とデータボリュームは保持します。
- `up -d --no-build --no-deps --force-recreate`：ビルド済みイメージで 5 アプリケーションを原位置換します。依存サービスを起動せず、移行も実行しません。
- `ps`：コンテナの実際の状態とイメージを確認します。healthy はプロセスとヘルスチェックの通過だけを意味し、業務フローの完了を意味しません。
- `curl`：フロントエンドの 200 を確認します。トークンなしの `/api/crm/lead/list` が返す 401 は認証拒否だけを示します。ルートと下流サービスの可用性には認可済みリクエストの成功、登録と健全性の証拠も必要で、401 だけからは判断できません。

停止リストは現在の環境に実際に登録されたサービスで埋めてください。他のプリセットをそのままコピーしないでください。mysql/redis/nacos とデータは保持し、`down -v` やボリュームのクリアを実行しないでください。

## 経路 2：独立した CRM プロジェクトを生成する

```bash
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm run dev -- preset create crm --output generated/learning-crm
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm run dev -- preset validate crm --output generated/learning-crm
```

- `preset create`：CRM プリセットを独立プロジェクトに削減します。成果物には独自の `scaffold.lock`、Compose、ドキュメント、Maven、フロントエンドソースが含まれます。
- `preset validate`：生成物のモジュール閉包、Compose、ドキュメント、AI 入口、削減境界を検証します。アプリケーションは起動しません。
- 生成物には独自のビルドコマンドがあります。生成物内でそのコマンドを使ってください。元のリポジトリディレクトリで生成物の Compose プロジェクトを起動したり、生成物の migrator で共有データベースを上書きしたりしないでください。

過去の初期段階：G6 構造は通過しました（固定成果物位置で 8 モジュール/9 サービス）。G7 では生成物のバックエンド `./mvnw clean install` が BUILD SUCCESS に達しました（CRM とゲートウェイのテストを含む）。ただしフロントエンド `npm run build` は未通過です。初回は `@rolldown/binding-linux-x64-gnu` が不足し、検証ボリュームの npm キャッシュをクリアした再実行では Maven ダウンロード中に TLS ハンドシェイク終了が発生しました。交付ロールの分離と生成物イメージの原位置換は未実行です。したがって「生成物のバックエンドがビルドできる」は「生成物が同じ環境で起動済み」ではありません。本ページでは両者を混同しません。

## 初回利用

1. `http://localhost:3000` を開き、開発テナントを選び、シードアカウントと**今回表示された CAPTCHA** を入力します。ローカルのデモ管理者は `admin` です（パスワードは[初回起動チュートリアル](../guides/quick-start.jp.md)を参照）。古い CAPTCHA を再利用したり、認証バイパスを使ったりしないでください。
2. Wiki ホームは元のタブに残し、マイワークスペースを別タブで開きます。アプリ一覧から CRM を新しいタブで開くと、概要、見込み客、顧客、連絡先、商談、フォローアップなど CRM のメニューだけが表示されます。権限は引き続き `/api/auth/menus` に基づきます。
3. 推奨する操作順：見込み客の作成 → フォローアップ記録 → 見込み客の変換（顧客/連絡先/商談を生成）→ 商談ステージの推進 → 受注または失注 → 顧客と連絡先の保守。デモデータには一部の変換結果が含まれ、そのまま閲覧できます。新規記録は今回の操作が返す ID を基準にしてください。
4. メニューが見えるのに一覧が空の場合は、現在のテナントとデータ範囲を確認します。`SALES_REP` は本人データ、`SALES_MANAGER` は部門以下、`CRM_ADMIN`/`CRM_VIEWER` はテナント単位です。他人のデータが見えないのはデータ権限が機能している可能性があり、API 障害とは限りません。
5. メニューがない場合は、現在のロールに CRM 権限が付与されているか確認します。`SUPER_ADMIN`、`CRM_ADMIN`、`SALES_MANAGER` は CRM の全権限、`SALES_REP` は日常入力と変換の権限、`CRM_VIEWER` は読み取り専用一覧の権限を持ちます。メニューを「直す」ためにデータベースのロールテーブルを直接変更しないでください。

## 成功基準

- CRM 閉包のアプリケーションサービスが healthy で、migrator が期待どおり終了する。
- フロントエンド 3000 が 200 を返し、静的リソースが読み込める。
- 実際の CAPTCHA でログインが成功し、`/api/auth/menus` が現在のログイン主体で見える CRM メニューを返す。
- CRM の概要、見込み客、顧客、連絡先、商談、フォローアップのページが開ける。権限のあるログイン主体はシードのデモデータを読める。
- 作成や変換などの書き込み操作は実際の API 結果で判断する。ヘルスチェックの通過は業務フローの完了ではない。
- 新しいプロジェクト、ネットワーク、ボリューム、ポート偏移がなく、共有データがクリアまたは再移行されていない。

**メニュー境界**：full で初期化した共有データベースでは、対応サービスを停止しても他の業務権限コードが残ることがあります。これは共有データの状態であり、CRM 閉包に SRM/購買/資産/ワークフローが含まれる証拠ではありません。「CRM プリセットに他の業務メニューがない」ことを検証するには、CRM シードで初期化した独立の空データベースまたはテナントを使います。既存の共有データベースで権限を削除したりロールを変えたりして模擬しないでください。

## 停止と復旧

- 今回起動したアプリケーションだけを停止します。コンテナ名で `docker stop` するか、Compose で明示サービスを停止します。mysql/redis/nacos とデータボリュームは保持します。
- 復旧：登録した元のサービス集合を `docker start` するか、明示サービスに `up -d --no-build --no-deps` を実行します。スタック全体の `down -v`、ボリュームのクリア、グローバル prune は行わないでください。
- 置換に失敗した場合は、置換前に記録した旧イメージを同じサービス位置で復元します。サイドサービスを起動しないでください。

## よくある失敗

| 症状 | まず確認 | してはいけないこと |
|---|---|---|
| ポート競合 | 3000/8100/8101/8102/8104/3306/6379/8080/8848/9848 | プリセット閉包の変更やランダムなポート偏移 |
| Nacos 認証失敗 | `.env` と Nacos の資格情報が一致するか | 認証の無効化やサンプル秘密の書き込み |
| ゲートウェイ 503/認可失敗 | 断言秘密、`omni-crm` の登録、ルート設定 | フロントエンドのリクエスト URL だけを変更 |
| CRM メニューがない | 現在のロールに `crm:*` が付与されているか、`/api/auth/menus`、auth/base の健康 | データベースのメニューやロールを直接変更 |
| ページは開けるが一覧が空 | 現在のテナント、データ範囲、業務データの有無 | 空データを起動失敗とみなす、手作業でデータを追加 |
| 見込み客の変換に失敗 | 見込み客の状態、必須項目、`crm:lead:convert` 権限 | API を迂回して顧客/商談を直接挿入 |
| 移行が二重実行される | 共有データベースが初期化済みか | データベースをクリアして再実行、シードの再インポート |

## 過去の段階別記録と検証範囲

- **検証済み（ソース経路）**：5 つのアプリケーションイメージをビルドし、同じ `omni-stack` プロジェクトで原位置換しました。auth/base/crm/gateway が healthy、フロントエンドが 200。実際の CAPTCHA ログインが code 200 を返しました。`/api/auth/menus` は 57 ノードを返し、CRM ディレクトリと 6 つの販売メニューが揃っています。`omni_crm` の読み取り専用クエリは lead=8、customer=5、opportunity=6、activity=13、pipeline_stage=6 でした。終了後、元に登録された 15 コンテナが再び稼働しました。
- **検証済み（生成経路、一部）**：G6 構造が 8 モジュール/9 サービスで通過しました。生成物のバックエンド `./mvnw clean install` が BUILD SUCCESS に達し、CRM の 45 テストとゲートウェイのテストが通過しました。
- **未検証**：生成物のフロントエンド `npm run build`（ネイティブバインディング不足と、その後の Maven TLS ハンドシェイク中断）、交付ロール分離、生成物イメージの原位置換、クリーンな空データベースへの初回インストール、CRM ページのブラウザ視覚レンダリングと業務書き込みフロー、スケジューリングと非同期中継（本プリセットに `xxl-job`/RocketMQ は含まれません）。
