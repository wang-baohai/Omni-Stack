# Harness 的五个组成部分

Harness 不是单一组件。把同一个任务——给采购申请单增加“预算科目”并验证权限——拆开看，它至少需要五部分协作。缺任何一部分，任务都会在某个环节失去可验证性。

## 一、上下文：让模型知道“现在是什么样”

上下文不是把整个仓库塞给模型，而是给出与当前任务相关的当前事实：

- 表结构：采购申请单在 `proc_*` 表，租户字段由拦截器处理。
- 模块边界：审批运行在 `omni-workflow`，采购服务不引入 Flowable。
- 现有接口：请求/响应遵循 `R<T>`，分页使用 `R<PageResult<T>>`。
- 错误语义：权限不足、参数错误和数据范围拒绝分别对应什么状态。

在 Omni-Stack 中，这些事实由 `AGENTS.md`、`docs/architecture.md`、`docs/api-contract.md` 和对应模块文档承载。上下文的质量取决于“是否当前”，而不是“是否很多”。过时的事实比没有事实更危险。

## 二、工具：让动作真的发生

模型需要能执行工程动作，而不是只输出文本：

- 构建与测试：Maven Wrapper、前端 `npm run build` / `npm run lint`。
- 生成器：`tools/omni-cli` 生成服务、CRUD 和裁剪预设工程。
- 数据库：Liquibase 迁移与受控种子。
- 运行环境：本机 Docker 中的服务、浏览器和日志。

工具的意义是把“我认为能跑”变成“实际跑过”。没有工具，验证只能靠阅读；阅读无法发现端口占用、迁移顺序或真实登录失败。

## 三、约束：让错误在提交前暴露

约束是写在仓库里、能被人和模型共同读取的规则：

- 写操作必须声明 `resource:action` 权限码，并同步种子和前端 `v-permission`。
- 租户拦截只作用于本模块表，`sys_mq_message` 保持全局可扫描。
- 金额字段使用十进制字符串，不能以 JSON 数字传输。
- 数据权限拦截器必须先于分页拦截器注册。

约束的价值不在于“限制自由”，而在于把隐性经验变成可检查的条件。一条只存在于口头评审里的规则，对模型和自动化都无法生效。

## 四、验证：让完成有证据

验证要覆盖不同层次：

| 层次 | 例子 | 能发现什么 |
|---|---|---|
| 单元/结构 | 服务单测、预设结构断言 | 逻辑和模块残留 |
| 构建 | Maven reactor、前端 build/lint | 编译、类型、样式规则 |
| 文档 | 链接、四语一致性、源码片段 | 死链、译文漂移、示例失真 |
| 运行 | 容器健康、真实登录、页面操作 | 配置、权限、数据范围 |
| 交付 | 生成工程自身的构建与裁剪 | 只在本仓库可用的隐式依赖 |

验证不是“跑一个最方便的命令”。同一变更至少要在受影响的最高层验证；只在低层通过，不能推出高层正确。

## 五、反馈与断点：让下一次能继续

长任务一定会中断：人离开、模型换轮次、环境阻塞。Harness 要留下四类痕迹：

- 当前状态：做到哪一步、哪些对象已完成。
- 失败证据：命令、退出码、日志位置、实际现象。
- 未完成清单：哪些是未尝试、哪些是阻塞、哪些只缺审校。
- 下一步入口：恢复时要先核对什么、从哪个动作继续。

这些痕迹必须是可核对的，而不是“我记得改过”。在 Omni-Stack 中，文档清单的审校状态、源摘要失效、证据文件和未完成清单承担这一职责。

## 五部分之间的关系

五部分不是流水线，而是循环：

1. 上下文决定模型能提出什么方案。
2. 工具让方案落地。
3. 约束在落地时拦截越界。
4. 验证证明结果，或暴露失败。
5. 反馈把失败写回上下文，供下一次使用。

任何一环缺失，循环就会断：没有上下文会重复造轮子，没有验证会把错误当完成，没有反馈会让下一次从零开始。

## 边界

组件越多不等于 Harness 越好。每增加一个工具或检查，都要付出维护、运行时间和误报处理的成本。判断是否值得，只看它是否让某类真实失败更早、更稳定地暴露。不能回答这个问题的组件，应该删掉而不是继续堆叠。
