# 프리셋이란: 소스 하위 집합과 생성 프로젝트의 선택

"프리셋"은 또 다른 코드베이스가 아니라 모듈 선택에 붙인 이름입니다. `scaffold/presets/*.yaml`은 명시 모듈만 나열하고, 실제 구성은 `scaffold/catalog/modules.yaml`의 의존성에서 계산됩니다. 이 이해가 축소의 이익과 비용을 판단하는 토대입니다.

## 명시 모듈과 의존성 폐쇄

core를 예로 봅니다.

```yaml
id: core
displayName: 코어 플랫폼
description: 인증, RBAC, 조직, 사전, 로그, 기본 작업.
modules: [base, gateway, mysql, redis, nacos]
```

파일에는 명시 모듈 5개만 있지만 `base`는 `auth`에, `auth`와 `nacos`는 `platform`에, `gateway`는 `base`에 의존합니다. 현재 CLI 해석 결과는 7개 모듈입니다.

```text
platform, auth, base, nacos, gateway, mysql, redis
```

따라서 두 가지를 반드시 구분합니다.

- **명시 모듈**: 사람이 프리셋 파일에 쓴 선택.
- **의존성 폐쇄**: catalog가 의존성으로 계산한 실제 모듈 집합.

명시 목록만 바꾸고 폐쇄를 확인하지 않으면 "선택하지 않았으니 없다"고 오해하기 쉽습니다. 예를 들어 `auth`는 직접 쓰지 않았지만 로그인과 권한은 기반의 전제이므로 core 폐쇄에 포함됩니다.

## 프리셋을 쓰는 두 방법

| 방법 | 명령 형태 | 산출물 | 용도 |
|---|---|---|---|
| 소스 하위 집합 | `dev up --preset core` | 현재 소스 트리에서 폐쇄 서비스만 기동 | 소스 읽기, 디버깅, 같은 저장소에서 개발 |
| 생성 프로젝트 | `preset create core --output ...` | 자체 잠금, 문서, AI 진입점을 가진 새 축소 프로젝트 | 독립 프로젝트 납품, 더 작은 코드베이스에서 시작 |

둘은 같은 뜻이 아닙니다.

- 소스 하위 집합은 전체 소스 트리를 유지하고 기동 서비스만 줄입니다. 선택하지 않은 모듈이 디스크에 남을 수 있습니다.
- 생성 프로젝트는 모듈, 프런트엔드 자산, 문서, 시드, 설정 참조를 축소합니다. 산출물은 자족해야 하며 원 저장소 경로에 의존해서는 안 됩니다.
- 둘 다 DB 마이그레이션, 시드, 사설 설정, Nacos 인증이 필요합니다. 축소가 줄이는 것은 구성이지 이런 전제가 아닙니다.

## 이익과 비용

**이익**

- 서비스, 포트, 프로세스 수가 줄어 기동과 조사의 범위가 작아집니다.
- 권한, 메뉴, 게이트웨이 라우트, 마이그레이션이 선택한 폐쇄 주변으로 한정되어 읽기 잡음이 줄어듭니다.
- 생성 프로젝트는 불필요한 업무를 싣지 않고 독립 납품할 수 있습니다.

**비용**

- 프리셋은 모듈 선택만 나타내며 비밀, 테넌트, 포트 충돌 처리, 외부 의존성을 채우지 않습니다.
- 축소한 프로젝트도 마이그레이션과 시드가 필요합니다. DB가 없으면 인증과 권한은 동작하지 않습니다.
- 자원은 0이 아닙니다. catalog는 모듈별 최소/권장 메모리 힌트를 가지며 core 7개 모듈 합계는 최소 3328 MB, 권장 5632 MB입니다. 이는 **설정 힌트의 산술 합이며 실측값이 아닙니다**. 실제 값은 JVM, DB 캐시, 빌드, 호스트 부하에 따라 달라집니다.
- 구성이 줄어도 복잡성이 0이 되지는 않습니다. Nacos 설정, 게이트웨이 단언, DB 연결, 로그를 이해해야 합니다.

## 다섯 프리셋의 위치

| 프리셋 | 한 줄 | 상세 페이지 |
|---|---|---|
| `core` | 인증, RBAC, 조직, 사전, 로그, 기반 | [core 프리셋](preset-core.kr.md) |
| `workflow` | 기반에 독립 승인 서비스 추가 | [workflow 프리셋](preset-workflow.kr.md) |
| `crm` | CRM 영업 파이프라인 추가 | [crm 프리셋](preset-crm.kr.md) |
| `supply-chain` | SRM, 구매, 자산 추가 | [supply-chain 프리셋](preset-supply-chain.kr.md) |
| `full` | 다섯 업무 방향의 합집합 | [full 프리셋](preset-full.kr.md) |

이 표는 위치만 보여 주며 의존성 매트릭스를 복제하지 않습니다. 가로 비교는 [프리셋 선택 가이드](../preset-quick-selection.kr.md)와 [의존성 매트릭스](../preset-dependency-matrix.kr.md)를 보세요. 선택 전에 명시 모듈, 폐쇄, 서비스, 포트, 자원 힌트를 보고 이름만으로 결정하지 마세요.

## 다섯 프리셋 × 두 경로: 과거 실측 매트릭스

이 표는 커버리지 축소 결함을 수정하기 전 실행 기록입니다. 컨테이너·메뉴·심사 대기 수는 당시 값이며 현재 버전의 값이 아닙니다. 이전 생성기는 증거가 없으면 검증 요구사항을 삭제했으므로 이전 G7과 `automated-delivery-pass`**로 현재 버전의 완전한 인수를 증명할 수 없습니다**. 빌드·기동·납품 실행 환경 분리에 대한 과거 증거는 입력이 여전히 유효한 범위에서 재사용할 수 있습니다. 현재 릴리스에는 모든 적용 요구사항을 보존한 G6/G7과 필요한 G11 재검증이 필요합니다.

열 칸에 공통으로 적용되는 세 가지 경계:

- **깨끗한 빈 DB 최초 설치는 다섯 프리셋 모두 미실측**: 검증 환경은 full로 초기화된 공유 DB이며 제2 환경·새 DB·데이터 삭제는 허용되지 않습니다. 공유 DB 결과를 빈 DB 설치 결과로 쓰지 마세요.
- **릴리스 준비 여부는 심사 대기 수만으로 판단하지 않습니다**: 표의 `release_ready=false`와 자동 검사 18개 통과는 과거 결과입니다. 현재 번역 심사·전체 커버리지·실제 게이트 결과도 확인해야 하며 이전 통과 결과를 새 생성물에 그대로 계승하면 안 됩니다.
- **healthy와 로그인 성공만으로 전체 업무 흐름을 증명할 수 없습니다**: 표의 과거 실행에서는 모듈 간 심층 체인을 검증하지 않았습니다. 이후 완료한 체인은 해당 버전의 실제 업무 증거로 확인해야 하며 이 표에서 추정할 수 없습니다.

## 선택 전 네 가지 질문

1. **어떤 신원과 권한이 필요한가?** 업무 모듈이 없을 때 core가 로그인, 테넌트, 역할, 조직, 사전을 덮는가.
2. **어떤 런타임 의존성이 필요한가?** DB, Redis, Nacos가 폐쇄에 있고 스케줄러와 메시지 큐가 선택되었는가.
3. **설정은 어디서 오는가?** `.env`, Nacos 설정, DB 초기화를 누가 제공하는가.
4. **소스 하위 집합인가 생성 프로젝트인가?** 전자는 개발, 후자는 납품에 맞고 검증 기준이 다릅니다.

## 놓치기 쉬운 경계

core 설명에는 "기본 작업"이 포함되지만 현재 core 폐쇄에는 **`xxl-job`이 없습니다**. `platform`은 공통 작업 모듈을, `base`는 작업 관련 코드와 API를 포함하지만 스케줄러 서비스는 core의 Compose 서비스 집합에 없습니다. 시스템/개인 정기 작업을 실제로 실행하려면 `xxl-job`을 포함한 프리셋을 선택하거나 "작업 코드는 있으나 스케줄러는 없음" 제약을 명시적으로 받아들여야 합니다. 모듈 코드의 존재를 스케줄러 동작으로 쓰지 마세요.
