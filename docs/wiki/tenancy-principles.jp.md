# 1. マルチテナント入門：一つのシステムを複数の会社で使う

A 社と B 社が Omni-Stack で自社の業務を管理するとします。同じアプリを開いても、A 社の社員が B 社の顧客、供給者、申請を見られるようになってはいけません。

マルチテナントが扱うのは、**ソフトウェアを共有しても、それぞれのデータが誰のものかを把握し、境界を守って使うこと**です。テナントは会社ごとの業務空間と考えられます。社員アカウントは対応する会社の空間に属します。

概念を先に説明し、その後でフレームワークとプロジェクトのソースを読みます。最初の二ページに Java やデータベースの知識は不要です。

## 同名の二人から考える

A 社にも B 社にも李さんがいるかもしれません。同じ名前でも同じアカウントではありません。ログインで先に会社を選ぶと、正しい空間から人を探せます。

両社に「営業管理者」のロールがあっても、同じ認可記録を共有する意味ではありません。どの会社のロールで、誰に割り当て、どの記録を扱うのかをそれぞれ確認します。

これは規則を理解するための物語です。提供済みのテストアカウントや、この名前で業務データを作る手順ではありません。

| 人物 | 会社の空間 | 部門 | 担当 |
|---|---|---|---|
| A 社の李さん | A 社 | 東部営業部 | 自分の顧客を管理 |
| A 社の王マネージャー | A 社 | 東部営業部 | 部門が担当する顧客を参照 |
| B 社の李さん | B 社 | 顧客サービス部 | B 社の記録を処理 |

王さんの権限が李さんより広くても、B 社の管理者になるわけではありません。部門、役割、会社の空間は別の層です。

## 四つの問いを分ける

| 問い | 概念 | 物語での意味 |
|---|---|---|
| このデータはどの会社のものか | テナント | 顧客記録は A 社に属する |
| この人はどの部門で働くか | 組織 | 李さんは東部営業部 |
| どんな操作をしてよいか | ロールと機能権限 | 営業員は顧客を管理し、管理者は割当もできる場合がある |
| 操作が許可された後、どの記録を扱えるか | データ範囲 | 本人、部門、会社の記録 |

組織は会社の空間の中で人を配置する仕組みです。部門を増やすだけで別テナントにする必要はなく、二人とも管理者というだけで互いのデータが見えるわけでもありません。

機能権限とデータ範囲を合わせて確認します。「顧客の参照」が許可されても、どの顧客を参照できるかはまだ決まっていません。

## 表示だけでは保護が完了しない

メニューやボタンは権限に応じて表示され、操作を見つける助けになります。データ要求時にはサーバーも身元、テナント、操作、データ範囲、業務状態を検査します。

そうしなければ、URL や記録番号を知るだけで画面を迂回され得ます。番号やアドレスを秘密にするだけで認可を代替できません。

認証の章とのつながりは、ログインで本人を確認し、テナントとデータ権限で会社と業務範囲を確認する、というものです。

## 先に覚えておく関係

テナントが会社の境界を定め、組織とデータ範囲が内部の分担を定めます。ただし専用の管理 API にテナント横断能力がある場合もあり、全サービスを同じ自動規則として考えることはできません。

たとえばドメインのテナントプラグインは会社条件を維持しますが、オンライン利用者管理の ALL には明示的な横断処理があります。「スーパー管理者ならどこでも同じ」とせず、後で分けて説明します。
