# 6. 확장과 검증: 상태 처리를 복사하지 않고 연결하기

새 기능에서 메시지를 보내기 전에 어떤 업무 사실이 발생했고 수신자가 무엇을 해야 할지 정합니다. 그다음 본문, 테넌트, 멱등 키, 복구 방식을 정합니다. 메시지는 사실을 전달하지만 인가나 업무 상태 검증을 대신하지 않습니다.

## 연결 순서

1. 기존 common-mqlog와 ReliableMessageRelay를 쓰고 별도 조회·재시도 테이블을 복사하지 않습니다.
2. 같은 데이터 소스의 유효한 업무 트랜잭션 안에서 발송 의도를 기록하고 tenantId를 명시합니다. 롤백 시 대기 메시지가 남지 않는지 검증합니다.
3. 해당 서비스의 Spring Cloud Stream에 binding과 destination을 설정하고 전략이 실제 Broker와 일치하는지 확인합니다.
4. 소비자는 고유 제약이나 도메인 Inbox로 업무 멱등성을 보장하고 완료 후 프레임워크 규약에 따라 확인합니다. 실제 실패는 재시도 가능한 오류로 남깁니다.
5. 스케줄, 전송, 중복 소비, 테넌트 거부, 데드레터, 정식 복구를 따로 검증합니다.

## 생략하면 안 되는 경계

외부 관리 조회는 신뢰할 수 있는 테넌트와 기능 권한으로 제한합니다. 내부 조회도 명시적 tenantId와 내부 호출 인증이 필요합니다. 중계는 의도적으로 모든 테넌트를 검색하므로 사용자용 테넌트 가로채기를 그대로 적용하면 전송 누락이 생길 수 있습니다.

Outbox는 서비스 간 DB 원자 커밋을 보장하지 않습니다. 여러 서비스 협업에는 도메인 보상과 멱등성이 필요합니다. 소비자 중복 제거 키는 같은 업무 사실을 가리켜야 하며 재시도마다 새 키를 만들면 안 됩니다. msgKey, 추적 헤더, 전송 true는 이 보장을 대신하지 않습니다.

## 무엇을 관찰해야 하는가

| 상황 | 필요한 결과 |
|---|---|
| 로컬 업무 롤백 | 업무 변경과 Outbox 모두 미커밋 |
| Broker 연결 불가 | 실제 실패가 백오프 또는 데드레터로 이동, 거짓 SENT 금지 |
| 전송 후 프로세스 종료 | 재전달을 허용하되 업무 결과는 중복 반영하지 않음 |
| 두 실행이 같은 기록 선점 | 성공한 실행만 계속하고 이전 결과로 덮어쓰지 않음 |
| 다른 테넌트 조회·조작 | 내용 유출 없이 거부 |
| 정식 재전송·무시 | 권한, 상태, 전달 스위치, 동시성 조건 유효 |

장애 검증은 등록된 테스트 객체와 통제된 fixture만 대상으로 합니다. 전체 스택 중단, 볼륨 삭제, 업무 상태 변경으로 성공을 만들지 마세요. 테스트 데이터, 실제 업무, 프로토콜 fixture, 실제 전달을 구분합니다.

관리 집계나 Broker 전략을 넓히려면 구체적 요구, 계약, 보안 경계, 테스트가 필요합니다. 이 장은 현재 동작과 확장 방법을 설명하며 그러한 제품 기능을 새로 추가하지 않습니다.
