# 1. 멀티테넌트 입문: 하나의 시스템을 여러 회사가 쓰는 방법

A사와 B사가 Omni-Stack으로 각자의 업무를 관리하려고 합니다. 같은 앱을 열 수 있어도 A사 직원이 B사의 고객·공급업체·신청을 보게 되어서는 안 됩니다.

멀티테넌트는 **소프트웨어를 공유하면서도 각 데이터가 누구의 것인지 알고 그 경계를 지켜 사용하는 문제**를 다룹니다. 테넌트는 회사별 업무 공간이라고 이해하면 됩니다. 직원 계정은 해당 회사 공간에 속합니다.

개념부터 이해한 다음 프레임워크와 프로젝트 소스를 읽습니다. 앞의 두 글은 Java나 DB 쿼리 지식 없이 읽을 수 있습니다.

## 이름이 같은 두 직원으로 시작하기

A사에도 B사에도 리 씨가 있을 수 있습니다. 이름이 같다고 같은 계정은 아닙니다. 로그인에서 회사를 먼저 선택하면 올바른 공간에서 사용자를 찾습니다.

두 회사에 모두 “영업 관리자” 역할이 있어도 하나의 인가 기록을 공유하지 않습니다. 어느 회사의 역할인지, 누구에게 할당했는지, 어떤 기록을 처리하는지 각각 확인해야 합니다.

규칙을 이해하기 위한 이야기입니다. 제공된 테스트 계정이나 이 이름으로 실제 업무 데이터를 만들라는 지시가 아닙니다.

| 사람 | 회사 공간 | 부서 | 담당 |
|---|---|---|---|
| A사의 리 씨 | A사 | 동부 영업부 | 자신의 고객 관리 |
| A사의 왕 관리자 | A사 | 동부 영업부 | 부서 담당 고객 조회 |
| B사의 리 씨 | B사 | 고객 서비스부 | B사 기록 처리 |

왕 관리자의 권한이 더 넓어도 B사의 관리자가 되는 것은 아닙니다. 부서·역할·회사 공간은 서로 다른 단계입니다.

## 네 질문을 구분하기

| 질문 | 개념 | 이야기의 의미 |
|---|---|---|
| 어느 회사의 데이터인가 | 테넌트 | 고객 기록은 A사 소유 |
| 어느 부서에서 일하는가 | 조직 | 리 씨는 동부 영업부 |
| 어떤 작업을 해도 되는가 | 역할과 기능 권한 | 영업 담당은 고객 관리, 관리자는 배정도 가능할 수 있음 |
| 작업이 허용된 뒤 어떤 기록을 다루는가 | 데이터 범위 | 본인·부서·회사 기록 |

조직은 회사 공간 안에서 사람을 배치합니다. 부서를 늘린다고 별도 테넌트로 만들 필요는 없고, 둘 다 관리자라고 서로의 데이터를 볼 수 있는 것도 아닙니다.

기능 권한과 데이터 범위를 함께 봐야 합니다. “고객 조회” 권한은 작업 가능 여부만 답하며 어떤 고객을 볼지는 아직 정하지 않습니다.

## 화면 표시만으로 보호가 끝나지 않음

메뉴와 버튼은 권한에 따라 표시되어 할 일을 찾도록 돕습니다. 데이터를 요청할 때 서버도 신원·테넌트·작업·데이터 범위·업무 상태를 검사해야 합니다.

그렇지 않으면 주소나 기록 번호만 알아도 화면을 우회할 수 있습니다. 이 값을 비밀로 취급하는 방식이 인가를 대신하지는 못합니다.

앞 장의 인증과 연결됩니다. 로그인은 누구인지 확인하고, 테넌트와 데이터 권한은 어느 회사와 업무 범위에 해당하는지 판단합니다.

## 먼저 기억할 관계

테넌트가 회사 경계를, 조직과 데이터 범위가 내부 분담을 정합니다. 일부 API에는 테넌트를 넘나드는 전용 관리 기능이 있으므로 모든 서비스를 같은 자동 규칙으로 볼 수 없습니다.

예를 들어 도메인 테넌트 플러그인은 회사 조건을 유지하지만 온라인 사용자 관리의 ALL은 명시적 교차 테넌트 처리가 있습니다. “최고 관리자면 모든 곳이 같다”고 생각하지 않도록 뒤에서 구분합니다.
