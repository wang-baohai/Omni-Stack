# Harness による二次開発：小さなタスクを最後まで

本稿は一つのタスクで Harness の五要素をつなぎます。**supply-chain の学習プロジェクトで、CRUD 生成器を使って「素材ブランド」の実行可能な機能を作り、権限、メニュー、ビルドを検証する。** タスクは小さいですが、同じ進め方は他の業務対象にも使えます。

以下のコマンドは[スキャフォールド開発ガイド](../guides/scaffold-development.jp.md)に由来します。本稿は、あなたの環境で実行済みだと主張しません。各手順に期待結果と、失敗時に記録すべきことを示します。

## 手順 0：境界を決める

作業前に次を答えます。

- 対象プリセット：`supply-chain`（SRM、購買、資産）。
- 生成先：リポジトリ内の `generated/learning-supply-chain`。主プロジェクトを汚さない。
- 共有データベースを変更せず、生成物の migrator やシードを実行しない。
- 完了条件：バックエンドビルド、フロントエンド lint/build、生成物自身の検証が通過し、権限とメニューの入口に実際の証拠がある。

これが文脈と制約です。なければ生成器が誤った場所に書き、本機で二つ目の環境を起動するかもしれません。

## 手順 1：現在の事実を読む

モデルにコードを変えさせる前に三か所を読みます。

1. ルート [AGENTS.md](../../AGENTS.md) のハード制約と完了チェックリスト。
2. [アーキテクチャとエンジニアリング事実](../architecture.jp.md)の supply-chain モジュール境界。
3. [購買設計](../design/procurement-design.jp.md)の素材カタログのテーブル、権限、データ範囲規則。

読み終えたら、素材テーブルがどのサービスに属し、テナント遮断の範囲は何か、書き込みに必要な権限コードは何か、失敗時は何を返すかを言える必要があります。言えなければ読み続け、生成を始めません。

## 手順 2：学習プロジェクトを生成する

```bash
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm run dev -- preset create supply-chain --output generated/learning-supply-chain
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm run dev -- preset validate supply-chain --output generated/learning-supply-chain
```

期待：最初は `preset created: supply-chain@...`、次は `generated preset valid`。失敗時は完全な出力と終了コードを記録し、テンプレート、ネットワーク、ディスクのどれが原因か確認する前に、ディレクトリを削除して繰り返し再試行しないでください。

生成物には独自の `scaffold.lock`、Compose、AI 入口があります。以降のコマンドは生成物内で実行し、元リポジトリの絶対パスに依存しません。

## 手順 3：生成器の変更内容をプレビューする

```bash
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm ci
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm run dev -- generate crud --spec scaffold/specs/material-brand.yaml --check
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm run dev -- generate crud --spec scaffold/specs/material-brand.yaml --dry-run
```

`--check` は入力を検証し、`--dry-run` は計画変更を一覧します。次を確認します。

- 想定モジュールだけが変わり、他の業務に触れていない。
- 権限コード、メニュー、マイグレーション、フロントエンド入口が含まれる。
- 既存ファイル上書きの警告が出ていない。

プレビューは形式ではありません。共有ファイルの書き換えが計画に現れたら、`--apply` で押し切らず、テンプレートを確認して停止します。

## 手順 4：適用して検証する

```bash
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm cli npm run dev -- generate crud --spec scaffold/specs/material-brand.yaml --apply
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm backend ./mvnw clean install -pl omni-procurement -am
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm frontend npm ci
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm frontend npm run lint
docker compose -p omni-stack-tools -f compose.tools.yaml run --rm frontend npm run build
```

期待：生成器が完了して変更を一覧し、Maven reactor が成功し、フロントエンドの lint と build が通過します。失敗時は次を記録します。

- コマンド、作業ディレクトリ、終了コード。
- 最後の要約行ではなく、最初の実際のエラー。
- テンプレート、依存取得、ローカル環境のどれが原因か。
- どのファイルが生成済みで、戻す必要があるか。

「もう一度実行する」で根本原因の判断を代替しないでください。書き込み結果が不明なときは、ファイルが生成されたかを確認してから再試行を決めます。

## 手順 5：権限と入口を検証する

ビルド成功はコードがコンパイルできたことだけを証明します。次も検証します。

1. バックエンドの書き込みが `resource:action` 権限コードを宣言しているか。
2. 権限シードとフロントエンドの `v-permission` が一致するか。
3. メニュー／ルートが権限時だけ現れるか。
4. テナントとデータ範囲がモジュール規則どおりか。
5. 実ログイン後、対象テナントで正しい入口が見え、越権要求が拒否されるか。

実際の実行環境と身元が必要で、ソース読解だけでは足りません。条件がなければ「未検証」と記録し、ビルド成功を機能通過にしないでください。

## 手順 6：フィードバックと断点を残す

完了後に少なくとも次を記録します。

- 変更した対象と、それぞれの所有モジュール。
- 通過した検査と証拠の場所。
- 未検証の内容と理由。
- 次に誰が何をするか。

長いタスクでは、現在の手順、失敗ログの位置、復帰入口も残します。断点は「後で見る」ためのメモではなく、次のセッションがゼロから模索しないための最小情報です。

## AI に実変更を任せる：要件・事実・境界・フィードバック

上記の 6 手順は「生成器に従う」流れです。実際の二開はむしろ**既存プロジェクトの中で AI に統制された変更をさせる**ことが多いです。本節は同じ主例——ワークスペースにモジュール入口を追加する——を使い、要件・事実・境界・検証をどう渡すかを説明します。「作っておいて」だけでは足りません。

### 要件：誰がどの条件で何を見るかを先に書く

実行可能な要件には少なくとも 4 つがあります。

```text
役割：ログイン済みの管理者または従業員
入口：ワークスペースのアプリ一覧、全体アプリドロワー、ヘッダーのメニュー検索
動作：モジュールをクリックすると新規タブで開く。モジュール内の移動は現在のタブに留まる
境界：入口は現在の権限で入れるページのみ。リンクにトークンを含めない。四言語と狭い画面で動く
受入：カード/ドロワー/検索が同じ遷移先を指す。権限のない深いリンクは 403。ビルド・単体・構造ゲートが通る
```

「ワークスペースを良くして」のような検証できない文は避けます。**受入条件が実装より先**です。そうでなければ AI は推測するしかありません。

### 影響分析：権限・テナント・データに触れるかを先に判断する

コードを書く前に AI に 4 つ尋ねます。

| 質問 | 主例の答え | 「はい」の場合 |
| --- | --- | --- |
| 権限コードを追加するか | いいえ。既存メニュー権限を再利用 | `sys_permission` シードと `v-permission` を更新 |
| テナント表・列を追加するか | いいえ | 前向き Liquibase changeset とシード検証を追加 |
| バックエンド API を変えるか | いいえ。既存のメニュー/統計 API のみ | API 契約とテストを更新 |
| 生成器の閉包を変えるか | いいえ。ページ帰属の登録のみ | catalog とトリミングを更新 |

主例には権限・テナント・移行の変更は**ありません**。テンプレートを流用して必要になる場合は、UI 変更に混ぜず独立したタスクとして先に行います。

### 事実の選択：印象ではなく検証できるファイルを渡す

変更点に近い順に渡します。

1. 対象ページとコンポーネント（`ConsoleHeader.vue`、`ApplicationDrawer.vue`、`WorkspaceEntryList.vue`、`layout/index.vue`）；
2. 派生ロジック（`useApplicationNavigation`、ルート meta）；
3. 制約文書（`docs/frontend-patterns.md` と `docs/architecture.md` の権限章）；
4. 既存テストと検査コマンド（`tests/navigation/*`、`package.json` scripts）。

回答では `file:line` を引用し、「確認済みの事実」と「推測」を分けるよう求めます。推測は明示し、実装に入れてはいけません。

### ファイル境界：変えてはいけないものを先に言う

主例の境界：

- **許可**：ワークスペース、ヘッダー、ドロワー、入口一覧、モジュールレイアウト、対応する詞条とテスト、`scaffold/catalog/modules.yaml` の帰属；
- **禁止**：バックエンド業務コード、DB 移行、正式シード、権限モデル、生成器閉包；
- **要承認**：品質スクリプト、スキャナ、README など横断 WP のファイル。

AI が範囲外の変更を提案したら、「ついでに直す」のではなく確認して止めます。

### 実装フィードバック：各段階で再確認できる結果を出す

実際の流れは閉ループでした。

1. まずビルドして撮影し、CRM の主領域が x=1038 に押されていることを発見；
2. DOM 寸法で `ConsoleHeader` と `el-main` が同一行にあると特定し、`direction="vertical"` を追加；
3. 1280〜1920 の 5 幅で再測定し、主領域がすべて x=220 から始まることを確認；
4. 四言語の撮影で英語ラベルと文字単位の折返しが見つかり、2 つの最小修正を実施；
5. 最後に G1/G2/G6 を実行し、G3 の既存失敗は別途登録。

各段階で「入力 → コマンド → 出力 → 判断」を残します。**出力のない段階は完了ではありません。**

### 検証の約束：ゲートをタスクに書く

| 種類 | 主例での使用 | 説明 |
| --- | --- | --- |
| ビルド/静的 | `npm run build`、`npm run lint` | 失敗したら止める。飛ばさない |
| 単体/型 | `npm run test:unit`、`npm run typecheck:e2e` | ナビ派生とページ挙動を覆う |
| 構造 | 五プリセット structure | トリミング後の死リンクがないことを示す |
| 実行時 | 実ログイン + コンテナ撮影 | 利用者に見える結果を示す |
| 既存欠陥 | G3 README 負例 | 本歩の PASS に混ぜず別途登録 |

失敗後の次の一手も書きます。ビルド失敗は最初のエラーと直近 diff、実行失敗はイメージ/ポート/ログイン、構造失敗は未登録ページ。**再実行で当たるのを待つのは禁止**です。

### 権限や移行が必要になる時

- 新しいページやボタン：権限コードとシードを先に追加し、`v-permission` を付ける；
- テナント表・列の追加：前向き changeset → エンティティとクエリ → シードマニフェスト更新；
- 表示とナビだけ：権限・移行の変更は**発生しない**。主例はこちら。

「今回は発生していない」と書くことも、「実施した」と同じくらい重要です。

## よくある失敗

| 現象 | 最初に確認 | してはいけないこと |
|---|---|---|
| 生成器がパス不存在を報告 | 現在のディレクトリ、プリセット出力、テンプレート完全性 | リポジトリ外の一時ディレクトリで再生成して回避 |
| Maven がモジュールを見つけない | 生成物に含まれるか、親 POM が更新されたか | 親 POM を手で直してテンプレート問題を隠す |
| フロントエンドの型エラー | テンプレートと現在のコンポーネント API の一致 | 型検査を無効化 |
| 権限入口が出ない | 権限コード、ロール、メニューシード、テナント | DB を直接編集してメニューを追加 |
| 実ログインが失敗 | CAPTCHA、テナント、アカウント、ゲートウェイ、サービス健全性 | テスト用裏口でログインを回避 |

## 終えた後

三つの問いに答えられるはずです。タスクに必要な事実、ツール、検査は何か。失敗時の証拠はどこか。次回はどう続けるか。三つに答えられて初めて、生成器を動かしただけでなく Harness を使ったことになります。

[Harness とは何か](harness-what-and-why.jp.md)または[事実の維持](harness-fact-maintenance.jp.md)に戻って概念を補ってください。
