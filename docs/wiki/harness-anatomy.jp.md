# Harness の五つの構成要素

Harness は単一の部品ではありません。購買依頼に「予算科目」を追加し権限を検証するという同じタスクを分解すると、少なくとも五つの部分が協調する必要があります。どれか欠けると、どこかで検証可能性が失われます。

## 1. 文脈：いま何が事実かをモデルに伝える

文脈はリポジトリ全体ではなく、タスクに関係する現在の事実です。

- スキーマ：購買依頼は `proc_*` テーブルにあり、テナント項目はインターセプタが処理する。
- モジュール境界：承認は `omni-workflow` で動作し、購買サービスは Flowable を追加しない。
- 既存 API：要求と応答は `R<T>`、ページングは `R<PageResult<T>>` に従う。
- エラー意味論：権限不足、入力不正、データ範囲拒否がそれぞれどの状態に対応するか。

Omni-Stack では、これらの事実は `AGENTS.md`、`docs/architecture.md`、`docs/api-contract.md`、各モジュール文書にあります。文脈の質は量ではなく「現在であること」で決まります。古い事実は、事実がないより危険です。

## 2. ツール：行為を実際に起こす

モデルにはテキスト出力だけでなく、エンジニアリング行為の実行が必要です。

- ビルドとテスト：Maven Wrapper、フロントエンドの `npm run build` / `npm run lint`。
- 生成器：`tools/omni-cli` がサービス、CRUD、絞り込んだプリセットプロジェクトを生成。
- データベース：Liquibase マイグレーションと統制されたシード。
- 実行環境：ローカル Docker のサービス、ブラウザ、ログ。

ツールは「動くと思う」を「実際に動いた」に変えます。なければ検証は読解になり、ポート競合、マイグレーション順序、実際のログイン失敗を見つけられません。

## 3. 制約：コミット前に誤りを露出させる

制約はリポジトリに書かれ、人とモデルの両方が読める規則です。

- 書き込み操作は `resource:action` 権限コードを宣言し、シードとフロントエンドの `v-permission` を同期する。
- テナント遮断はモジュールのテーブルだけに適用し、`sys_mq_message` は全体走査のままにする。
- 金額項目は十進文字列を使い、JSON 数値で送らない。
- データ権限インターセプタはページングより先に登録する。

制約の価値は自由の制限ではなく、暗黙の経験を検査可能な条件に変えることです。口頭レビューだけの規則は、モデルにも自動化にも効きません。

## 4. 検証：完了には証拠が必要

検証は複数の層を覆います。

| 層 | 例 | 見つけるもの |
|---|---|---|
| 単体・構造 | サービステスト、プリセット構造アサーション | ロジック誤りとモジュール残留 |
| ビルド | Maven reactor、フロントエンド build/lint | コンパイル、型、スタイル規約 |
| 文書 | リンク、四言語の一貫性、ソース抜粋 | リンク切れ、翻訳のずれ、古い例 |
| 実行 | コンテナ健全性、実ログイン、画面操作 | 設定、権限、データ範囲 |
| 納品 | 生成物のビルドと絞り込み | 本リポジトリへの暗黙依存 |

検証は「一番楽なコマンドを一つ実行する」ことではありません。変更は影響する最も高い層で確認する必要があり、低い層の通過だけでは高い層の正しさを証明できません。

## 5. フィードバックと断点：次回を可能にする

長いタスクは必ず中断します。人が離れる、モデルのターンが変わる、環境が遮断する。Harness は四種類の痕跡を残します。

- 現在の状態：どの手順、どの対象が完了したか。
- 失敗の証拠：コマンド、終了コード、ログ位置、実際の現象。
- 未完了リスト：未試行、遮断、審査待ち。
- 次の入口：復帰時に最初に確認することと再開する行為。

痕跡は「変更した覚えがある」ではなく、検証可能でなければなりません。Omni-Stack では、マニフェストの審査状態、ソース摘要の失効、証拠ファイル、未完了リストがこの役割を担います。

## 五つの関係

五つは一直線の工程ではなく循環です。

1. 文脈が、モデルが提案できる選択肢を決める。
2. ツールが選択肢を実装させる。
3. 制約が境界を越えるのを止める。
4. 検証が結果を証明するか、失敗を露出させる。
5. フィードバックが失敗を次の文脈へ書き戻す。

どれか欠けると循環が切れます。文脈がなければ車輪の再発明、検証がなければ誤りを完了とみなし、フィードバックがなければ次回がゼロから始まります。

## 境界

部品が多ければ良い Harness ではありません。ツールや検査を増やすたびに、維持、実行時間、誤検知対応のコストが増えます。判断基準は、ある種の実際の失敗をより早く安定して露出させるかどうかだけです。答えられない部品は積み増すのではなく削るべきです。
