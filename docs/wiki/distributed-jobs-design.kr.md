# 2. XXL-JOB를 선택한 이유: 무엇을 관리해야 할까요?

주기적으로 일을 실행하는 방법은 여러 가지입니다. 여러 머신에 배정해야 하는지, 한곳에서 확인하고 수동 실행하며 기록과 복구를 관리해야 하는지 먼저 생각합니다. 도구가 늘면 배포, 인증, 일관성 유지도 복잡해집니다.

## 흔히 쓰는 세 가지 방법

| 방법 | 적합한 용도 | 직접 책임질 부분 |
|---|---|---|
| 운영체제 스케줄러 | 단일 머신 스크립트와 고정 유지보수 | 머신 관리, 앱 권한, 로그, 중복 실행 |
| 앱 내부 타이머 | 서비스와 함께 시작하는 소수의 주기 작업 | 다중 인스턴스 조정, 중앙 관리, 복구 |
| 센터와 실행기 | 여러 서비스, 원격 배정, 공통 기록 | 센터 가용성, 등록, 네트워크, 업무 멱등성 |

XXL-JOB는 세 번째 방식입니다. 이 프로젝트에는 여러 서비스의 유지보수와 사용자가 만드는 작업이 필요하므로 기존 센터와 실행기를 사용합니다. 현재 선택의 이유를 설명하는 것이며 다른 방식을 부정하거나 두 번째 스케줄링 플랫폼을 도입하는 것은 아닙니다.

## 현재 버전과 배포 역할

core와 Admin은 3.3.1로 고정합니다. Admin은 스케줄링 데이터를, 업무 서비스는 업무 데이터와 개인 작업의 소유권을 보관합니다. 실행기는 각 서비스 안에서 동작하고 서로 다른 AppName으로 대상을 구분합니다.

서로 다른 실행기 그룹에는 같은 handler 이름이 있을 수 있습니다. 여러 서비스의 MQ 중계도 각각 자기 데이터를 처리합니다. 이름만 보지 말고 그룹까지 확인해야 잘못된 대상을 조사하지 않습니다.

## 두 기록이 하나의 트랜잭션은 아닙니다

개인 작업을 만들 때 Base는 소유자를 저장하고 센터에는 실행 시간을 등록합니다. 로컬 DB 트랜잭션이 다른 서비스에 대한 HTTP 쓰기까지 자동으로 포함하지는 않습니다.

그래서 원격 ID를 저장하고 등록 실패, 응답 유실, 로컬 ID 기록 실패를 처리합니다. 원격에 남은 작업이 없음을 확인한 뒤에만 로컬 행을 삭제합니다. 결과가 불명확하면 연결 정보를 보존해 대조합니다. 오류 응답만으로 아무것도 생성되지 않았다고 판단하면 안 됩니다.

단일 타이머 메서드보다 복잡하지만 실패 후 무엇을 복구할지 분명해집니다. 뒤에서는 저장소로 이동할 필요 없이 실제 복구 코드를 본문에서 설명합니다.

## 센터에 넘기지 않는 책임

개인 작업 소유권은 테넌트와 작성자를 함께 확인합니다. 업무 권한, 상태 전이, 트랜잭션, 멱등성도 서비스의 책임입니다. 기본 Admin의 사용자 관리와 Omni-Stack 역할 기반 인가는 같은 시스템이 아닙니다.

워크플로는 누가 승인하고 다음에 무엇을 할지를, 예약 작업은 언제 한 번 실행할지를, MQ는 비동기 메시지를 어떻게 전달할지를 다룹니다. 스케줄러가 중계기를 깨워도 전달 결과는 Outbox, Broker, 소비자까지 확인해야 합니다.

## 운영 비용

센터가 불가용하면 등록, 수정, 실행 요청에 영향을 줍니다. 실행기에 도달할 수 없으면 배정이 실패하고, 처리 시간이 길면 후속 작업이 막힙니다. 잘못된 재시도는 업무 결과를 반복시킬 수 있습니다. 로그, 적절한 주기, 제한된 관리 권한, 복구 경로가 필요합니다.

다음은 [프레임워크 내부](distributed-jobs-framework.kr.md)입니다. 정확한 현재 버전의 원문을 사용하며 클래스 이름 암기보다 흐름 이해를 먼저 합니다.
