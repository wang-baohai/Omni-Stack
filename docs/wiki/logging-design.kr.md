# 2. 설계 선택: 앱은 기록하고 도구는 수집한다

앱이 원격 수집 서버로 직접 보내는 방식과 표준 출력에 기록하고 수집기가 읽는 방식이 있습니다. 이 프로젝트는 후자를 사용합니다. 업무 메서드마다 Loki 클라이언트를 넣지 않아도 되며, 컨테이너 교체 후에도 Docker 메타데이터로 대상을 다시 발견합니다.

## 네 가지 역할

| 역할 | 이 프로젝트의 도구 | 담당하지 않는 일 |
|---|---|---|
| 사건 생성 | Spring Boot 로깅 프레임워크 | 중앙 저장 |
| 발견과 수집 | Alloy | 업무 감사와 권한 판단 |
| 저장과 검색 | Loki | 업무 데이터베이스 대체 |
| 조회와 연결 | Grafana | 수집되지 않은 데이터 생성 |

Loki는 레이블로 로그 스트림을 좁힌 뒤 내용을 검색합니다. 사용자 이름, 주문 번호, 요청마다 달라지는 ID를 레이블로 사용하면 값 종류가 늘어 관리 비용이 커집니다. 필요한 상관관계 ID는 로그 필드에 남겨 내용 검색으로 찾을 수 있습니다.

## 구조화 출력 설정

정식 앱 Compose 환경에 있는 설정입니다.

<!-- omni:source path="compose.apps.yaml" -->
```yaml
      LOGGING_STRUCTURED_FORMAT_CONSOLE: ${STRUCTURED_LOGGING_FORMAT:-ecs}
```

Spring Boot는 대응하는 로깅 속성을 읽고 기본적으로 ECS(Elastic Common Schema) JSON을 사용합니다. ECS는 필드 규약이며 다른 메시지 큐나 자동 마스킹 스위치가 아닙니다. 다른 기동 방식에서는 해당 실행 설정을 따로 확인해야 합니다.

## 모두 한 데이터베이스에 넣지 않는 이유

실행 로그는 업무 테이블과 쓰기 빈도, 보관 기간, 조회 패턴이 다릅니다. 작업 감사에는 명확한 테넌트와 접근 권한도 필요합니다. 한 테이블에 섞으면 성능과 책임 경계가 흐려지므로 실행 로그와 DB의 작업 기록·보안 사건을 분리합니다.

이 방식도 수집, 저장, 보관 정책, 조회 권한을 유지해야 합니다. 수집기 장애 중에는 지연이나 누락이 생길 수 있습니다. 운영 배포에서는 접근 제어, 용량, 백업을 평가해야 하며 로컬 템플릿만으로 충족됐다고 볼 수 없습니다.
