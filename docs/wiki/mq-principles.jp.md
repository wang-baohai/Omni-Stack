# 1. 統合MQ管理：「あとで処理する」を理解する

操作記録を共通の検索先へ届けるなど、利用者を待たせず後で処理したい仕事があります。メッセージキュー（MQ）は、送り手が仕事を残し、別の側が後から受け取る仕組みです。双方が同時に稼働する必要を減らしますが、待機、失敗、重複、調査への対策が必要です。

## 荷物の発送に例える

| 用語 | 例え | 本工程の例 |
|---|---|---|
| 生成側 | 仕事を作る送り主 | 業務サービスや操作ログ生成側 |
| Broker | 荷物を受け取り転送する中継所 | RocketMQ |
| 消費側 | 荷物を受け取り仕事をする側 | Baseの操作ログ消費側 |
| Outbox | 送り主自身の発送待ち一覧 | 各サービスのローカルsys_mq_message |
| 中継処理 | 一覧から受け取り発送する係 | XXL-JOBが起動するメッセージ中継 |

OutboxはBroker内のキューではなく、管理画面も配送経路そのものではありません。送信記録、再試行、デッドレターを確認できますが、業務完了は消費側の結果を調べる必要があります。

## 最初に意図を保存する理由

業務保存後に直接MQへ送ると、業務はコミットしたのに送信だけ失敗する場合があります。先に送れば、送信済みでも業務がロールバックする場合があります。Outboxでは、同じ有効なローカルトランザクションで業務と送信予定を一緒に保存し、後で発送します。

同じデータソース、有効な一つのトランザクション、適切なプロキシ呼び出しが前提です。sendという名前のメソッドだけでは原子性を証明できません。操作ログ生成側は送信例外を捕捉するため、全業務経路への保証にも使えません。
