# 7. 失败恢复与扩展：先确认发生在哪一层

看到“任务没执行”，先分清是时间未到、没有派发、业务失败，还是结果没有回报。每种情况恢复入口不同，重复点击并不能代替诊断。

## 按线索逐层确认

| 看到什么 | 先查什么 | 不要立即做什么 |
|---|---|---|
| 系统目录没有任务 | 双注解、实际部署、执行器开关 | 给所有个人处理器补系统注解 |
| 项目显示未注册 | 远端查询是否成功、执行器组与 handler | 仅凭标签断定不存在并再次注册 |
| 调度失败 | 在线地址、网络、认证、handler 名 | 先改业务状态或无依据重试 |
| 调度成功、执行失败 | 对应执行日志、输入与业务状态 | 把派发成功当成业务成功 |
| 执行进行中很久 | 耗时、阻塞策略、超时与回调 | 认定中断已撤销所有副作用 |
| 工作台没有个人日志 | 是否派发、解析失败、数据库写入 | 填一个虚假的成功时间 |
| 创建或删除结果未知 | 本地 ID、远端 ID、可信关联和完整查询 | 按任务名称猜测并批量清理 |

排查时记录准确时间与时区、租户、本地任务编号、执行器组、远端任务编号和日志编号。密码、Cookie 和完整敏感参数不进入公共报告。

## 注册报错，为什么保留本地记录

下面是工程在查询或清理也失败时的真实分支。此时无法确认远端有没有任务，删除本地行会丢掉恢复线索。

<!-- omni:source path="omni-backend/omni-base/src/main/java/com/omni/base/service/impl/UserJobServiceImpl.java" -->
```java
        } catch (Exception cleanupFailed) {
            // 查询/清理失败：无法确认远端，保留本地可恢复关联与停止责任，绝不删本地
            log.error("{}：调度中心反查/清理失败，保留本地待恢复记录 localId={}, executorParam={}, 需对账",
                    action, localId, executorParam, cleanupFailed);
            throw new BusinessException(500, "调度中心注册结果未知且清理失败，已保留本地待恢复记录(id="
                    + localId + ")，请联系运维对账: " + cleanupFailed.getMessage());
        }
```

恢复时按已有精确远端 ID，或执行器组、共享 handler、含租户与本地 ID 的参数核对。名称可能重复或已修改，不能作为删除依据。重启种子同步也不能替代未知结果的核对。

## 新增一个个人任务类型

先定义用户到底要做什么、输入是什么和怎样防止重复。然后实现既有 UserJobHandler 接口，Bean 名与类型目录编码完全一致，并维护参数定义。喝水处理器的真实声明是：

<!-- omni:source path="omni-backend/omni-base/src/main/java/com/omni/base/job/handler/DrinkWaterRemindHandler.java" -->
```java
@Slf4j
@Component("Task-00001")
@RequiredArgsConstructor
public class DrinkWaterRemindHandler implements UserJobHandler {
```

任务消息明确携带 tenantId，处理器不能依赖 HTTP 线程的租户上下文。涉及业务写入时，按业务权限和状态机设计事务及幂等，不把用户提交的编号直接当成可信授权。

类型种子、参数模板和断言要同步维护，结构变化使用前向迁移；只改页面选项不够。本章只是说明扩展步骤，没有新增任务种类或实现新的调度能力。

## 新增一个系统维护任务

保留两类注解，给出可理解的名称、默认周期、参数及路由策略。先评估数据量、批次、并发、幂等和失败后的状态，再让调度中心定期唤醒。不同服务的执行器组仍保持各自 AppName。

## 怎样验证扩展真的有效

在同一套本地 Docker 环境，用专用测试身份检查创建、编辑、暂停、手动执行、恢复、真实周期执行、成功与失败日志、他人和跨租户拒绝，以及删除后的远端无残留。对账异常要保留真实失败与恢复记录。

源码匹配、单元测试、真实周期执行和图片审读是不同证据，分别记录。涉及跨服务的注册和清理，要覆盖响应丢失与未知结果，不能只验证顺利路径。工程硬约束见[调度事实](../scheduling.md)，回到[本章开头](distributed-jobs-principles.md)可以重新按顺序阅读。
