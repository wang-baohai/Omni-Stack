# 独立文書サイトと四言語の保守

対象はリポジトリ Markdown と文書サイトです。業務サービスの起動は不要です。本文は `docs/docs-manifest.yaml` に登録し、`docs/.vitepress/source` は生成物のため編集・コミットしません。

## 1. ビルド、起動、停止

ローカル Docker が使用でき、4173 ポートが空いている状態でリポジトリ直下から実行します。

```bash
docker compose -p omni-stack-docs -f compose.docs.yaml up -d --build
docker compose -p omni-stack-docs -f compose.docs.yaml ps
docker compose -p omni-stack-docs -f compose.docs.yaml logs wiki
```

`http://localhost:4173` を開き、言語を選択してプロジェクト用語を検索します。四言語とも本文とナビゲーションがあります。言語ファイルが不足した場合はビルドが失敗し、中国語へ代替表示しません。停止：

```bash
docker compose -p omni-stack-docs -f compose.docs.yaml down
```

`omni-stack-docs` は一つの Nginx コンテナを `127.0.0.1:4173` で動かし、業務データボリュームを使いません。ポート競合は明示的に解消します。Node で構築し、実行時は静的ファイルだけを配信します。

## 2. 本文は一つ、入口は二つ

GitHub/Gitee では `docs/wiki/index.jp.md` と相対リンクを直接読みます。同じ Markdown から `/zh-CN/`、`/en-US/`、`/ja-JP/`、`/ko-KR/` を生成し、生成ディレクトリとキャッシュは無視します。

ソースと規則の相対リンクは、サイトではホスト先のソースリンクになります。既定は GitHub です。Gitee 用にはビルド時に `DOCS_REPOSITORY_URL=https://gitee.com/wang-baohai/Omni-Stack` を設定します。生成プロジェクトは自分のリポジトリ URL を設定します。過去の検収記録は対象コミットを保ち、現在の動作を自動的に証明しません。

`docs/images` の画像をサイトへコピーします。説明とコードはリポジトリでも読めます。ビルド時に同梱した Mermaid がブラウザーで図のソースを SVG に描画し、ページやライト・ダークテーマの切り替え後に更新します。描画に失敗した場合はソースを残します。大きな図は図の領域内でスクロールでき、外部描画サービスに依存しません。

## 3. 変更と品質ゲート

1. 中国語原文と全言語の本文、ナビゲーション、図注を同期します。画面文字のある画像は実際に各言語へ切り替えて撮影します。
2. 新規ページを登録し、更新後にハッシュを計算します。中国語原文または訳文の変更により、以前のレビュー記録は無効になります。
3. 内容の完全性、リンク、画像、秘密情報、派生プリセット文書、サイト構築を確認します。内容チェックとレビュー承認は別です。
4. manifest の方針に従って実際にレビューし、`reviewer`、`reviewed_at`、`review_type`、`reviewed_source_sha256`、`translation_sha256` を記録します。人によるレビューは `HUMAN_REVIEW` を使います。[ADR-0003](../adr/0003-authorized-ai-translation-review.md) に基づき、所有者は Codex の `AI_REVIEW` を承認しています。この方式では文書ごとのレビュー証拠のパスとハッシュも記録してから `synchronized` にします。
5. レビュー待ち一覧を再生成します。厳格な `docs:i18n:check` が公開ゲートであり、草稿オプションはその代わりになりません。

AI レビューでは各文書の意味と手順の完全性、技術的なリテラル、安全境界と失敗条件、対象言語、画像、リンクを確認します。人によるレビューと偽って記録しません。自動翻訳、プラットフォームの操作承認、内容チェックだけでは署名を作成しません。未レビューのページには案内を表示します。版、日付、証拠は実際の実行を反映します。

業務画面の証拠はローカル Docker 内の Playwright で取得します。`E2E_RUNTIME_MODE=external` を選び、確認済みの Docker フロントエンドへ接続します。`E2E_BASE_URL`、`E2E_TENANT_ID`、一意の `E2E_EXECUTION`、`E2E_REGISTRY_PATH`、リポジトリ外の `E2E_ARTIFACT_DIR` を明示します。未確認画像の保存先は `E2E_DOCS_IMAGE_DIR` でリポジトリ外に指定します。目視確認、マスキング、出所の登録後、必要な画像だけを正式資料へ追加します。実際のログイン CAPTCHA は人が入力し、テスト用の短期トークンはテスト classpath の管理された fixture で発行します。

`E2E_RUNTIME_MODE=display-fixtures` は画面表示のデモ専用です。CAPTCHA、テナント、デバイスコードの応答を置換し、時刻を固定します。この結果には模擬表示と明記し、実際の認証や業務処理の成功を証明する資料にしません。正式な `external` モードでは実際の API と時刻を使用し、残り時間もそのまま表示します。意図的な障害注入は試験範囲を別途明記します。`npm run docs:screenshots:test` でモードの境界を検証し、このコマンドも Docker のフロントエンド用ツールコンテナで実行します。

## 4. 静的成果物

`docker/docs/Dockerfile` の build 段階は `/workspace/docs/.vitepress/dist` を生成します。実行イメージには静的成果物だけがあります。構築したコンテナから書き出し、別の Web サーバーで配信できます。サブパス公開は `DOCS_BASE` をビルド時に設定し、ナビゲーション、検索、画像を検証します。

業務イメージはルート `.dockerignore` に従い docs と ai を含みません。文書イメージは専用の除外規則を使います。公開前に厳格な言語・画像ゲートを完了します。ローカルプレビューは GitHub Pages、Gitee、本番へ自動公開しません。

## 5. 問題解決

| 現象 | 確認 |
|---|---|
| ページ・言語不足 | マニフェストの原文・翻訳パスと新規登録 |
| サイトリンク切れ | 元の相対パスと投影の再構築 |
| 検索結果なし | 現在の言語、マニフェストと索引への登録 |
| 画像不足 | 元のパス、構築コンテキスト、画像一覧、言語 |
| レビュー失敗 | レビュー担当者、日付、原文と訳文のハッシュ。AI レビューでは承認と証拠のハッシュも必要で、変更後は実際に再レビューする |
| 古い内容 | 再構築して原文のハッシュとイメージ ID を比較 |
