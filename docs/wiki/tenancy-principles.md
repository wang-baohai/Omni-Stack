# 1. 多租户入门：一套系统怎样服务多家公司

甲公司和乙公司都想用 Omni-Stack 管理自己的业务。它们可以打开同一个应用，但甲公司的员工不应该因此看见乙公司的客户、供应商或申请。

多租户要解决的就是这件事：**共享一套软件时，仍然知道每份数据属于谁，并按边界使用它。** 这里的“租户”可以先理解为一家公司在系统中的业务空间，员工账号则属于相应的企业空间。

本章先把概念讲清楚，再打开框架和工程源码。前两篇不要求你认识 Java 或数据库语句。

## 从两位同名员工开始

甲公司和乙公司都可能有一位叫小李的员工。名字相同，不代表同一个账号。登录时先选企业，再填写账号，系统才能在正确的企业空间里找人。

即使两家公司各有一个“销售经理”角色，也不表示它们共享同一份授权。角色属于谁、分配给谁、能处理哪一部分数据，仍需分别确认。

下面只是帮助理解的故事，不是现成测试账号，也不是让你照着这些名字创建真实业务数据。

| 人物 | 所属企业空间 | 所属部门 | 工作安排 |
|---|---|---|---|
| 甲公司的小李 | 甲公司 | 华东销售部 | 维护自己的客户 |
| 甲公司的王经理 | 甲公司 | 华东销售部 | 查看本部门负责的客户 |
| 乙公司的小李 | 乙公司 | 客户服务部 | 处理乙公司的记录 |

王经理比小李权限多，不等于王经理自动成为乙公司的管理者。部门、岗位和企业空间是三个不同层次。

## 把四个问题分开问

| 问题 | 对应概念 | 用故事解释 |
|---|---|---|
| 这份数据属于哪家公司 | 租户 | 客户记录属于甲公司 |
| 这个人在哪个部门工作 | 组织 | 小李在华东销售部 |
| 这个人可以执行什么操作 | 角色和功能权限 | 销售员可以维护客户，经理可能可以分配客户 |
| 操作允许后，可以处理哪些记录 | 数据范围 | 自己的、本部门的，或本企业的记录 |

组织是在企业空间里面安排人员的方式。不能为了增加一个部门，就把它当成另一家租户；也不能因为两个人都叫经理，就默认可以互看数据。

功能权限与数据范围也需要一起考虑。例如，有“查看客户”的资格，只回答能否进行这项操作，还没有回答可以查看哪一条客户。

## 页面看不到，不是唯一的保护

菜单和按钮会根据权限显示，帮助用户找到自己能做的事。但真正请求数据时，服务器还要检查身份、租户、操作权限、数据范围和业务状态。

否则，只要知道一个网址或记录编号，就可能绕过界面。系统不能把这些信息当成秘密来代替授权检查。

这一点与上一章的认证衔接：登录确认你是谁，多租户和数据权限继续确认这次访问属于哪家企业、哪一部分业务。

## 可以先记住的关系

租户先确定企业边界，组织和数据范围再决定企业内部怎样分工。不过，具体接口可能有专门的跨租户管理能力，不能把所有服务都想成同一种自动规则。

例如，当前领域服务的租户插件会保留企业条件；在线用户管理中，ALL 范围则有明确的跨租户处理。后面会解释它们为什么要分别读，避免把“超级管理员”理解成所有地方都一样。
