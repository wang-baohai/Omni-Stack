# 6. 扩展验证：让新业务接入，而不是复制状态机

给新功能发消息前，先定义“哪个业务事实已经发生，接收方要完成什么”，再确定消息内容、租户、幂等键与失败恢复。消息只是传递事实，不能代替授权或业务状态校验。

## 接入顺序

1. 引入现有common-mqlog，使用ReliableMessageRelay，不复制一套定时扫描与重试表。
2. 在同数据源、有效的业务事务内写入待发意图，显式传入tenantId；验证回滚不会留下待发消息。
3. 在对应服务的Spring Cloud Stream配置登记binding与destination，确认发送策略和实际Broker匹配。
4. 消费侧用唯一约束或领域Inbox保证业务幂等，完成后再按框架语义确认；真正失败时保留可重试错误。
5. 验证调度、发送、重复消费、租户拒绝、死信与正式恢复，分别记录结果。

## 哪些边界不能省略

外部管理查询按受信任租户与功能权限过滤；内部查询也要显式tenantId和内部调用认证。后台中继故意扫描全部租户，不能把面向用户的租户拦截直接套上去导致漏投。

Outbox不保证跨服务数据库原子提交；需要跨服务协作时按领域补偿与幂等设计。消费者去重键要对应同一件业务事实，不能简单每次重试生成新键。不要把msgKey、Trace头或“发送返回true”当成这些保证。

## 怎样证明实现有效

| 场景 | 必须观察的结果 |
|---|---|
| 本地业务回滚 | 业务和Outbox均未提交 |
| Broker不可达 | 真实失败进入退避或死信，不假SENT |
| 发送后进程中断 | 允许重投，但消费业务不重复生效 |
| 两个执行流领取同一记录 | 只有领取成功者继续，旧结果不覆盖新状态 |
| 其他租户读取或操作 | 拒绝，不能泄漏消息内容 |
| 正式重发/忽略 | 权限、状态、投递开关和并发条件均有效 |

故障验证应只操作登记测试对象和受控夹具；不能停掉整套应用、清卷或改业务状态制造成功。测试数据、真实业务、受控协议与实际投递分别说明。

后续可以扩大管理聚合范围或增加Broker策略，但要有具体需求、接口契约、安全边界和对应测试。本章只解释当前能力与扩展方法，没有为教程新增这些功能。
