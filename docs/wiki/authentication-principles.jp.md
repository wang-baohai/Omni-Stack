# 1. 認証と認可：一度のログインから考える

李さんが Omni-Stack のホームを開くと、プロジェクトの Wiki が表示されます。読むだけならログインは不要です。購買申請を処理するときに初めて本人であることを示し、利用権限のあるワークスペースへ進みます。

この章では、その流れに沿って「誰かを識別する」「ログインを覚える」「ログイン後も使えないボタンがある理由」を説明します。前半は Java の知識を前提にしません。まず概念を理解してから、フレームワークとプロジェクトのソースを読みます。

## 一度の利用を最後まで追う

李さんはアカウント、パスワード、画像認証を送信します。認証サービスが確認すると、以降のアクセスに使う資格情報を発行します。後続のリクエストは資格情報を添えてゲートウェイを通り、業務サービスが操作権限と参照できるデータを確認します。

たとえば購買システムへログインできても、自分の申請を承認できるとは限りません。部門の管理者が承認できても、別の企業のデータを見られるわけではありません。ログイン、機能権限、データ範囲は別の問いに答えます。

ログインしても公開 Wiki の本文が別のものには変わりません。変わるのはアカウント領域です。条件を満たす利用者は、そこからワークスペースや管理コンソールへ進めます。

## まず三つを分ける

| 知りたいこと | システムの処理 | 身近な例 |
|---|---|---|
| この人は誰か | 認証 | 受付が来訪者の身元を確認する |
| 何をしてよいか | 認可 | 入館証で決められた階に入れる |
| どの記録を見てよいか | データ範囲の制御 | 部門管理者が担当範囲の申請を扱う |

権限エラーに対してパスワードを何度入れ直しても、通常は解決しません。パスワードは本人確認を担当します。役割、組織、業務データの帰属には、それぞれ別の条件があります。

メニューやボタンは操作を助ける表示です。実際のリクエストではサーバーも権限を確認する必要があります。ボタンを隠すだけでは API を保護できません。

## ログインをどう覚えるのか

よく出てくるのが、セッションとトークンです。

セッションは、サーバーが保存するログイン記録です。ブラウザーは通常 Cookie に入った参照情報を送り、サーバーが対応する記録を探します。Cookie 自体が身元情報のすべてではなく、ブラウザーがサーバーの信頼する人物を自由に決められるわけでもありません。

トークンは後続リクエストに添えるアクセス用の資格情報です。Omni-Stack の通常のパスワードログインでは JWT が返ります。JWT は身元に関する情報を含む署名付きトークンです。署名は改ざんの検出に使い、中身を暗号化することとは異なります。

トークンは入館証と同様に大切に扱ってください。Wiki が公開されていても、任意のトークンで全業務データを読めるわけではありません。

## セッションとトークンが両方登場する理由

通常のパスワードログインと企業 SSO は、同じ経路ではありません。

通常の入口はアカウント、パスワード、画像認証を確認してアクセストークンを発行します。企業 SSO の認可サーバーは、ブラウザーを使っている人を識別してから認可コードを発行し、トークン交換へ進みます。このため、このプロジェクトではサーバー側セッションも使います。

このプロジェクトでの分担は、セッションが認可サーバーにブラウザーのログイン状態を伝え、アクセストークンが後続の業務リクエストに使われる、というものです。一方を取得しても他方が自動で作られることはありません。
