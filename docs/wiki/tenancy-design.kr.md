# 2. 설계 생각: 서로 다른 회사의 데이터를 분리해 저장하기

A사와 B사의 데이터를 격리하려면 반드시 두 대의 컴퓨터에 둬야 할까요?

그렇지는 않습니다. 별도 DB, DB 안의 독립 공간, 회사 식별자를 둔 공유 테이블을 선택할 수 있습니다. 어떤 방식도 올바른 인가가 필요합니다. 물리적으로 나눠도 로그인·권한·캐시 문제가 자동으로 해결되지는 않습니다.

## 세 가지 흔한 방식

| 방식 | 비유 | 장점 | 감당할 일 |
|---|---|---|---|
| 테넌트별 DB | 회사마다 자료실 보유 | 백업·이동·자원을 개별 관리하기 쉬움 | DB·업그레이드·연결·운영 대상 증가 |
| 독립 schema를 지원하는 DB에서 공간 구분 | 같은 건물의 다른 방 | 객체와 관리 범위의 일정한 분리 | DB 지원·마이그레이션 도구 필요, 잘못된 공간 선택도 방지 |
| 테넌트 식별자가 있는 공유 테이블 | 같은 서류함에서 각 서류에 회사를 표시 | 배포와 공통 업그레이드 집중 | 읽기·쓰기·캐시·백그라운드의 회사 경계 유지 |

선택의 절충을 이해하는 표이며 지금 DB를 만들거나 배포를 바꾸라는 지시가 아닙니다. 고객 규모·규정·복구·운영 능력도 영향을 줍니다.

공유 테이블은 필드 하나를 추가하는 데서 끝나지 않습니다. 이후의 모든 접근이 그 소유 관계를 지켜야 합니다.

## 프로젝트의 현재 선택

업무 테이블은 소속 회사 번호인 tenant_id를 저장하며 서버 신원·명시적 쿼리·테넌트 플러그인·도메인 데이터 범위를 결합합니다.

마이크로서비스별로도 DB를 나눕니다. 인증 데이터와 업무 데이터는 담당 책임이 다릅니다. 이는 **서비스별 분리**이며 회사마다 같은 수의 새 DB를 만든다는 뜻은 아닙니다.

두 축을 나눠 보세요.

- 서비스는 인증·기반 플랫폼·워크플로 등의 책임을 누가 관리하는지 답합니다.
- 테넌트는 특정 업무 기록이 어느 회사의 것인지 답합니다.

하나의 서비스 DB가 여러 회사 데이터를 보관하고 한 회사의 업무가 여러 서비스를 거칠 수 있습니다.

## MyBatis-Plus를 재사용하는 이유

MyBatis는 Java DB 접근을 매핑합니다. MyBatis-Plus는 공통 작업과 플러그인 장치를 더하며 프로젝트의 많은 업무 테이블에서 사용됩니다.

플러그인은 DB 접근의 특정 단계에 처리를 끼워 넣는 장치입니다. 뒤의 common-service는 여러 업무 서비스가 공유하는 지원 코드입니다. 서비스가 이를 포함하고 해당 기능을 켜야 처리 체인을 쓸 수 있습니다. 따로 실행할 업무 서비스가 아닌 라이브러리입니다.

해당 DB 문에 회사 조건을 추가하면 개발자가 같은 제한을 반복해서 직접 쓰는 부담을 줄입니다. 범위 플러그인은 본인·조직에 대한 도메인 규칙을 연결합니다.

현재 의존성과 구현에서 추론한 절충이며 과거 선정 회의를 만들어 낸 것이 아닙니다. 작업 권한·상태 변경·하위 기록 소유 관계·메시지의 회사는 여전히 프로젝트 책임입니다.

다음 글은 실제 3.5.16 소스로 동작을 설명합니다. 프레임워크 이름만 나열하지 않습니다.

## “공통”에서 혼동하기 쉬운 세 가지

**공통 로그인 뒤에도 인가는 따로 필요합니다.** 진입점에서 사람을 알아도 업무 서비스가 회사와 작업을 확인해야 합니다.

**공통 플러그인이 모든 서비스의 동일한 설정을 뜻하지는 않습니다.** Auth는 명시적 테넌트 조건, common-service 도메인은 활성화된 플러그인, Workflow는 업무·엔진 테이블별 처리를 사용합니다.

**공유 캐시도 소유 관계를 구분합니다.** 하나의 Redis에 여러 회사 데이터가 있어도 키·조회·무효화에서 회사를 구분해야 합니다.

일반적인 구호보다 이번 처리가 어떤 경로인지 먼저 확인하세요.

## 전역 공유 내용도 보호해야 하는 이유

테넌트 목록·전역 권한 코드·개인 작업 종류·Nacos/XXL-JOB 기반 시스템은 모두 한 회사의 일반 업무 기록인 것은 아닙니다.

공유는 관리 경계가 다르다는 뜻이며 익명·일반 업무 요청의 무제한 읽기와 쓰기를 허용하지 않습니다. 릴레이가 여러 회사 메시지를 조회한다고 일반 쿼리의 교차 접근이 허용되는 것은 아닙니다.

마지막 글에서 캐시·백그라운드·예외를 함께 설명합니다. 먼저 [프레임워크 조건 추가](tenancy-framework.kr.md)를 읽어 보세요.
