# 6. 요청 밖의 처리: 캐시·메시지·작업·새 기능

요청 안에 회사 신원이 있어도 끝이 아닙니다. 캐시·온라인 상태·메시지·예약 작업도 어느 회사 데이터를 처리하는지 알아야 합니다.

## 캐시에서 회사 구분하기

A사와 B사 모두 “고객 등급” 사전이 있다고 해 봅시다. 이름만으로 캐시하면 먼저 읽은 회사의 값이 다른 회사에 영향을 줄 수 있습니다.

현재 사전 옵션 키는 dict:type:{tenantId}:{typeCode}로 회사와 유형을 함께 사용합니다. DictDataServiceImpl의 시작 부분이며 CACHE_KEY_PREFIX는 dict:type:입니다.

<!-- omni:source path="omni-backend/omni-base/src/main/java/com/omni/base/service/impl/DictDataServiceImpl.java" -->
```java
    public List<SysDictData> listEnabledData(Long tenantId, String typeCode) {
        String cacheKey = CACHE_KEY_PREFIX + tenantId + ":" + typeCode;

        // 优先从 Redis 读取
        String cachedJson = stringRedisTemplate.opsForValue().get(cacheKey);
```

tenantId는 명시적 메서드 인수이며 캐시에서 추측하지 않습니다. 읽기·DB 재조회·캐시 쓰기·변경 후 무효화 모두 같은 소유 규칙을 지켜야 합니다.

프런트 useDictOptions의 키에도 테넌트가 있습니다. XSS 설정은 xss:enabled:{tenantId}와 xss:rules:{tenantId}를 사용하고 변경 시 해당 키를 무효화합니다. Redis 하나를 공유해도 회사별 설정은 구분합니다.

## 모든 키가 같은 모양인 것은 아님

온라인 상태 키는 online:{userId}, 값은 username|jti입니다. 완전한 테넌트 정보가 없으므로 목록·강제 종료 서비스가 사용자 테이블로 회사와 조직 범위를 확인합니다.

JWT 차단 목록은 jti로 특정 토큰을 구분하며 회사마다 같은 이름의 출입증을 만드는 방식이 아닙니다. 키 이름뿐 아니라 연결 식별자·DB 조회·작업 시 인가도 확인합니다.

## 백그라운드가 회사를 자동으로 알 수 없는 이유

HTTP 요청은 보통 작업 스레드 하나에서 실행합니다. ThreadLocal은 그 스레드가 잠시 보관하는 메모로 생각할 수 있습니다. 스레드 풀·큐·예약 작업으로 넘기면 다른 스레드나 서비스에서 실행할 수 있습니다.

브라우저 요청의 메모를 자동으로 받는다고 가정하면 안 됩니다. 회사 식별자를 메시지·작업·메서드 인수로 명확히 전달해야 합니다.

신뢰성 있는 메시지 인터페이스는 tenantId를 요구합니다.

<!-- omni:source path="omni-backend/omni-common-core/src/main/java/com/omni/common/core/mq/ReliableMessageRelay.java" -->
```java
    void send(String bindingName, Object payload, Long tenantId);
```

호출자가 소속을 제공하고 릴레이는 현재 스레드에서 추측하지 않습니다. 구현은 업무 DB의 대기 발송 목록 Outbox에 먼저 기록한 뒤 백그라운드에서 전달합니다.

개인 작업 메시지에도 명시적 필드가 있습니다.

<!-- omni:source path="omni-backend/omni-common-core/src/main/java/com/omni/common/core/job/UserJobMessage.java" -->
```java
    /** 租户 ID，用于多租户隔离，确保任务在正确的租户上下文中执行 */
    private Long tenantId;
```

처리기는 이를 검증하고 사용해야 합니다. DTO에 속성만 추가해도 모든 처리가 격리되지는 않습니다. 라우팅·매개변수 검증·쿼리·정리는 각각 필요합니다.

## 교차 테넌트 백그라운드는 명확한 책임

MQ 릴레이는 기반 시스템 책임으로 모든 테넌트의 대기 메시지를 조회합니다. 소비자는 이벤트의 회사 식별자를 검증하고 도메인의 수신 중복 제거 목록 Inbox로 중복 실행을 막습니다. 생산자 스레드의 컨텍스트에 의존하지 않습니다.

보관·마이그레이션 등 시스템 작업도 여러 테넌트를 처리할 수 있습니다. 전용 진입점과 책임이 있는 예외이며 일반 업무 API가 따라 할 수는 없습니다. 외부 메시지 조회는 여전히 tenantId로 제한합니다.

| 내용 | 현재 경계 |
|---|---|
| sys_tenant | 통제된 테넌트 목록 |
| sys_permission | 전역 권한 코드, 역할 인가는 테넌트별 |
| sys_user_job_type | 공통 개인 작업 유형, 각 작업은 테넌트와 생성자를 가짐 |
| Nacos·XXL-JOB 등 | 관리 영역 규칙이 업무 데이터의 무제한 접근을 허용하지 않음 |
| MQ Relay | 의도적 Outbox 교차 조회, 일반 쿼리는 제한 |
| Flowable ACT_* | 엔진과 전용 쿼리에서 검사하며 일반 도메인 TenantLine에 일괄 위임하지 않음 |

공유는 소유 규칙이 다르다는 뜻이며 신원·권한 검사를 없애지 않습니다.

## 새 기능을 한 경로로 확인하기

1. 소속 테넌트·필수 열·값을 전달하는 책임을 정합니다.
2. 명시 SQL·플러그인·직접 JDBC·엔진 API 중 어떤 경로인지 보고 플러그인 밖은 따로 검사합니다.
3. 작업 권한과 범위를 구분하고 본인이 신청자·담당자·현재 사용자인지, 조직이 어느 열인지 확인합니다.
4. 상세가 어느 부모를 통해 조회 권한을 상속하는지 확인하고 없는 owner 열을 만들지 않습니다.
5. 캐시 키·DB 조회·무효화에서 회사 소속을 유지하며 온라인 상태 같은 특수 키는 연결 관계를 검사합니다.
6. 메시지·작업에 회사를 명시하고 소비·중복 제거·실패 재시도를 검증합니다. 원래 요청 스레드에 의존하지 않습니다.
7. finally에서 신원과 범위를 지우고 쓰기는 소유 관계·상태·버전·영향 행 수도 확인합니다.

연동 접근법이며 모든 서비스를 바꾸라는 지시는 아닙니다. 권한 어노테이션이나 테넌트 플러그인 하나로 전체 경로가 완성되지는 않습니다.

## 멈춘 계층부터 조사하기

| 현상 | 먼저 확인 | 복구 방향 |
|---|---|---|
| 같은 이름이 예상과 다른 공간으로 로그인 | 회사 선택·해당 사용자·현재 자격 증명 | 올바른 회사에서 재로그인, 헤더만 바꾸지 않음 |
| 메뉴는 있지만 기록 없음 | 작업·회사·역할 범위·주 조직·담당자 | 필터를 지우기 전에 소유 관계와 범위 확인 |
| 범위 서비스 거부·이용 불가 | 인수·권한 부여·사용자와 회사·상위 서비스 | 실제 403/503 등 분기에 따라 처리, 전체 조회로 완화 금지 |
| 캐시에 다른 설정·이전 값 | 키 소속·DB 조건·무효화 대응 | 소속·무효화 경로를 수정하고 다시 조회 |
| 백그라운드에 회사 누락 | 메시지·작업과 소비자 컨텍스트 | 추측 대신 명시적으로 전달·검증 |
| 워크플로 확장에 컨텍스트 누락 | 진입점·TenantInfoHolder·현재 폴백 | 전용 경로 조사, 기본 1을 안전 방식으로 쓰지 않음 |

현재 소스의 설명입니다. 원리를 이해하는 것과 모든 교차 테넌트 시나리오 실행은 별개이며 정적 발췌나 이미지를 전체 격리 합격 증거로 삼지 않습니다.

후속 개선은 회사 누락 처리의 일관성·전용 쿼리의 명확한 소속·더 많은 교차 테넌트 부정 사례에 집중할 수 있습니다. 각각 재현과 검증이 필요하며 문서 정리를 이유로 업무 리팩터링으로 확대하지 않습니다.
