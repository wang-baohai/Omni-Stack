# 2. 设计思路：不同公司的数据怎样分开存

先问一个实际问题：甲公司和乙公司的数据，必须放在两台机器上才算隔离吗？

不一定。可以把它们放在不同数据库，也可以放在同一个数据库的不同区域，或者放在同一张表里，用所属企业的标识区分。每种方式都要正确授权；“物理上分开”也不会自动修好登录、权限或缓存。

## 三种常见的安排

| 方式 | 可以怎样理解 | 获得什么 | 需要承担什么 |
|---|---|---|---|
| 每个租户独立数据库 | 每家公司有自己的资料室 | 数据备份、搬迁和资源分配更容易单独安排 | 建库、升级、连接管理和运维对象更多 |
| 在支持独立 schema 的数据库内划分空间 | 同一座楼，不同公司的资料在不同房间 | 一定程度分开对象和管理范围 | 数据库支持与迁移工具要配合，仍要防止走错空间 |
| 共享表，记录带租户标识 | 同一套档案柜，每份记录都标所属企业 | 部署和统一升级相对集中 | 每条读写、缓存、后台任务都必须守住企业边界 |

这是一张理解取舍的表，不是让你现在新建数据库或更改部署。真正选择还会受客户规模、合规、恢复方式和运维能力影响。

共享表的关键不在“加一个字段就好了”，而在后续每条访问都不能忘记这个字段代表的归属。

## 本项目采用的方式

当前工程在业务表中保存所属企业编号字段 tenant_id，并结合服务端身份、显式查询条件、租户插件与领域数据范围处理访问。

工程本身还按微服务划分数据库。比如，认证数据与某个业务服务的数据有各自的归属。这是**服务分库**；它不表示每家公司都会得到同样数量的新数据库。

可以把两个维度分开：

- 服务维度回答“认证、基础平台、工作流等职责分别由谁管理”。
- 租户维度回答“这一份业务记录属于哪家企业”。

因此，同一个服务的数据库可以保存多家企业的数据；同一家企业的一次业务也可能经过多个服务。

## 为什么复用 MyBatis-Plus

MyBatis 帮 Java 程序执行映射好的数据库访问。MyBatis-Plus 在这套基础上提供通用数据操作和插件机制，工程已经使用它管理大量业务表。

这里的插件，就是在数据库访问的相应阶段插入一段处理。后文的 common-service 是仓库里供多个业务服务共用的支撑代码；服务引入并开启相应能力后，才能使用它的处理链。它本身是一组库，不是需要另外启动的业务服务。

租户插件在符合条件的数据库语句执行前加入企业条件，可以减少每个开发者反复手写相同限制的工作。数据范围插件再接入各领域的本人、组织等规则。

这里是根据当前依赖和实现推导的取舍，不是虚构一次历史选型会议。它也不意味着插件能够替代所有判断：是否有权限、能不能修改当前状态、子表归谁、后台消息来自哪家企业，仍是工程的责任。

下一篇会用实际 3.5.16 源码解释插件怎样工作，而不是只列一串框架名字。

## 三种容易误解的“统一”

**统一登录，不等于统一授权。** 同一个入口认出了用户，业务服务仍要知道当前企业和具体操作。

**统一插件，不等于所有服务用法相同。** Auth 的查询显式带租户条件；采用 common-service 的领域服务可启用租户与数据范围插件；Workflow 对业务表和引擎表分别处理。

**统一缓存，不等于数据混在一起。** 同一套 Redis 可以保存不同企业的内容，但键、读取条件和失效操作都必须能够区分归属。

读后面的实现时，先问“这条路径是哪一类”，比记住一个统一口号更有用。

## 共享的内容为什么仍需要保护

租户目录、全局权限码目录、个人任务类型目录，以及 Nacos、XXL-JOB 等基础设施，不都属于某一家企业的普通业务记录。

共享表示它们的管理边界不同，不表示匿名用户或普通业务请求可以任意读取、修改。后台中继可以扫描多家企业的待发消息，也不能成为普通查询跨租户的理由。
