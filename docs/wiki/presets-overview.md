# 预设是什么：源码子集与生成工程的取舍

“预设”不是另一套代码，而是对模块目录的一次命名选择。`scaffold/presets/*.yaml` 只列出显式模块，真正的组件清单由 `scaffold/catalog/modules.yaml` 的依赖关系计算出来。理解这一点，才能判断裁剪的收益和代价。

## 显式模块与依赖闭包

以 core 为例：

```yaml
id: core
displayName: 核心平台
description: 认证、RBAC、组织、字典、日志与基础任务。
modules: [base, gateway, mysql, redis, nacos]
```

文件里只有 5 个显式模块，但 `base` 依赖 `auth`，`auth` 与 `nacos` 依赖 `platform`，`gateway` 依赖 `base`。当前 CLI 解析结果是 7 个模块：

```text
platform, auth, base, nacos, gateway, mysql, redis
```

所以阅读预设时必须区分两件事：

- **显式模块**：人写进预设文件的选择。
- **依赖闭包**：catalog 根据依赖计算出的实际模块集合。

只改显式列表、不检查闭包，容易误以为“没选就没有”。例如没有直接写 `auth`，但 core 的闭包包含它，因为登录与权限是基础平台的前提。

## 两种使用方式

同一份预设可以走两条路：

| 方式 | 命令形态 | 产物 | 适用场景 |
|---|---|---|---|
| 源码子集 | `dev up --preset core` | 在当前源码树内启动闭包对应的服务 | 阅读源码、调试、在同一仓库内开发 |
| 生成工程 | `preset create core --output ...` | 一个新的裁剪工程，含自己的锁、文档和 AI 入口 | 交付独立项目、从更小代码库开始 |

两者不是同义词：

- 源码子集保留完整源码树，只是启动更少的服务；未选模块可能仍在磁盘上。
- 生成工程会裁剪模块、前端资源、文档、种子与配置引用，产物必须自足，不能依赖原仓库路径。
- 两者都仍然需要数据库迁移、种子、私有配置和 Nacos 认证；裁剪减少的是组件，不是这些前置。

## 收益与代价

**收益**

- 更少的服务、端口和进程，启动与排错范围更小。
- 权限、菜单、网关路由和迁移只围绕选定闭包，阅读时噪声更少。
- 生成工程可作为独立交付物，避免把不需要的业务一起带走。

**代价**

- 预设只描述模块选择，不替你填写秘密、租户、端口冲突处理或外部依赖。
- 裁剪后的工程仍要跑迁移和种子；没有数据库，认证和权限无法工作。
- 资源不是零。catalog 为每个模块给出最小/建议内存提示；core 的七个模块合计为最小 3328 MB、建议 5632 MB。这是**配置提示的算术和，不是实测占用**，实际值取决于 JVM、数据库缓存、构建和宿主环境。
- 组件减少不等于复杂度归零：Nacos 配置、网关断言、数据库连接和日志仍要理解。

三点共同边界：

- **空库首次安装五预设均未实测**：验证环境是 full 已初始化的共享库，且不允许第二环境、新库或清库；共享库结果不能当作空库安装结果。
- **发布就绪不能只看待审数**：表中 `release_ready=false` 和 18 项绿灯属于历史结果；还必须核对当前译文审校、完整覆盖及实际门禁，不能把旧通过记录直接继承到新生成物。
- **healthy 与登录成功不等于业务闭环**：表中历史窗口没有验证跨模块深度链路；后续完成的链路只能由对应版本的真实业务证据支持，不能从本表推断。

## 选择时先问四个问题

1. **需要哪些身份与权限？** 没有业务模块时，core 是否已覆盖登录、租户、角色、组织与字典。
2. **需要哪些运行时依赖？** 数据库、Redis、Nacos 是否都在闭包内；调度中心、消息队列是否被选入。
3. **配置从哪里来？** `.env`、Nacos 配置、数据库初始化分别由谁提供。
4. **要源码子集还是生成工程？** 前者适合开发，后者适合交付；验证口径不同。

## 一个容易忽略的边界

core 的描述包含“基础任务”，但当前 core 闭包**不包含 xxl-job**。`platform` 带有任务公共模块，`base` 也包含任务相关代码与接口，但调度中心服务不在 core 的 Compose 服务集合中。需要实际运行系统/个人定时任务时，应选择包含 `xxl-job` 的预设，或明确接受“任务代码存在、调度中心缺席”的限制。不要把模块代码的存在写成调度已可用。
