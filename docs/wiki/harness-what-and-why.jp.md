# Harness とは何か、なぜ必要なのか

まず普通のタスクを考えます。購買依頼に「予算科目」フィールドを追加し、購買権限を持つ人だけが変更できるようにする、というタスクです。モデルはエンティティのフィールド、API パラメータ、画面の入力欄を書けますが、このプロジェクトのテーブル接頭辞、テナント遮断の規則、権限コードの形式、マイグレーションの場所、変更後に実行すべき検査を既定では知りません。こうした「モデルの外側にあるエンジニアリング条件」を整理し、モデルが継続的かつ検証可能にタスクを完了できるようにする仕組みを、本稿では Harness と呼びます。

## モデルだけでは足りないもの

モデルは与えられた文脈からコードを生成するのが得意ですが、実際のタスクには五種類の情報が必要です。

| 不足 | 具体的な現れ方 | ない場合の結果 |
|---|---|---|
| 文脈 | テーブル構造、モジュール境界、既存 API、エラーコード | つながらないもっともらしいコード |
| 制約 | `R<T>`、書き込み時の権限コード、テナント項目を手書きしない | コンパイルは通るが規約違反 |
| ツール | ビルド、テスト、生成器、DB マイグレーション、ブラウザ | 実行せずに「正しそう」で終わる |
| 検証 | 単体テスト、構造検査、リンク検査、実際のログイン | 「変更した」を「検証した」とみなす |
| フィードバックと断点 | 失敗ログ、未完了項目、次の入口 | 次のセッションがゼロから推測して繰り返す |

Harness は新しいフレームワークでも、モデルを「賢くする」プロンプトでもありません。上記の情報をモデルが読め、実行でき、検査できる場所に置き、失敗が次へ続けられる痕跡を残すエンジニアリングの取り決めです。

## 実用的な判定基準

Harness の有無は使うモデルではなく、次の三問で判断します。

1. 新しいメンバーやセッションが、口頭の記憶ではなくリポジトリ内で現在の事実を見つけられるか。
2. 間違えたとき、人が目視するのではなく自動検査が失敗するか。
3. 中断後に、検証可能な進捗・証拠・次の行動が残るか。

三問すべてが「はい」なら、モデル参加型の開発には安定した土台があります。大きなモデルとシステムプロンプトだけでは短いタスクしか扱えず、長くなると文脈の喪失、制約のずれ、「早すぎる完了宣言」が同時に現れます。

## 解決しないこと

Harness は要件判断、権限設計、人のレビューを代替できず、生成された業務ロジックの正しさも保証しません。ツールの限界も残ります。自動テストが実際の外部認可画面を覆えないことや、ブラウザツールが環境の制約を受けることがあります。その場合は未検証として記録するのが正しく、長いプロンプトで隠すべきではありません。

あるベンダーのエンジニアリングブログは、長いタスクの代理における典型的な失敗を「一度に多くをやりすぎる」「完了前に完了したと宣言する」と説明し、初期化スクリプト、進捗ファイル、機能リスト、コミット要約などの実践を挙げています。これは一組織の経験であり業界標準ではありません。本稿では検証可能な一事例としてのみ扱います。詳細は[業界事例](harness-industry-practice.jp.md)を参照してください。
