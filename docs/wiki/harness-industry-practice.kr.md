# 업계 사례: 장기 작업 에이전트의 초기화, 진행, 커밋

이 글은 실제로 열고 날짜를 기록한 업계 자료 하나만 다루어 Harness가 엔지니어링에서 어떤 모습인지 보여 줍니다. 업계 조사가 아니며, 어떤 실천이 다른 실천보다 우월함을 증명하지 않습니다. 결론은 "이 조직은 이렇게 했다"로 한정해 읽고 "업계는 이렇게 한다"로 확장하지 마세요.

## 설명하는 문제

글은 장기 작업 에이전트의 흔한 실패를 두 가지로 정리합니다. 한 번에 너무 많이 시도하는 것, 그리고 실제로 끝나지 않았는데 완료를 선언하는 것입니다. 이것은 더 긴 프롬프트로 충분하지 않은 이유를 설명합니다. 문제는 단일 응답의 품질이 아니라 세션을 넘는 상태, 진행, 수용입니다.

## 설명하는 실천

설명된 흐름은 관찰 가능한 네 행동으로 나뉩니다.

1. **초기화 에이전트**: `init.sh`, 진행 파일, 최초 커밋을 준비해 이후 세션에 안정된 시작점을 준다.
2. **증분 전진**: 이후 세션은 작게 나아가고 다음을 위한 명확한 산출물을 남기도록 요구받는다.
3. **기능 목록**: JSON 목록으로 기능을 기록하고 `passes` 필드 변경만으로 상태를 갱신한다.
4. **커밋과 요약**: 진행을 커밋하고 요약을 써서 이력을 추적 가능하게 한다.

공통 아이디어는 "어디까지 했는지, 무엇이 남았는지, 어떻게 계속할지"를 대화에서 저장소의 검증 가능한 객체로 옮기는 것입니다. 이는 Harness의 피드백/체크포인트와 일치하지만, 파일 이름과 구체적 흐름은 해당 조직의 구현이므로 모든 프로젝트에 그대로 이식해서는 안 됩니다.

## 인정하는 한계

글은 시각과 브라우저 자동화 같은 도구 능력의 한계가 남는다고 명시합니다. 이 인정은 중요합니다. Harness는 흐름을 정리할 수 있지만 도구 능력을 새로 만들어 내지는 못합니다. 도구가 닿지 않는 실제 페이지나 인가 흐름에서는 "에이전트가 끝냈다"로 증거를 대체하지 말고 미검증으로 기록합니다.

## 이 프로젝트와의 관계

Omni-Stack은 같은 목표를 가지지만 구현은 다릅니다.

| 관점 | 사례 | 이 프로젝트의 현재 |
|---|---|---|
| 진행 매체 | 진행 파일, 기능 목록 | 매니페스트 상태, 증거 파일, 미완료 목록(프로세스 기록은 제품 저장소 밖) |
| 제약 매체 | 프롬프트와 저장소 산출물 | `AGENTS.md`, 아키텍처/API/패턴 문서, 하드 제약 |
| 검증 매체 | 커밋, 요약, 도구 실행 | 빌드, 테스트, 품질 게이트, 실제 Docker 실행 |
| 사실 무효화 | 언급 없음 | 소스 다이제스트 갱신으로 번역 검토 무효화, 소스 발췌 테스트가 원문과 비교 |

"이 프로젝트" 열은 저장소에서 위치를 찾을 수 있는 현재 구현만 설명합니다. 유사점은 개념 이해를 위한 것이며 동등성을 주장하지 않습니다.

## 인용 방법

- 쓸 수 있는 문장: "Anthropic은 2025-11-26 엔지니어링 블로그에서 초기화 스크립트, 진행 파일, 기능 목록, 커밋 요약 실천을 설명했다."
- 쓰면 안 되는 문장: "업계는 일반적으로 네 단계 흐름을 쓴다", "최신 최고 실천이다", "도입하면 효율이 몇 % 오른다".
- 짧은 원문을 인용할 때는 링크, 게시일, 접근일을 함께 쓰고 무엇을 지지하고 지지하지 않는지 밝힙니다.
