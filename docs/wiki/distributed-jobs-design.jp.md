# 2. XXL-JOB を選ぶ理由：何を管理する必要があるか

定期実行の方法は一つではありません。まず複数マシンへの割り当て、一元的な確認、手動実行、実行履歴、復旧が必要かを考えます。道具が増えると配置、認証、整合性の維持も複雑になります。

## 代表的な三つの方法

| 方法 | 向いている用途 | 自分たちで担うこと |
|---|---|---|
| OS の定期実行 | 単一マシンのスクリプト、固定の保守 | マシン管理、アプリの権限、ログ、重複実行 |
| アプリ内部のタイマー | サービスと共に動く少数の周期処理 | 複数台の調整、一元管理、復旧 |
| センターと実行器 | 複数サービスへの割り当てと共通記録 | センターの可用性、登録、ネットワーク、業務の冪等性 |

XXL-JOB は三番目に当たります。本プロジェクトでは複数サービスの保守とユーザー自身が作るジョブが必要なので、既存のセンターと実行器を使用しています。これは現在の選択理由であり、他の方法を否定したり、第二のスケジューリング基盤を追加したりする説明ではありません。

## 現在のバージョンと役割分担

core と Admin は 3.3.1 に固定されています。Admin はスケジューリングの記録を持ち、業務サービスは業務データと個人ジョブの帰属を持ちます。実行器は各サービス内で動き、異なる AppName で送信先を区別します。

異なる実行器グループに同名の handler が存在することがあります。たとえば複数サービスに MQ 中継があっても、処理するデータは各サービスのものです。名前だけでなくグループも確認しないと、別の対象を調べてしまいます。

## 二つの記録は一つのトランザクションではない

個人ジョブの作成では、Base が「誰の仕事か」を保存し、センターが「いつ動かすか」を登録します。一つのローカル DB トランザクションが、別サービスへの HTTP 操作を自動的に含むわけではありません。

そのため関連 ID を保存し、登録失敗、応答の消失、ローカルへの ID 保存失敗を扱います。遠隔側に残存がないと確認してからローカル行を削除します。結果が不明なら関連を残して照合し、エラーだけを見て「何も作られていない」と判断しません。

単なる定時メソッドより複雑ですが、失敗時に何を復旧するかが明確になります。後の本文で実際の復旧コードを直接説明します。

## センターへ移さない責任

個人ジョブの帰属はテナントと作成者の両方で判断します。業務権限、状態遷移、トランザクション、冪等性もサービスの責任です。ネイティブ Admin のユーザー管理は Omni-Stack のロール認可と同一ではありません。

ワークフローは「誰が承認し次に何をするか」、定期ジョブは「いつ一度実行するか」、MQ は「非同期の情報をどう渡すか」を扱います。スケジューリングで中継を起動しても、配送結果は Outbox、Broker、消費側まで確認します。

## 運用上の負担

センターへ接続できないと登録、更新、実行依頼に影響します。実行器へ到達できないと割り当てに失敗し、処理が遅ければ後続が詰まります。不用意な再試行は業務を重複させます。ログ、適切な周期、限定した管理権限、復旧入口が必要です。
