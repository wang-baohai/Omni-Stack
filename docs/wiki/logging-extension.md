# 6. 扩展维护：为下一次排查留足线索

给新模块接日志，第一步不是到处打印完整对象，而是想清楚：哪件事需要被解释、谁会查看、多久以后还要能查到。不同答案决定它应该进入运行日志、业务操作记录，还是安全审计。

## 接入一个新功能的顺序

1. 为关键成功、失败和耗时留下必要事件，使用参数化日志与固定的事件含义。
2. 复用已有 traceId；异步任务和消息显式保留需要的关联字段，并在结束时清理上下文。
3. 需要业务操作记录的 Servlet 模块使用既有 operlog 接入点，补充快照和敏感字段规则；认证服务继续自己的安全审计路径。
4. 核对结构化输出和当前项目采集筛选，最后验证查询、访问权限与失败恢复。

“统一”是入口与约定统一，不要求把所有服务数据写进同一个业务库，也不要求用户能看到别人的日志。

## 维护时保留四类边界

| 边界 | 应保持的规则 |
|---|---|
| 内容 | 凭证和业务秘密不入日志，异常也要处理敏感文本 |
| 容量 | 评估等级、写入频率和保留期；不要默认长期打开SQL明文输出 |
| 身份 | 应用内查询按租户与权限；Grafana/Loki访问控制另行配置 |
| 控制面 | Docker socket即使只读挂载仍是高权限入口，不能把本地模板直接当生产最小权限方案 |

## 可以怎样改良

可逐步增加受控事件字段、字段清洗的回归用例、采集健康监测，以及按环境设定的保留与容量策略。先记录触发问题、预期收益和验证方法，再决定是否实施；这些是改良方向，不是当前已交付能力。

最后用一条不含秘密的实际请求验证输出与检索，用一个故意失败的合法请求验证错误信息；再确认跨租户不可读和敏感字段不会泄漏。只有配置检查而没有真实采集结果时，应写“配置已核对”，不要写“端到端采集通过”。

若需要理解操作日志在后台如何可靠传递，继续阅读[统一MQ管理](mq-principles.md)。
