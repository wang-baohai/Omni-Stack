# 6. 拡張と検証：状態遷移の処理をコピーせず接続する

新機能から送る前に、どの業務上の事実が発生し、受け手が何をするかを決めます。その後、本文、テナント、冪等キー、復旧方法を定義します。メッセージは事実を運びますが、認可や業務状態の検証を代替しません。

## 接続の順序

1. common-mqlogとReliableMessageRelayを使い、独自の走査や再試行テーブルをコピーしません。
2. 同じデータソースの有効な業務トランザクションで送信意図を書き、tenantIdを明示します。ロールバック時に待ち記録が残らないことを検証します。
3. 対象サービスのSpring Cloud Streamにbindingとdestinationを設定し、戦略と実際のBrokerを一致させます。
4. 消費側で一意制約やドメインInboxにより冪等性を保ち、完了後にフレームワークの規約に従って確認します。実際の失敗は再試行可能なエラーとして残します。
5. スケジュール、送信、重複消費、テナント拒否、デッドレター、正式復旧を別々に検証します。

## 省けない境界

外部管理APIは信頼できるテナントと機能権限で絞ります。内部APIにも明示的tenantIdと内部呼び出し認証が必要です。中継は意図して全テナントを検索します。利用者用のテナント遮断をそのまま適用すると配送漏れになります。

Outboxはサービス間DBの原子コミットを保証しません。複数サービスの協調にはドメインの補償と冪等性が必要です。重複排除キーは同じ事実を指す必要があり、再試行ごとに別キーを作ってはいけません。msgKey、追跡ヘッダー、送信trueはその代わりではありません。

## 何を観察すればよいか

| 場面 | 必要な結果 |
|---|---|
| 業務のロールバック | 業務変更とOutboxのどちらも未コミット |
| Brokerに接続できない | 実際の失敗が待機かデッドレターとなり、偽SENTにしない |
| 送信後のプロセス停止 | 再配送を許し、業務は二重に反映しない |
| 二つの実行が同じ記録を取得 | 取得成功者だけ続行し、古い結果で上書きしない |
| 他テナントの読み取り・操作 | 内容を漏らさず拒否 |
| 正式な再送・無視 | 権限、状態、配送スイッチ、競合条件が有効 |

故障検証は登録したテスト対象と制御されたfixtureだけで行います。全スタック停止、ボリューム削除、業務状態の書き換えで成功を捏造しません。テストデータ、実業務、プロトコルfixture、実配送を区別します。

集約範囲やBroker戦略の拡張には具体的な要望、契約、安全境界、テストが必要です。本章は現状と拡張方法の説明で、それらの新機能を追加していません。
