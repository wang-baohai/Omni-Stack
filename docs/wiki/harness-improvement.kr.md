# 개선 방향: 이익, 비용, 검증 방법부터

여기 있는 것은 제안이며 현재 능력이 아닙니다. 각 항목은 문제, 이익, 비용, 검증 방법, 현재 상태를 적습니다. 검증 방법이 없는 제안은 목록에 넣지 않습니다. 그것은 소망일 뿐입니다.

## 제안 1: 여러 조직의 업계 사례 보완

**문제**: 업계 실천 문서에는 검증 가능한 자료가 Anthropic(2025-11-26) 하나뿐이라 조직 간 선택을 비교할 수 없습니다.

**이익**: "한 벤더의 구현"과 "여러 구현이 수렴하는 패턴"을 구분해 단일 경험을 규칙으로 오인할 위험을 줄입니다.

**비용**: 네트워크 권한, 시간, 사람의 읽기가 필요합니다. 각 자료에 게시일, 접근일, 지지하는 결론과 지지하지 않는 결론을 기록합니다.

**검증 방법**: 서로 다른 독립 조직의 1차 자료 최소 두 건. 각 외부 주장이 특정 출처로 이어짐. 글에 "업계 합의" 같은 표현이 없음.

**현재 상태**: 미완료. 이번 환경에서 외부 검색이 차단되어 미검증으로 기록했습니다. 대체 자료로 채우지 않았습니다.

## 제안 2: 소스 발췌 검사 범위 확대

**문제**: `omni:source` 장치는 원리 페이지의 Java/TypeScript 발췌를 덮지만, 코드가 있는 모든 글이 표시를 쓰지는 않습니다.

**이익**: 특히 리팩터링 후 오래된 코드를 계속 인용하는 글을 줄입니다.

**비용**: 각 발췌에 고유 소스가 필요하고 상류 발췌에는 버전 기록도 필요합니다. 범위에 비례해 유지 비용이 늘어납니다.

**검증 방법**: 새로 대상에 넣은 페이지에서 `docs/scripts/source-excerpts.test.mjs`를 실행합니다. 한 줄 변조는 실패해야 하고, 소스 누락, 언어 누락, 상류 버전 누락도 실패해야 합니다.

**현재 상태**: 장치는 있으나 범위가 제한적입니다. 한 번에 전부 옮기지 말고 장별로 추가하는 것이 좋습니다.

## 제안 3: 검토 대기열을 변경 영향으로 정렬

**문제**: 소스 변경으로 여러 번역이 동시에 검토 대기가 되지만 현재 대기열은 "링크 수정"과 "결론 변경"을 구분하지 않습니다.

**이익**: 검토자가 의미 변화가 큰 항목을 먼저 처리해 대기 시간이 줄어듭니다.

**비용**: 영향 수준을 정의해야 하고, 수준 분류가 검토 생략의 구실이 되어서는 안 됩니다.

**검증 방법**: 링크 수정과 결론 변경 두 가지를 만들어 수준 분류가 맞는지 확인합니다. 낮은 수준 항목도 대기로 남고 자동 서명되지 않아야 합니다.

**현재 상태**: 미구현. 현재 대기열은 상태별로 나열할 뿐 영향을 추론하지 않습니다.

## 제안 4: 체크포인트 템플릿을 재사용 자산으로

**문제**: 긴 작업 중단 시 실행자마다 기록 형식이 달라 복귀 비용이 큽니다.

**이익**: 복귀할 때 현재 단계, 실패 증거, 미완료 대상, 다음 행동을 빠르게 찾습니다.

**비용**: 템플릿이 짧지 않으면 작성 자체가 부담이 되고, 템플릿을 "완료 증명"으로 오인할 위험도 있습니다.

**검증 방법**: 실제 중단 복귀 훈련을 합니다. 템플릿과 저장소만으로 원 작성자에게 묻지 않고 계속할 수 있는가? 복귀 후 완료한 행동을 반복하지 않았는가?

**현재 상태**: 저장소에는 `ai/prompts`와 워크플로 자산이 있지만 통일된 체크포인트 템플릿은 제품 능력이 아닙니다. 먼저 `ai/prompts`에서 시험하고 실행 규칙을 직접 바꾸지 마세요.

## 제안 5: Harness 자체의 최소 측정 정의

**문제**: 측정이 없으면 "검사를 더해 좋아졌다"는 느낌일 뿐입니다.

**이익**: 변경 전후의 재작업, 실패 발견 시간, 복귀 비용을 비교할 수 있습니다.

**비용**: 측정은 숫자 놀이가 되기 쉽고, 표본이 적으면 불안정하며, 수집에도 추가 기록이 필요합니다.

**검증 방법**: 수동으로 모을 수 있는 세 지표(예: 첫 검증 통과까지의 재작업 횟수, 실패 발생에서 발견까지의 단계 수, 중단 후 복귀에 필요한 행동 수)를 정의하고 몇 개 작업을 기록한 뒤 자동화를 결정합니다.

**현재 상태**: 미구현이며 신뢰할 기준값도 없습니다. 지금 "몇 % 개선"을 쓰면 안 됩니다.

## 하지 말아야 할 것

- "더 자동"으로 만들기 위해 에이전트가 직접 커밋, 공개, 프로덕션 조작을 하게 하지 마세요. 권한과 책임 경계가 먼저입니다.
- 부족한 도구나 검증을 프롬프트로 대체하지 마세요. 프롬프트는 실제 실행 증거를 만들지 못합니다.
- 대기열을 초록으로 만들려고 번역을 일괄 동기화하지 마세요. 사실과 검토의 대응이 깨집니다.
- 한 벤더 자료를 업계 표준으로 쓰지 마세요. 출처의 수와 독립성이 결론의 강도와 맞아야 합니다.

## 순서

하나만 한다면 제안 4를 고릅니다. 체크포인트 템플릿은 비용이 가장 낮고 중복 작업을 직접 줄입니다. 제안 1은 외부 조건에 묶이고, 제안 2와 3은 유지 투자가 필요하며, 제안 5는 마지막입니다. 안정된 흐름 전의 측정은 잡음만 기록합니다.
