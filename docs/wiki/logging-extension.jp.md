# 6. 拡張と保守：次の調査に役立つ記録を残す

新しいモジュールでは、何を説明する記録か、誰が見るか、いつまで検索できる必要があるかを最初に考えます。その答えで、実行ログ、業務操作記録、安全監査のどこに入れるかを決めます。完全なオブジェクトを至る所で出力することから始めません。

## 新機能を接続する順序

1. 成功、失敗、所要時間に必要なイベントを残し、パラメーター化したログと安定した意味を使います。
2. 既存のtraceIdを使い、非同期処理とメッセージでは関連項目を明示的に引き継ぎ、終了時にコンテキストを消します。
3. 操作記録が必要なServletモジュールでは既存のoperlog入口を使い、スナップショットと機密項目のルールを追加します。認証サービスは独自の安全監査経路を保ちます。
4. 構造化出力と現在のプロジェクトの絞り込みを確認し、最後に検索、権限、復旧を検証します。

統合とは入口と約束を共通にすることです。全サービスの業務DBを一つにしたり、他人のログを読めるようにしたりする意味ではありません。

## 四つの境界を保つ

| 境界 | 守ること |
|---|---|
| 内容 | 資格情報と業務秘密を出さず、例外内の機密文も処理する |
| 容量 | レベル、頻度、保持期間を評価し、SQLの平文出力を既定で長期間有効にしない |
| 本人と権限 | アプリではテナントと権限を守り、Grafana/Lokiのアクセス制御は別途設定する |
| 制御面 | Docker socketの読み取り専用マウントも高権限。ローカルのひな形を本番の最小権限設計と見なさない |

## 改良できること

管理されたイベント項目、サニタイズの回帰テスト、収集の健全性監視、環境別の保持・容量方針を段階的に追加できます。問題、利益、検証方法を先に記録してから実装を判断します。これは改善の方向で、実装済みの機能ではありません。

最後に、秘密を含まない実際のリクエストで出力と検索を確認し、正当な失敗リクエストでエラー記録も確認します。他テナントから読めないことと、機密情報が漏れないことも検証します。設定だけなら「設定を確認済み」と記録し、「収集経路全体の検証に成功」とは書きません。

操作記録の信頼性のある配送は、[統合MQ管理](mq-principles.jp.md)へ進んでください。
