# 6. リクエストの外側：キャッシュ・メッセージ・ジョブ・拡張

要求内の会社が分かっても、すべてが終わるわけではありません。キャッシュ、オンライン状態、メッセージ、定期ジョブも、どの会社のデータを扱うか知る必要があります。

## キャッシュで会社を区別する

両社に「顧客ランク」の辞書があるとします。この名前だけでキャッシュすると、先に読んだ会社の値が別会社に影響する可能性があります。

現在の辞書選択肢は dict:type:{tenantId}:{typeCode} で、会社と辞書種別を合わせます。DictDataServiceImpl の先頭です。CACHE_KEY_PREFIX は dict:type: です。

<!-- omni:source path="omni-backend/omni-base/src/main/java/com/omni/base/service/impl/DictDataServiceImpl.java" -->
```java
    public List<SysDictData> listEnabledData(Long tenantId, String typeCode) {
        String cacheKey = CACHE_KEY_PREFIX + tenantId + ":" + typeCode;

        // 优先从 Redis 读取
        String cachedJson = stringRedisTemplate.opsForValue().get(cacheKey);
```

tenantId は明示的引数で、キャッシュから推測しません。読取、キャッシュがないときの DB 照会、キャッシュへの保存、変更後の無効化も同じ帰属規則にします。

フロントの useDictOptions の鍵にもテナントを含めます。XSS 設定は xss:enabled:{tenantId} と xss:rules:{tenantId} を使い、変更後は対応鍵を無効化します。一つの Redis でも会社別の値を区別します。

## 鍵の形はすべて同じではない

オンライン状態は online:{userId}、値は username|jti です。完全なテナント情報はなく、一覧・切断サービスが利用者表で会社と組織範囲を確認します。

JWT ブラックリストは jti で特定トークンを識別します。会社ごとに同名の通行証を作る方式ではありません。鍵だけでなく、関連識別子、DB 照会、操作認可を調べます。

## バックグラウンドが会社を自動では分からない理由

HTTP リクエストは通常、一つの作業スレッドで処理されます。ThreadLocal はそのスレッドの一時メモと考えられます。スレッドプール、キュー、定期実行へ移ると、別スレッドや別サービスになることがあります。

ブラウザー要求のメモが自動で届くとは限りません。会社識別子をメッセージ、ジョブ、引数に明示します。

信頼性付きメッセージの契約にも tenantId が必要です。

<!-- omni:source path="omni-backend/omni-common-core/src/main/java/com/omni/common/core/mq/ReliableMessageRelay.java" -->
```java
    void send(String bindingName, Object payload, Long tenantId);
```

呼出し元が帰属を提供し、中継がスレッドから推測しません。実装は業務 DB の未送信一覧である Outbox に先に保存し、後で配信します。

個人ジョブにも明示フィールドがあります。

<!-- omni:source path="omni-backend/omni-common-core/src/main/java/com/omni/common/core/job/UserJobMessage.java" -->
```java
    /** 租户 ID，用于多租户隔离，确保任务在正确的租户上下文中执行 */
    private Long tenantId;
```

処理器は値を検証して使う必要があります。DTO の属性を増やすだけで全処理を隔離できず、振分け、引数検証、検索、片付けがそれぞれ必要です。

## 横断するバックグラウンドには専用の責任がある

MQ 中継は基盤の責任として全テナントの未送信メッセージを走査します。受信側はイベントの会社を検証し、受信・重複排除一覧の Inbox と合わせて重複実行を防ぎます。送信側のスレッドには依存しません。

アーカイブ、移行なども複数テナントを扱う場合があります。専用入口と責任のある例外で、通常業務 API がそのまま模倣してよいわけではありません。外部向けメッセージ照会は tenantId を制限します。

| 内容 | 現在の境界 |
|---|---|
| sys_tenant | 制御されたテナント一覧 |
| sys_permission | 全体の権限コード一覧。ロール認可はテナント別 |
| sys_user_job_type | 共通の個人ジョブ種別。ジョブごとにテナントと作成者を保持 |
| Nacos、XXL-JOB 等 | 管理面規則は業務データの無制限アクセスを許可しない |
| MQ Relay | Outbox を意図的に横断走査し、通常照会は制限 |
| Flowable ACT_* | エンジンと専用クエリーで確認し、汎用ドメイン TenantLine 任せにしない |

共有は帰属方法の違いで、身元や権限の検査をなくす意味ではありません。

## 新機能を一つの経路として確認する

1. 所属テナント、表の列、値を渡す責任者を定めます。
2. 明示 SQL、プラグイン、直接 JDBC、エンジン API のどの経路か確認します。プラグイン外は別途検査します。
3. 操作権限と範囲を区別し、本人が申請者・担当者・現在利用者の誰で、組織がどの列か決めます。
4. 明細がどの親から可視性を継承するか確認し、存在しない owner 列を足しません。
5. キャッシュの鍵、DB 照会、無効化で帰属を維持します。オンライン状態の特殊鍵は関連確認が必要です。
6. メッセージ・ジョブで会社を明示し、受信、重複排除、失敗再試行を検証します。元の要求スレッドに依存しません。
7. finally で身元と範囲を消し、更新では帰属、状態、版、影響行数も確認します。

接続の考え方であって、全サービスの書換え要求ではありません。注釈一つやプラグイン一つで経路全体は完成しません。

## 止まった層から調べる

| 現象 | 先に確認 | 復旧方向 |
|---|---|---|
| 同名で想定と違う場所へログイン | 選んだ会社、対応利用者、現在の資格情報 | 正しい会社から再ログインし、ヘッダーだけ変えない |
| メニューはあるが記録なし | 操作、会社、ロール範囲、主組織、担当 | 条件を消す前に帰属と範囲を確認 |
| 範囲サービス拒否・停止 | 引数、許可、利用者・会社、上流 | 403/503 等の実分岐に従い、全件検索へ緩めない |
| キャッシュが別設定や古い値 | 鍵の帰属、DB 条件、無効化の対応 | 帰属や無効化を直して再取得 |
| バックグラウンドに会社なし | メッセージ・ジョブと受信コンテキスト | 推測せず明示し検証 |
| フロー拡張にコンテキストなし | 入口、TenantInfoHolder、現行フォールバック | 専用経路を調べ、既定 1 を安全策にしない |

現在のソースの説明です。機構を理解することと全横断シナリオを実行することは別で、静的引用や画像を全隔離テストの合格とはしていません。

今後は会社不足時の統一、専用クエリーの明示帰属、横断負例の拡充を検討できます。それぞれ再現と検証が必要で、文書を整えるための業務リファクタリングには広げません。
