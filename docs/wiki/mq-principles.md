# 1. 统一MQ管理：先理解“稍后处理”

保存业务时，有些后续工作不适合让用户一直等，例如把操作记录送到统一查询端。消息队列（MQ）让发起者先留下“需要处理的事情”，由另一端稍后接手。它解开双方必须同时在线的限制，也带来了等待、失败、重复与追踪问题。

## 用寄件来理解几个角色

| 名词 | 可以怎样理解 | 本工程中的例子 |
|---|---|---|
| 生产者 | 寄件人，产生待处理事件 | 业务服务或操作日志生产者 |
| Broker | 接收并转交消息的中间站 | RocketMQ |
| 消费者 | 收件并完成处理的一端 | Base中的操作日志消费者 |
| Outbox | 寄件人自己的待寄清单 | 各服务本地的sys_mq_message |
| 中继 | 从清单领取并寄出的人 | XXL-JOB触发的消息中继 |

Outbox不是Broker里的队列，管理页面也不是消息真正流动的通道。它帮助查看发送记录、重试和死信，而业务是否完成还要看消费结果。

## 为什么需要先记清单

如果业务保存后直接发MQ，可能出现业务已经提交、发送却失败；反过来先发消息再存业务，也可能出现消息已发、业务回滚。Outbox让业务与“待发记录”在同一个有效本地事务中一起提交，然后后台发送。

这个前提很关键：必须是同一数据源、同一有效事务和正确的代理调用。仅仅调用一个名叫send的方法，不能证明业务和消息原子提交。操作日志生产者还会捕获发送异常，不能用它为所有业务路径作保证。
