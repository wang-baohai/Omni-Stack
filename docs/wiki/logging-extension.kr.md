# 6. 확장과 유지보수: 다음 조사를 위한 단서 남기기

새 모듈에 로그를 붙일 때는 무엇을 설명할지, 누가 볼지, 언제까지 검색해야 할지부터 생각합니다. 그 답에 따라 실행 로그, 업무 작업 기록, 보안 감사 중 어디에 남길지 결정합니다. 모든 곳에 전체 객체를 출력하는 것으로 시작하지 않습니다.

## 새 기능을 연결하는 순서

1. 성공, 실패, 소요 시간에 필요한 사건을 기록하고 파라미터 로깅과 일정한 의미를 사용합니다.
2. 기존 traceId를 재사용하고 비동기 작업과 메시지에서는 필요한 연결 필드를 명시적으로 전달한 뒤 문맥을 정리합니다.
3. 작업 기록이 필요한 Servlet 모듈은 기존 operlog 진입점을 사용하고 스냅샷·민감 필드 규칙을 보완합니다. 인증 서비스는 자체 보안 감사 경로를 유지합니다.
4. 구조화 출력과 현재 프로젝트 필터를 확인한 뒤 조회, 접근 권한, 실패 복구를 검증합니다.

통합은 진입점과 규약을 공유한다는 뜻입니다. 모든 서비스의 업무 DB를 하나로 합치거나 다른 사람의 로그를 읽도록 한다는 뜻이 아닙니다.

## 네 가지 경계 유지하기

| 경계 | 지킬 규칙 |
|---|---|
| 내용 | 자격 증명과 업무 비밀을 기록하지 않고 예외의 민감 문자열도 처리 |
| 용량 | 수준, 빈도, 보관 기간을 평가하고 평문 SQL 출력을 기본으로 오래 켜 두지 않기 |
| 신원과 권한 | 앱 조회는 테넌트·권한 적용, Grafana/Loki 접근 제어는 별도 설정 |
| 제어 영역 | 읽기 전용 Docker socket 마운트도 높은 권한이므로 로컬 템플릿을 운영 최소 권한 설계로 간주하지 않기 |

## 개선할 수 있는 방향

관리되는 이벤트 필드, 정제 회귀 테스트, 수집 상태 감시, 환경별 보관·용량 정책을 점진적으로 추가할 수 있습니다. 문제, 기대 효과, 검증 방법부터 기록하고 구현을 결정하세요. 이는 개선 방향이며 이미 제공된 기능이라는 뜻은 아닙니다.

마지막으로 비밀 없는 실제 요청으로 출력과 검색을 확인하고, 적법한 실패 요청으로 오류 기록을 검증합니다. 다른 테넌트에서 읽을 수 없는지, 민감 필드가 새지 않는지도 확인하세요. 설정만 확인했다면 “설정 확인”이라고 쓰고 “전체 수집 경로 검증 통과”라고 쓰지 않습니다.

작업 기록의 신뢰성 있는 전달은 [통합 MQ 관리](mq-principles.kr.md)에서 이어집니다.
