# 7. 権限・ログアウト・問題の切り分け：トークン取得後の検査

ログインできても、すべての申請承認、他部門の記録、供給者機能が開くわけではありません。資格情報、業務権限、データ範囲、退出後の状態を整理して、正しい層を調べます。

## トークン付きリクエストにも残る検査

| 段階 | 問い | プロジェクトの処理 |
|---|---|---|
| ゲートウェイの検証 | 信頼でき、まだ有効な資格情報か | 署名、期限、トークン ID のブラックリスト |
| 内部の身元伝達 | 下流の身元を誰が確認したか | 外来の身元ヘッダーを除き、検証済み情報と署名したゲートウェイアサーションを付ける |
| 操作の認可 | この人が操作してよいか | コントローラー権限または専用の所有者検査 |
| データ範囲 | どの記録にアクセスできるか | 役割、組織、本人範囲、ドメイン集約の関連 |
| 業務規則 | 今この記録に対して操作してよいか | 状態、版、その他の業務条件 |

ゲートウェイが李さんを識別しても、他人の記録の承認は拒否され得ます。管理者の操作権限にもデータ範囲が必要です。メニューやボタンは表示であり、サーバーの検査を代替しません。

クライアントが身元ヘッダーを書いてもテナントや管理者を指定できません。ゲートウェイが外来ヘッダーを処理し、下流はアサーションを検証します。外部の任意の文字列を信頼しません。

## 調査に必要なトークンのフィールド

通常のパスワード JWT は RS256 署名です。

| フィールド | 意味 |
|---|---|
| sub | 現在の主体識別子 |
| tenant_id | 身元が属するテナント |
| username | ユーザー名 |
| roles | 役割情報 |
| scope | 発行時に書いた権限情報 |
| jti | この一つのトークンの識別子。区別と取消確認に使用 |
| iat、exp | 発行時刻と期限 |

権限は発行時のスナップショットです。役割を変えてもブラウザーのトークンは自動更新されません。変更後の認可と手元の資格情報の両方を確認します。

## 署名検証に秘密鍵が不要な理由

発行者は秘密鍵で署名し、検証者は公開鍵で確認します。公開鍵を配っても他人がトークンを発行できるわけではありません。中の情報を読めても、編集後に署名が通るとは限りません。パスワードなどの秘密をトークンへ入れないでください。

ゲートウェイの JwkKeyProvider は Auth の JWKS から RSA 公開鍵を取得してキャッシュします。次の連続原文でキャッシュか再取得かを決めます。

<!-- omni:source path="omni-backend/omni-gateway/src/main/java/com/omni/gateway/config/JwkKeyProvider.java" -->
```java
    public Mono<RSAPublicKey> getPublicKey() {
        // 缓存命中且未过期，直接返回（快速路径）
        if (cachedPublicKey != null && !isExpired()) {
            return Mono.just(cachedPublicKey);
        }
        // 缓存未命中或已过期，发起远程请求
        return fetchJwkSet();
    }
```

有効なキャッシュがあれば返し、なければ鍵集合を取得します。保持時間は設定で決まります。毎回の署名検証は毎回のネットワーク取得を意味しません。

全鍵ローテーションが無停止で処理できる証拠でもありません。接続先、キャッシュ、署名鍵、古いトークンの互換性は設定とテストで確認します。

検証後、ゲートウェイは X-User-Id、X-Tenant-Id、X-User-Name、役割・権限、X-Gateway-Assertion を渡し、受信 Bearer を除去します。業務サービスは事前認証規則でアサーションを検証してから処理を続けます。

完全なトークン、パスワード、Cookie を問題票、公開画像、外部デコードサイトへ貼らないでください。時刻、入口、エラー、秘匿化した関連情報から調べられます。

## ローカル退出・管理者による切断・プロトコル取消を分ける

メニューのログアウトはフロントの token、権限状態、動的ルートを消します。プロジェクト独自の /api/auth/logout で発行済み通常 JWT をすべて即時失効させる処理ではありません。「ブラウザーがログイン画面に戻った」と「旧資格情報がサーバーで取り消された」は別です。

管理者が権限確認後にオンライン利用者を切断すると、対応する記録を削除し、そのセッションの jti を 24 時間ブラックリストへ入れます。以後の保護リクエストで確認します。同じ人の全機器・全システムの資格情報を一括取消する意味ではありません。

Spring 認可サーバーには OAuth2/OIDC の取消・ログアウトもありますが、認可記録とセッションの境界が別です。入口が存在しても通常 JWT の全体ログアウトにはなりません。

## 供給者ポータルの追加検査

ポータルはローカルのパスワード認証を使います。通過しても、その資格情報でログインできることを示すだけです。

情報、評価、見積には SUPPLIER と有効なポータル関連付けも必要です。管理者が供給者の代わりになるわけではありません。役割、関連付け、業務状態を別々に確認します。

自己登録も別です。成功しても自動ログインせず、管理権限も与えません。既定 USER 割当を試みますが、失敗は現設計で警告だけです。「作成済み」が「全認可が準備済み」とは限りません。

## 現在の境界

- 独自のパスワード API は OAuth2 password grant ではなく、このグラントを対応方式として登録していません。
- フロントの型に任意の refresh_token があっても、保存するのはアクセストークンだけで自動更新はありません。設定したグラントと実装した更新を区別します。
- ポータルは既存の入口を再利用し、別の資格情報プロトコルを持ちません。
- ソーシャル入口は GitHub、Google、Gitee です。WeChat の画面やアダプターはありません。
- ソース、実行テスト、制御されたプロトコルテスト、実外部アカウント認可は別に記録します。相互の代用はできません。実外部アカウント連携は未検証範囲を別記します。

機器ページのポーリングと拒否ボタンにも制約があります。「成功」の表示だけで業務アクセスを判断せず、接続前に理解してください。

## 止まった段階から調べる

| 現象 | 先に確認 | 続け方 |
|---|---|---|
| 通常ログイン失敗 | 企業、画像認証の消費、ロック、パスワード | 新しい画像かアカウント状態を扱い、古い材料を再送しない |
| 企業 SSO がログインへ戻る | セッション、state と原本、コールバックとクライアント | 入口からやり直し、削除済み材料を使わない |
| 機器が待ち続ける | 確認、期限、待機か恒久エラーか | 画面とプロトコルエラーで判断し、待機を成功にしない |
| 外部ログイン失敗 | 拒否、戻り材料、state、関連付け衝突 | 提供者の入口から再開し、秘匿化したエラーを残す |
| 業務入口がない | 役割、権限、新しいトークン、対象入口 | 認可と資格情報を確認し、管理者アカウントを共有しない |
| 権限はあるが記録がない | テナント、組織、本人範囲、所有者、状態 | ドメイン規則を調べ、身元ヘッダー偽装で回避しない |
| ポータルが拒否 | SUPPLIER、有効な関連付け、供給者状態 | 利用登録と関連付けを確認し、管理者で代用しない |

通常ログインのサイト入口、認可コードの管理入口、ポータルは別のフロント分岐です。まず経路と保存・消費する戻り先を確認します。

認証変更は対応する実践ページへ戻ってください。「自社・自部門だけを見られる理由」は多テナント章で説明します。
