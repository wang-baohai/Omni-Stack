# 1. 인증과 인가: 한 번의 로그인부터 이해하기

리 씨가 Omni-Stack 홈을 열면 프로젝트 Wiki가 보입니다. 문서를 읽는 데는 로그인이 필요하지 않습니다. 구매 요청을 처리하려 할 때 자신의 신원을 확인하고, 계정이 사용할 수 있는 작업 공간으로 들어갑니다.

이 장은 이 과정을 따라갑니다. 시스템이 사람을 알아보는 방법, 로그인을 기억하는 방법, 로그인했어도 어떤 버튼을 쓸 수 없는 이유를 설명합니다. 앞부분은 Java를 몰라도 읽을 수 있습니다. 개념을 이해한 다음 프레임워크와 프로젝트 소스를 읽어 보세요.

## 한 번의 사용 과정을 끝까지 살펴보기

리 씨가 계정, 비밀번호, CAPTCHA를 제출합니다. 인증 서비스가 확인을 마치면 이후 접근에 쓸 자격 증명을 발급합니다. 다음 요청은 이 자격 증명을 가지고 게이트웨이를 통과합니다. 업무 서비스는 사용자가 해당 작업을 할 수 있는지, 어떤 기록에 접근할 수 있는지 확인합니다.

예를 들어 구매 시스템에 로그인할 수 있어도 자신의 요청을 승인할 권한까지 있는 것은 아닙니다. 부서 관리자가 담당 신청을 승인할 수 있어도 다른 회사의 데이터를 볼 수는 없어야 합니다. 로그인, 기능 권한, 데이터 범위는 서로 다른 질문에 답합니다.

로그인한다고 공개 Wiki 본문이 다른 문서로 바뀌지는 않습니다. 바뀌는 부분은 계정 영역입니다. 권한이 있는 계정은 그곳에서 작업 공간이나 관리 콘솔로 들어갑니다.

## 세 가지 질문을 구분하기

| 알고 싶은 내용 | 시스템이 하는 일 | 일상적인 예 |
|---|---|---|
| 이 사람은 누구인가 | 인증 | 안내 데스크가 방문자의 신원을 확인 |
| 무엇을 해도 되는가 | 인가 | 출입증이 허용된 층에만 접근을 허용 |
| 어떤 기록을 볼 수 있는가 | 데이터 범위 제어 | 부서 관리자가 자신의 담당 범위에 있는 요청을 처리 |

권한 오류가 났다고 비밀번호를 반복 입력해도 보통 해결되지 않습니다. 비밀번호 검증은 신원을 확인합니다. 역할, 조직, 업무 데이터 소유 관계는 각자의 조건을 충족해야 합니다.

메뉴와 버튼은 사용자가 조작하도록 돕는 화면 요소입니다. 요청이 실행될 때 서버도 권한을 검사해야 합니다. 버튼을 숨겼다는 사실만으로 API가 보호되지는 않습니다.

## 로그인 상태를 기억하는 방법

여기서 자주 등장하는 말이 세션과 토큰입니다.

세션은 서버가 보관하는 로그인 기록입니다. 브라우저는 보통 Cookie에 담긴 작은 참조 값을 보내고, 서버는 이에 해당하는 기록을 찾습니다. Cookie가 모든 신원 정보인 것은 아니며, 브라우저가 서버가 신뢰할 사람을 마음대로 정하는 것도 아닙니다.

토큰은 이후 요청에 실어 보낼 수 있는 접근 자격 증명입니다. Omni-Stack의 일반 비밀번호 로그인은 JWT를 반환합니다. JWT는 신원 관련 주장을 담을 수 있는 서명된 토큰입니다. 서명은 내용 변조를 확인하며, 내용을 암호화하는 것과는 다릅니다.

토큰은 출입증처럼 보관해야 합니다. Wiki를 공개로 읽을 수 있다고 아무 토큰으로 모든 업무 데이터를 조회할 수 있는 것은 아닙니다.

## 세션과 토큰이 함께 나오는 이유

일반 비밀번호 로그인과 기업 SSO는 같은 경로가 아닙니다.

일반 진입점은 계정, 비밀번호, CAPTCHA를 확인한 뒤 접근 토큰을 발급합니다. 기업 SSO가 사용하는 인가 서버는 브라우저의 사용자가 누구인지 먼저 알아야 인가 코드를 발급하고 토큰 교환을 이어 갈 수 있습니다. 이 단계에서는 서버 측 세션을 사용합니다.

프로젝트 내 역할을 기억하면 됩니다. 세션은 인가 서버가 현재 브라우저의 로그인 상태를 알아보게 하고, 접근 토큰은 이후 업무 요청에 쓰입니다. 하나를 얻는다고 다른 하나가 자동 생성되지는 않습니다.

다음 글에서는 네 참여자와 그림으로 인가 코드와 PKCE를 설명합니다. 약어부터 외울 필요는 없습니다.
