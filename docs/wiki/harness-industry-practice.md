# 行业实践案例：长任务代理的初始化、进度与提交

本文只讲一份实际打开并记录日期的行业材料，用它说明“Harness 在工程上具体长什么样”。它不是行业调查，也不能证明某种做法优于其他做法。阅读时请把结论限定为“这家组织这样做了”，不要扩写成“行业普遍如此”。

## 它描述了什么问题

该文把长任务代理的常见失败归为两类：一次尝试做太多，以及在未真正完成时宣布完成。这个描述能帮助我们理解为什么“更长的提示词”不够：问题不在单次回答质量，而在跨会话的状态、进度和验收。

## 它给出了哪些做法

文章描述的流程可以拆成四个可观察的动作：

1. **初始化代理**：先准备 `init.sh`、进度文件和一次初始提交，让后续会话有稳定起点。
2. **增量推进**：后续会话被要求小步前进，并为下一次留下清晰产物。
3. **功能清单**：用 JSON 列表记录功能，只通过修改 `passes` 字段更新状态。
4. **提交与摘要**：要求代理提交进度并写摘要，使历史可追溯。

这些动作的共同点是：把“做到哪里、还剩什么、如何继续”从对话上下文转移到仓库里的可核对对象。这与 Harness 的反馈/断点部分一致，但具体文件名和流程属于该组织的实现，不应原样移植到所有项目。

## 它承认的限制

文章明确说明仍存在工具能力限制，例如视觉和浏览器自动化。这个承认很重要：Harness 能组织流程，但不能凭空扩展工具能力。遇到工具覆盖不到的真实页面或授权流程，正确做法是标记未验证，而不是用“代理已完成”替代证据。

## 与本项目的关系

Omni-Stack 有相似的目标，但实现方式不同：

| 维度 | 该案例 | 本项目当前做法 |
|---|---|---|
| 进度载体 | 进度文件、功能清单 | 文档清单状态、证据文件、未完成清单（流程记录不在产品仓库内） |
| 约束载体 | 提示与仓库产物 | `AGENTS.md`、架构/API/模式文档、硬约束 |
| 验证载体 | 提交与摘要、工具执行 | 构建、测试、质量门、真实 Docker 运行 |
| 事实失效 | 未展开 | 源摘要刷新使译文复核失效、源码片段测试比对原文 |

表中的“本项目”只描述仓库中可定位的当前实现，不代表已经达到该案例的全部能力。相似点用于理解概念，不用于宣称等价。

## 如何引用这份材料

- 可以说：“Anthropic 在 2025-11-26 的工程博客中描述了初始化脚本、进度文件、功能清单和提交摘要的做法。”
- 不可以说：“行业普遍采用四步流程”“这是最新最佳实践”“采用后效率提升多少”。
- 如果需要在文章中使用原文短句，应同时给出链接、发布日期和访问日期，并说明它支持什么、不支持什么。
