# プリセットとは：ソースサブセットと生成プロジェクトの選択

「プリセット」は別のコードベースではなく、モジュール選択に付けた名前です。`scaffold/presets/*.yaml` は明示モジュールだけを列挙し、実際の構成は `scaffold/catalog/modules.yaml` の依存関係から計算されます。この理解が、絞り込みの利益とコストを判断する土台になります。

## 明示モジュールと依存閉包

core を例にします。

```yaml
id: core
displayName: コアプラットフォーム
description: 認証、RBAC、組織、辞書、ログ、基本タスク。
modules: [base, gateway, mysql, redis, nacos]
```

ファイルには 5 つの明示モジュールしかありませんが、`base` は `auth` に、`auth` と `nacos` は `platform` に、`gateway` は `base` に依存します。現在の CLI 解決結果は 7 モジュールです。

```text
platform, auth, base, nacos, gateway, mysql, redis
```

したがって、次の二つを必ず分けます。

- **明示モジュール**：人がプリセットファイルに書いた選択。
- **依存閉包**：catalog が依存から計算した実際のモジュール集合。

明示リストだけを変えて閉包を確認しないと、「選んでいないから存在しない」と誤解しやすくなります。たとえば `auth` は直接書かれていませんが、ログインと権限は基盤の前提なので core の閉包に含まれます。

## プリセットの二つの使い方

| 方式 | コマンドの形 | 成果物 | 用途 |
|---|---|---|---|
| ソースサブセット | `dev up --preset core` | 現在のソースツリー内で閉包のサービスを起動 | ソース読解、デバッグ、同一リポジトリでの開発 |
| 生成プロジェクト | `preset create core --output ...` | 独自のロック、文書、AI 入口を持つ新しい絞り込み工程 | 独立プロジェクトの納品、より小さいコードベースからの開始 |

両者は同義ではありません。

- ソースサブセットは完全なソースツリーを保持し、起動するサービスだけを減らします。未選択モジュールがディスクに残ることもあります。
- 生成プロジェクトはモジュール、フロントエンド資産、文書、シード、設定参照を絞り込みます。成果物は自足し、元リポジトリのパスに依存してはいけません。
- どちらも DB マイグレーション、シード、プライベート設定、Nacos 認証が必要です。絞り込みで減るのは構成であって、これらの前提ではありません。

## 利益とコスト

**利益**

- サービス、ポート、プロセスの数が減り、起動と調査の範囲が小さくなります。
- 権限、メニュー、ゲートウェイルート、マイグレーションが選択した閉包の周囲だけになり、読解時のノイズが減ります。
- 生成プロジェクトは不要な業務を抱えずに独立納品できます。

**コスト**

- プリセットはモジュール選択だけを表し、秘密、テナント、ポート競合の処理、外部依存は埋めません。
- 絞り込んだ工程でもマイグレーションとシードは必要です。DB がなければ認証と権限は動きません。
- リソースはゼロではありません。catalog はモジュールごとに最小/推奨メモリのヒントを持ち、core の 7 モジュール合計は最小 3328 MB、推奨 5632 MB です。これは**設定ヒントの算術和であり実測値ではありません**。実際値は JVM、DB キャッシュ、ビルド、ホスト負荷で変わります。
- 構成が減っても複雑さはゼロになりません。Nacos 設定、ゲートウェイのアサーション、DB 接続、ログは理解が必要です。

10 マス共通の三つの境界：

- **空 DB 初回インストールは五プリセットとも未実測**：検証環境は full 初期化済みの共有 DB で、第二環境・新規 DB・消去は許可されていません。共有 DB の結果を空 DB インストールの結果として書かない。
- **公開準備は審査待ち件数だけでは決まらない**：表の `release_ready=false` と自動検査 18 項目の通過は過去の結果です。現在の翻訳審査、全適用要件、実際の検証結果も確認し、旧版の合格を新しい生成物へ引き継がないでください。
- **healthy とログイン成功だけでは業務全体の完了を証明できない**：表の過去の実行ではモジュール横断の詳細な連鎖を検証していません。その後完了した連鎖は該当版の実際の業務証拠で確認する必要があり、本表からは推定できません。

## 選択前の四つの質問

1. **必要な身元と権限は何か。** 業務モジュールがないとき、core がログイン、テナント、ロール、組織、辞書を覆うか。
2. **必要な実行時依存は何か。** DB、Redis、Nacos が閉包にあり、スケジューラやメッセージキューが選ばれているか。
3. **設定はどこから来るか。** `.env`、Nacos 設定、DB 初期化を誰が提供するか。
4. **ソースサブセットか生成プロジェクトか。** 前者は開発、後者は納品に向き、検証基準が異なります。

## 見落としやすい境界

core の説明には「基本タスク」が含まれますが、現在の core 閉包に **`xxl-job` は含まれません**。`platform` は共通タスクモジュールを持ち、`base` もタスク関連コードと API を含みますが、スケジューラサービスは core の Compose サービス集合にありません。システム/個人の定期タスクを実際に動かすには `xxl-job` を含むプリセットを選ぶか、「タスクコードはあるがスケジューラはない」制約を明示的に受け入れてください。モジュールコードの存在をスケジューラ稼働として書かないでください。
