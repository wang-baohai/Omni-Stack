# 7. 권한·로그아웃·문제 해결: 토큰을 받은 뒤의 검사

리 씨가 로그인할 수 있어도 모든 승인, 다른 부서 기록, 공급업체 포털 기능이 열리지는 않습니다. 자격 증명·업무 권한·데이터 범위·로그아웃 상태를 함께 정리해 올바른 계층을 조사합니다.

## 토큰을 가진 요청에도 남는 검사

| 단계 | 질문 | 프로젝트 동작 |
|---|---|---|
| 게이트웨이 자격 증명 검증 | 신뢰할 수 있고 유효한가 | 서명·만료·토큰 ID 차단 목록 검사 |
| 내부 신원 전달 | 누가 하위 서비스 신원을 확인했는가 | 외부 신원 헤더 제거, 검증된 정보와 서명한 게이트웨이 assertion 주입 |
| 서버 작업 인가 | 이 사람이 실행해도 되는가 | 컨트롤러 권한 또는 전용 소유 관계 검사 |
| 데이터 범위 | 어떤 기록을 볼 수 있는가 | 역할·조직·본인 범위·도메인 집합 관계로 제한 |
| 업무 규칙 | 지금 이 기록에 작업할 수 있는가 | 상태·버전·기타 조건 확인 |

게이트웨이가 신원을 확인했어도 다른 사람의 신청 승인은 거부될 수 있습니다. 관리자에게 작업 권한이 있어도 기록 범위 검사는 필요합니다. 메뉴와 버튼은 UI이며 서버 검사를 대신하지 않습니다.

클라이언트가 신원 헤더를 넣어 테넌트나 관리자 신원을 정할 수는 없습니다. 게이트웨이가 외부 헤더를 처리하고 하위 서비스가 assertion을 검증합니다. 외부 문자열을 내부 신원으로 신뢰하지 않습니다.

## 조사할 때 알아둘 토큰 필드

일반 비밀번호 JWT는 RS256 서명을 사용합니다.

| 필드 | 의미 |
|---|---|
| sub | 현재 주체 식별자 |
| tenant_id | 신원이 속한 테넌트 |
| username | 사용자명 |
| roles | 역할 |
| scope | 발급 시 기록한 권한 |
| jti | 이 토큰 하나의 식별자, 구분과 취소 검사에 사용 |
| iat, exp | 발급·만료 시각 |

권한은 발급 시점의 스냅샷입니다. 역할을 바꿔도 브라우저의 기존 토큰이 자동 교체되지 않습니다. 새 인가 상태와 현재 자격 증명을 함께 확인합니다.

## 개인키 없이 서명을 확인하는 이유

발급자는 개인키로 서명하고 검증자는 공개키로 확인합니다. 공개키 공개가 토큰 발급 권한을 주지는 않습니다. 필드를 읽을 수 있어도 고친 토큰의 서명이 유효한 것은 아닙니다. 비밀번호 같은 비밀을 토큰에 담지 마세요.

게이트웨이 JwkKeyProvider는 Auth JWKS에서 RSA 공개키를 받아 캐시합니다. 캐시와 재조회를 선택하는 연속 원문입니다.

<!-- omni:source path="omni-backend/omni-gateway/src/main/java/com/omni/gateway/config/JwkKeyProvider.java" -->
```java
    public Mono<RSAPublicKey> getPublicKey() {
        // 缓存命中且未过期，直接返回（快速路径）
        if (cachedPublicKey != null && !isExpired()) {
            return Mono.just(cachedPublicKey);
        }
        // 缓存未命中或已过期，发起远程请求
        return fetchJwkSet();
    }
```

유효한 캐시는 바로 반환하고, 없거나 만료되면 키 집합을 요청합니다. 캐시 기간은 설정으로 정합니다. 매 요청의 서명 검사가 매번 네트워크에서 키를 받는다는 뜻은 아닙니다.

모든 키 교체가 끊김 없이 처리된다는 증거도 아닙니다. 주소·캐시·서명키·기존 토큰 호환성을 설정과 테스트로 확인해야 합니다.

검증 후 게이트웨이는 X-User-Id, X-Tenant-Id, X-User-Name, 역할·권한, X-Gateway-Assertion을 전달하고 수신 Bearer를 제거합니다. 업무 서비스는 사전 인증 규칙으로 assertion을 검증하고 계속합니다.

토큰 전체, 비밀번호, Cookie를 이슈·공개 스크린샷·외부 디코더에 붙이지 마세요. 시각·진입점·오류·민감 정보를 가린 요청 연관 정보부터 기록할 수 있습니다.

## 로컬 로그아웃·관리자 강제 종료·프로토콜 취소 구분

메뉴 로그아웃은 프런트 token·권한 상태·동적 라우트를 정리합니다. 자체 /api/auth/logout으로 이미 발급한 모든 일반 JWT를 즉시 무효화하지 않습니다. “브라우저가 로그인으로 돌아옴”과 “서버가 이전 자격 증명을 취소함”은 별개입니다.

관리자 강제 종료는 권한 검사 후 온라인 기록을 삭제하고 해당 세션 jti를 24시간 차단 목록에 넣습니다. 이후 보호 요청에서 검사합니다. 같은 사용자의 모든 기기·모든 시스템의 자격 증명을 취소하는 것은 아닙니다.

Spring 인가 서버도 OAuth2/OIDC 취소·로그아웃을 제공하지만 별도 인가 기록과 세션 경계가 있습니다. 엔드포인트가 있다는 이유로 일반 비밀번호 JWT의 전역 로그아웃이라고 설명하면 안 됩니다.

## 공급업체 포털의 추가 검사

포털은 로컬 비밀번호 인증을 재사용합니다. 통과했다는 것은 해당 자격 증명으로 로그인할 수 있다는 뜻뿐입니다.

프로필·평가·견적은 SUPPLIER 및 유효한 포털 연결도 필요합니다. 관리자 신원이 공급업체를 자동으로 대신하지 않습니다. 역할·연결·업무 상태를 각각 확인해야 합니다.

자가 가입도 별개입니다. 성공해도 자동 로그인하거나 관리 권한을 받지 않습니다. 생성 경로는 기본 USER 할당을 시도하지만 현 설계에서 실패는 경고만 남깁니다. 사용자 생성이 모든 인가 준비 완료를 뜻하지는 않습니다.

## 현재 능력의 경계

- 자체 계정·비밀번호 API는 OAuth2 password grant가 아니며 그 그랜트를 지원 로그인으로 등록하지 않습니다.
- 프런트 타입에 선택적 refresh_token이 있지만 접근 토큰만 저장하며 자동 갱신하지 않습니다. 등록 그랜트와 갱신 구현은 다릅니다.
- 포털은 기존 비밀번호 진입점을 쓰며 별도 자격 증명 프로토콜이 없습니다.
- 소셜 진입점은 GitHub·Google·Gitee이며 WeChat 화면·어댑터는 없습니다.
- 소스·실행 테스트·통제된 프로토콜 테스트·실제 외부 계정 인가는 구분해 기록하며 서로를 대신할 수 없습니다. 실제 외부 계정 연결의 미검증 범위는 별도로 남깁니다.

기기 글에는 폴링과 거부 버튼의 제한도 있습니다. 실제 기기를 연결하기 전에 이해하고 “성공” 표시만으로 업무 접근을 판단하지 마세요.

## 멈춘 단계부터 조사하기

| 현상 | 먼저 확인 | 다음 행동 |
|---|---|---|
| 일반 로그인 실패 | 회사·CAPTCHA 소비·계정 잠금·비밀번호 | 새 CAPTCHA를 받거나 계정 상태 처리, 이전 자료 반복 전송 금지 |
| 기업 SSO가 로그인으로 복귀 | 세션·state와 원본·콜백과 클라이언트 | 진입점에서 다시 시작, 지워진 자료 재사용 금지 |
| 기기가 계속 대기 | 사용자 확인·만료·대기와 영구 오류 구분 | 화면과 프로토콜 오류에 따라 처리, 대기는 성공이 아님 |
| 소셜 로그인 실패 | 외부 거부·콜백 자료·state·연결 충돌 | 해당 제공자에서 다시 시작, 민감 정보를 가린 오류 보관 |
| 업무 진입점 없음 | 역할·권한·토큰 갱신·대상 적합성 | 인가와 자격 증명 확인, 관리자 계정 공유 금지 |
| 권한은 있지만 기록 없음 | 테넌트·조직·본인 범위·소유 관계·상태 | 도메인 범위 검사, 신원 헤더 위조로 우회 금지 |
| 포털 로그인 후 거부 | SUPPLIER·유효한 연결·공급업체 상태 | 입점과 연결 확인, 관리자로 대신하지 않음 |

일반 로그인 기본 사이트 진입점, 인가 코드 콜백의 콘솔, 포털은 다른 프런트 분기입니다. 어떤 경로인지, 어떤 대상을 저장하고 소비하는지부터 확인하세요.

인증 코드를 수정하려면 해당 실습 글로 돌아갑니다. “내 회사·내 부서 데이터만 보이는 이유”는 멀티테넌트 장에서 이어갑니다.
