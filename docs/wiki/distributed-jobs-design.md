# 2. 为什么选择 XXL-JOB：先看需要管理什么

定时运行并不只有一种办法。选择工具前，先问任务是否需要跨机器派发、统一查看、手动触发、运行记录和失败恢复。工具越多，部署、认证和一致性处理也越复杂。

## 三种常见办法

| 办法 | 适合的问题 | 需要自行承担什么 |
|---|---|---|
| 操作系统定时器 | 单机脚本、固定维护动作 | 机器管理、应用权限、日志与重复执行 |
| 应用内定时器 | 少量随服务启动的周期工作 | 多副本协调、统一管理和故障恢复 |
| 集中调度中心与执行器 | 多服务任务、远程派发和统一记录 | 调度中心可用性、注册、网络和业务幂等 |

XXL-JOB 属于第三种。本项目已经需要多服务维护任务和用户自己创建的任务，因此采用现有调度中心与执行器。这里解释的是当前选择，不是声称其他工具不适合，也没有引入第二个调度平台。

## 当前版本和部署分工

工程固定使用 XXL-JOB core 与 Admin 3.3.1。Admin 使用自己的调度数据；业务服务保留业务数据和个人任务归属。执行器随服务运行，各服务使用不同 AppName，帮助调度中心区分发送目标。

同一个 handler 名称可以出现在不同执行器组中。例如几个服务都有 MQ 中继，但它们处理各自的数据。排查时要同时核对执行器组和 handler，只记名字会找错对象。

## 两份记录，为什么不能当成一个事务

用户创建个人任务时，Base 要保存“这个任务属于谁”，还要到调度中心登记“何时执行”。一次本地数据库事务不能自动覆盖另一个服务的 HTTP 操作。

所以工程既保存关联 ID，也处理注册失败、响应丢失和本地回填失败。确认远端没有残留后才能删除本地记录；远端结果未知时保留关联用于核对，不能把“接口报错”直接理解为“什么也没创建”。

这比只写一个定时方法复杂，却能明确失败之后要恢复什么。后文会直接展示实际恢复代码，而不是让读者跳到仓库猜测。

## 哪些职责没有交给调度中心

个人任务归属仍由当前租户与创建人共同决定；业务权限、业务状态机、事务和幂等仍由服务负责。原生 Admin 的用户管理不等于 Omni-Stack 的角色授权。

工作流解决“谁审批、下一步是什么”，定时任务解决“何时发起一次执行”，MQ 解决“如何异步交付消息”。例如调度可以唤醒消息中继，但消息是否送达仍要查看 Outbox、Broker 和消费者。三个工具各有职责。

## 需要付出的成本

调度中心不可达会影响注册、更新和触发；执行器地址不通会派单失败；任务执行太慢会产生阻塞；错误的重试可能重复业务结果。保留日志、设置合理周期、限制管理权限和准备恢复入口，是采用集中调度后必须做的工作。
