# Harness 是什么，为什么需要它

先看一个普通任务：给采购申请单增加一个“预算科目”字段，并保证只有具备采购权限的人能修改。模型可以写出实体字段、接口参数和页面控件，但它默认不知道这个项目的表名前缀、租户拦截规则、权限码格式、迁移文件位置，也不知道改完后该跑哪些检查。把这些“模型之外的工程条件”组织起来，让模型能够持续、可验证地完成任务的系统，就是本文所说的 Harness。

## 模型本身缺什么

模型擅长在给定上下文里生成代码，但一个真实任务还需要五类信息：

| 缺口 | 具体表现 | 没有它会怎样 |
|---|---|---|
| 上下文 | 表结构、模块边界、现有接口、错误码 | 生成看似合理但接不上的代码 |
| 约束 | 必须使用 `R<T>`、写操作要权限码、租户字段不能手写 | 代码能编译，却违反项目规则 |
| 工具 | 构建、测试、生成器、数据库迁移、浏览器 | 只能“看着像对”，无法真正运行 |
| 验证 | 单元测试、结构检查、链接检查、真实登录 | 把“改完了”当成“验证过了” |
| 反馈与断点 | 失败日志、未完成事项、下一步入口 | 下一次会话从零猜测，重复试错 |

Harness 不是又一个框架，也不是让模型“更聪明”的提示词。它是一组工程安排：把上述信息放在模型能读到、能执行、能被检查的位置，并让失败留下可继续的痕迹。

## 一个可操作的判断标准

判断一个项目有没有 Harness，不看它用了哪个模型，而看三个问题：

1. 新成员或新会话能否在仓库内找到当前事实，而不是依赖口头记忆？
2. 改错时是否有自动检查会失败，而不是靠人盯？
3. 任务中断后，是否留下可核对的进度、证据和下一步？

三个问题都能回答“是”，模型参与开发才具备稳定的基础。只提供一个大模型和一段系统提示词，通常只能完成短任务；任务一长，上下文丢失、约束漂移和“提前宣布完成”就会同时出现。

## 它不解决什么

Harness 不能替代需求判断、权限设计和人工审校。它也不能保证模型生成的业务逻辑正确。工具本身的能力边界仍然存在：例如自动化测试覆盖不到真实外部授权页，浏览器工具可能受环境限制。遇到这些情况，正确做法是记录未验证项，而不是用一段更长的提示词掩盖。

一份厂商工程博客把长任务代理的常见失败描述为“一次做太多”和“过早宣称完成”，并给出初始化脚本、进度文件、功能清单和提交摘要等做法。这是单一组织的实践经验，不是行业标准；本文只把它当作可核验的案例，具体见[行业实践案例](harness-industry-practice.md)。
