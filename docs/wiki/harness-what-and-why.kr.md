# Harness란 무엇이며 왜 필요한가

평범한 작업 하나로 시작해 봅시다. 구매 요청서에 "예산 과목" 필드를 추가하고, 구매 권한이 있는 사람만 수정할 수 있게 하는 일입니다. 모델은 엔티티 필드, API 파라미터, 화면 입력란을 작성할 수 있지만, 이 프로젝트의 테이블 접두사, 테넌트 차단 규칙, 권한 코드 형식, 마이그레이션 위치, 변경 후 실행할 검사를 기본적으로 알지 못합니다. 이런 "모델 밖의 엔지니어링 조건"을 정리해 모델이 지속적이고 검증 가능하게 작업을 끝내도록 만든 체계를 이 글에서는 Harness라고 부릅니다.

## 모델만으로 부족한 것

모델은 주어진 문맥에서 코드를 생성하는 데 능하지만, 실제 작업에는 다섯 가지 정보가 필요합니다.

| 부족한 것 | 구체적 모습 | 없을 때의 결과 |
|---|---|---|
| 문맥 | 테이블 구조, 모듈 경계, 기존 API, 오류 코드 | 연결되지 않는 그럴듯한 코드 |
| 제약 | `R<T>`, 쓰기 권한 코드, 테넌트 필드 직접 작성 금지 | 컴파일은 되지만 규칙 위반 |
| 도구 | 빌드, 테스트, 생성기, DB 마이그레이션, 브라우저 | 실행 없이 "맞아 보인다"로 끝남 |
| 검증 | 단위 테스트, 구조 검사, 링크 검사, 실제 로그인 | "변경했다"를 "검증했다"로 착각 |
| 피드백과 체크포인트 | 실패 로그, 미완료 항목, 다음 진입점 | 다음 세션이 0에서 추측하고 반복 |

Harness는 또 하나의 프레임워크도, 모델을 "더 똑똑하게" 만드는 프롬프트도 아닙니다. 위 정보를 모델이 읽고 실행하고 검사받을 수 있는 위치에 두고, 실패가 다음으로 이어질 흔적을 남기는 엔지니어링 배치입니다.

## 실용적인 판단 기준

Harness의 유무는 어떤 모델을 쓰는지가 아니라 세 질문으로 판단합니다.

1. 새 구성원이나 세션이 구두 기억이 아니라 저장소 안에서 현재 사실을 찾을 수 있는가?
2. 틀렸을 때 사람이 들여다보는 대신 자동 검사가 실패하는가?
3. 중단 후 검증 가능한 진행, 증거, 다음 행동이 남는가?

세 답이 모두 "예"라면 모델 참여 개발에는 안정된 토대가 있습니다. 큰 모델과 시스템 프롬프트만으로는 짧은 작업만 처리할 수 있고, 작업이 길어지면 문맥 상실, 제약 드리프트, "너무 이른 완료 선언"이 함께 나타납니다.

## 해결하지 않는 것

Harness는 요구 판단, 권한 설계, 사람의 리뷰를 대체하지 않으며 생성된 업무 로직의 정확성도 보장하지 않습니다. 도구의 한계도 남습니다. 자동 테스트가 실제 외부 인가 화면을 덮지 못할 수 있고, 브라우저 도구가 환경 제약을 받을 수 있습니다. 그럴 때는 더 긴 프롬프트로 숨기지 말고 미검증으로 기록하는 것이 맞습니다.

한 벤더의 엔지니어링 블로그는 긴 작업 에이전트의 흔한 실패를 "한 번에 너무 많이 시도함"과 "완료 전에 완료를 선언함"으로 설명하고, 초기화 스크립트, 진행 파일, 기능 목록, 커밋 요약 같은 실천을 제시합니다. 이는 한 조직의 경험이며 업계 표준이 아닙니다. 이 글은 검증 가능한 사례 하나로만 다룹니다. 자세한 내용은 [업계 사례](harness-industry-practice.kr.md)를 보세요.
