# トラブルシューティング手引き

トラブルシューティングの原則：まず失敗層を特定し、Trace ID、業務 ID、ログ証拠で位置を特定する；繰り返しの再起動やデータベースの直接変更で根因を隠さない。 ビルド・検査・診断プログラムは本機 Docker 内で実行し、ホストは編集・読取監査・Docker 操作だけに使います。HTTP ステータスと応答本文の R.code は別々に保存し、業務コードをそのまま HTTP ステータスとしないでください。

四言語文書は[承認済み AI レビュー方針](../adr/0003-authorized-ai-translation-review.md)に従い、実際の AI 意味レビュー合格で受け入れます。人による翻訳レビューは必須ではありません。[今回のレビュー範囲](../reference/evidence/troubleshooting-guide-review-2026-10-17.json)は文書と現在のソースのみで、ログイン・ジョブ・メッセージ・キャッシュ更新・ログ保存処理を再実行していません。手順の利用可能性は現在の障害の再試験・解決を証明しません。

## 1. 起動失敗

| 現象 | 検査 | 処理 |
|---|---|---|
| Maven プラグイン非互換 | `java -version`、`JAVA_HOME` | JDK 25 に切り替えてから `./mvnw` を使用 |
| アプリが Nacos を待機 | Nacos ヘルス、8848/9848、身分設定 | まず Nacos を復旧し、次に対象サービスを再起動 |
| migrator 失敗 | migrator ログ、DATABASECHANGELOG | 新しい changeSet や環境を修正し、実行済み changeSet は変えない |
| MySQL 接続拒否 | コンテナヘルス、ポート、アカウント、データベース | 対象 Compose project と接続文字列を確認 |
| 未選択依存の繰り返しリトライ | `dev status` / `dev doctor`（`dev plan` サブコマンドは存在せず、計画は `dev up` が Docker 起動前に出力）、profile | 正しいプリセットを使うか任意統合を明示的に無効化 |

## 2. ログイン失敗

- CAPTCHA が空または誤り：画像を更新し新しい `captchaKey` を使用。
- ユーザーが存在しない：テナントとテナント内ユーザー名を確認。
- ログイン後にログインページへループ：トークン有効期、ローカル時刻、Gateway 身分ヘッダーを確認。

- ソーシャルコールバック失敗：コールバック URI、バックエンド HMAC 署名の `state`、プロバイダ設定を確認（外部ソーシャルはフロントエンド PKCE を含まない）。フロントエンド PKCE（`code_verifier`/`code_challenge`）はローカル `/oauth2/authorize` SPA フローとして個別に調査します。
- Portal 403：`SUPPLIER` ロール、Portal 関連、サプライヤー状態を確認。

ログインイベントはログインログで確認します。これは安全監査のログインイベントの読取専用投影です。その他の認証・安全イベントは安全監査記録を確認してください。Auth の認証行為を業務操作ログでは探しません。

## 3. メニューまたは権限の異常

1. 非公開環境で JWT の `scope` 権限集合と `/api/auth/menus` の返却を確認。JWT 全体をログやサポート依頼へ貼らない。
2. 権限シード、ロール関係、組織範囲を確認。
3. 権限変化後は再ログイン。
4. 権限のないアカウントで書き込み API を直接呼び、バックエンドが 403 を返すことを確認。
5. フロントエンドのボタンだけ異常なら、`v-permission` とバックエンド権限コードが完全一致するか照合。

## 4. データが見えないまたは権限超過

- リクエストが Gateway を経由しているか確認（身分ヘッダーを偽装してビジネスサービスに直接接続しない）。
- テナント ID、現在ユーザー、組織、ロール範囲を確認。
- ドメイン DataPermission のテーブル名と列マッピングを確認。
- 子テーブルは集約ルート経由で継承しなければならず、存在しない owner 列に条件を追加しない。
- DataPermission インターセプターが Pagination の前にあるか確認。

## 5. Workflow

- モデルを保存できない：BPMN XML とデザイナー状態を確認。
- 検証失敗：検証リストに従い process id、接続線、候補者設定、式を修正。
- 公開競合：同一モデルの並行操作と現在のドラフトを確認。
- 起動失敗：業務伝票番号で起動要求の予約記録とリトライ状態を照会。
- 承認者が空：候補者プレビューで role、anchor、組織範囲、フォールバック戦略を確認。
- 会署結果の異常：`MI_END` 履歴タスクの削除理由と計数変数を確認。

## 6. XXL-JOB

- システムタスクが見えない：`@XxlJob` と `@SystemJobMeta` の二重アノテーションを確認。
- 個人タスクにハンドラなし：Bean 名は `typeCode` と等しくなければならない。
- 作成が孤児記録を残す：登録失敗後のデータベース削除補償を確認。
- 即時実行でログなし：Admin、実行器登録、ハンドラ例外、ログ書き込みを確認。

## 7. MQ とクロスサービス

1. Outbox でメッセージ ID、Topic、業務 Key で照会。
2. PENDING、FAILED、DEAD_LETTER 状態と次回リトライ時刻を確認。
3. Broker 配信とコンシューマー Inbox を確認。
4. producer traceId と consumer traceId で Loki/Tempo 上に関連付け。
5. 下流の冪等性を確認した後のみ手動再送。

Relay のクロステナントスキャンは設計動作；外部照会インターフェースは引き続きテナントでフィルタしなければならない。

## 8. フロントエンド

- 空白ページ：動的メニューロード、ルート chunk、ブラウザコンソール、API 401/403/404 を確認。
- 動的フォームのフィールド型エラー：JSON Schema の `type`、`enum`、`options`、required を確認。
- 言語が永続化されない：`omni-lang` が `zh-CN`、`en-US`、`ja-JP`、`ko-KR` か確認。
- 日付/金額の形式エラー：現在の locale を使用しているか確認、インターフェース値は翻訳で変わってはいけない。
- lint 失敗：ルールを下げず、ソースを修正し `--max-warnings 0` を維持。

## 9. サポート依頼時に提供する情報

- 該当バージョンとコミット ID。
- 対象プリセットと Compose project 名。
- 時間範囲、Trace ID、業務 ID。
- 秘匿化後のエラー応答と関連サービスログ。
- 再現手順、期待結果、実際の結果。

パスワード、CAPTCHA の答え、JWT、内部トークン、秘密鍵、未秘匿化の個人データを提供しないこと。

## 10. 旧運用説明から移した調査手順

現在のソースに合わせた手順です。古い画像・ポート・過去の検証成功は現在の障害解決を証明しません。ビルドと診断プログラムはローカル Docker 内で実行し、ホストは編集と Docker 操作に使用します。

|---|---|---|
| CAPTCHA 画像がない | Auth の正常性、Redis 接続と非公開パスワード設定 | `CaptchaServiceImpl` の検証は記録を一度消費します。失敗・期限切れ後は更新して人が入力し、旧コードを再利用しません |

| メニューが空・ボタンが隠れる | `scope`、`sys_role_permission`、`permission_code`、`v-permission` | 権限変更後は再ログインします。メニュー非表示と API 403 は別々に確認し、固定ルートで権限を補いません |
| ソーシャルコールバック失敗 | provider の URI と `AUTH_OAUTH2_*_REDIRECT_URI` の完全一致、サーバー `state` 署名設定、コンテナ外向き接続 | ローカル回調は Gateway 8102 に入り、内部 Auth 8080 は外部回調ではありません。[認証手順](authentication.jp.md)を参照 |
