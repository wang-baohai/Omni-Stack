# 시스템 작업, 개인 작업과 작업 유형 확장

스케줄링은 두 경로입니다. 코드 선언 시스템 작업은 운영자가 관리하고 개인 작업은 승인된 유형에서 사용자가 생성합니다. 모두 XXL-JOB을 사용하지만 소유권과 수명주기가 다릅니다.

## 1. 시스템 작업

MQ relay, 로그 보관, 보상 스캔은 두 어노테이션이 모두 필요합니다.

```java
@XxlJob("handlerName")
@SystemJobMeta(...)
```

하나라도 없으면 `SystemJobRegistry`에 나타나지 않습니다. 화면은 등록, 시작/중지, 즉시 실행을 관리하고 구현은 코드 버전으로 관리합니다.

### 스크린숏

#### 그림 1 `scheduling-system-jobs-ko-KR`: 시스템 작업 목록

- 전제 조건: 시스템 작업 조회 권한을 가진 관리자로 로그인
- 작업자: 플랫폼 관리자
- 작업: 작업 스케줄링 → 시스템 작업 열기
- 예상 결과: 메인 영역에 등록된 핸들러와 시작/중지·즉시 실행 작업이 표시됨

## 2. 개인 작업

작업 공간에서 유형, Cron, JSON Schema 동적 파라미터를 입력해 생성합니다. 저장 후 일시중지, 재개, 편집, 즉시 실행, 로그 확인이 가능합니다. 개인 작업은 RBAC 대신 `createBy` 소유권을 사용하고 공통 `userJobExecuteHandler`가 `typeCode`로 처리기를 선택합니다.

## 3. 작업 유형

안정적인 `typeCode`, 표시 이름, 설명, 파라미터 Schema, 상태를 정의합니다. `typeCode`는 `UserJobHandler` Bean 이름과 정확히 같아야 합니다. 문자열 `enum`은 선택 상자로 표시하고 API에는 안정 값을 보냅니다.

## 4. 유형 추가

처리기와 동일 Bean 이름, 파라미터 검증, 유형과 Schema 등록, `omni-base` 빌드, 격리 XXL-JOB에서 생성/즉시 실행, 성공·실패·중지·갱신·삭제를 검증합니다.

## 5. 일관성

DB 생성과 XXL-JOB 등록이 모두 성공해야 합니다. 실패 시 `UserJobServiceImpl.createJob()`이 행을 삭제합니다. 세션 쿠키는 메모리만 사용하고 자동 갱신합니다. 정기 실행과 즉시 실행이 겹칠 수 있으므로 처리기는 멱등해야 합니다.

## 6. 문제 해결

화면 유형 없음은 상태와 코드, XXL-JOB 기록 없음은 Admin과 실행기, 라우팅 실패는 Bean 이름, 결과 없음은 작업/처리기 로그, 시스템 처리기 없음은 두 어노테이션과 `omni-common-job`을 확인합니다.
