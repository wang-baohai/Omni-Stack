# S0-08 / G1 数据与租户初始化门禁证据

> 验收日期：2026-08-21
> 状态：通过
> 隔离范围：Compose project `omni-g1`、独立 MySQL 命名卷和独立宿主机端口；原有开发栈与原有数据卷未修改

## 1. 验收结论

G1 已关闭。全新空卷可以只依赖一次性 `omni-db-migrator` 完成九个目标库的结构与正式种子初始化；迁移成功后，基础设施、七个后端服务、Gateway 和前端按健康门启动。真实验证码登录、租户模块化开通、结果汇总、失败恢复和消息重放幂等均在隔离全栈通过。

Compose 不再把旧聚合 SQL 挂载到 MySQL entrypoint。应用使用最小权限账号连接业务库；Flowable 运行时自动建表已关闭，数据库结构只由 migrator 管理。

## 2. 数据库门禁

| 场景 | 证据 | 结果 |
|---|---|---|
| Fresh | 全新 MySQL 8.4 命名卷运行 migrator，九个目标库完成结构和种子迁移 | 通过 |

| 失败关闭 | 非空未接管库、未知历史、错误/过期/篡改备份证据和错误确认均被拒绝 | 通过，自动化测试和 S0-06 演练覆盖 |

## 3. 完整 Compose 启动

隔离栈共验证 15 个长期运行服务：MySQL、Redis、Nacos、RocketMQ NameServer/Broker、XXL-JOB、Auth、Base、Workflow、CRM、SRM、Procurement、Asset、Gateway 和 Frontend；`omni-db-migrator` 作为 one-shot 服务成功退出。

七个后端服务和 Gateway 均通过容器健康检查。真实请求经隔离 Gateway 完成验证码获取与管理员登录，不依赖绕过验证码或直接伪造会话。

## 4. 租户开通与失败恢复

### 4.1 故障发现与恢复样本

租户 4 首次运行时，六个远端模块均写入成功回执，Auth 也收到结果事件，但汇总状态停留在 `PROVISIONING`。运行日志和数据库版本字段共同定位到：实体使用 MyBatis-Plus `@Version`，自定义拦截器链却未注册 `OptimisticLockerInnerInterceptor`。

修复后，通用默认配置和 Auth、Workflow、CRM、SRM、Procurement、Asset 的自定义链均按“租户/数据权限 → 乐观锁 → 分页”顺序注册。对应顺序测试和 15 模块 Maven reactor 测试通过。重放租户 4 的结果事件后，租户转为 `ACTIVE`，六个远端模块状态均为 `SUCCESS`，乐观锁版本从 0 增加到 1。

### 4.2 无人工补偿的完整样本

通过真实验证码登录后创建租户 5。初始状态为 `PROVISIONING`；约 30 秒后自动转为 `ACTIVE`：

- `platform`、`auth`、`base`、`workflow`、`crm`、`srm`、`procurement`、`asset` 全部为 `SUCCESS`；
- 六个远端模块各有且仅有 1 条成功接收凭据；
- 六个远端模块状态的 `attempt_count=1`、`version=1`；
- 整个过程没有手工重放、数据库改值或跳过验证码。

## 5. 消息重放幂等

将 Base、Workflow、CRM、SRM、Procurement、Asset 六个独立消费组的 `tenant-provisioning` offset 重置到租户 5 创建前，再次消费同一请求事件。重放完成后：

- 租户 5 仍为 `ACTIVE`；
- 六个模块各自仍只有 1 条 `sys_tenant_provision_receipt`；
- 六个模块各自仍只有 1 条该租户的结果 Outbox 消息；
- Auth 模块状态的 `attempt_count` 和 `version` 均未增加。

这证明消费者在回执唯一键处提前返回，没有重复创建领域默认数据或重复发布结果。

## 6. 安全与清理约束

- 本证据不记录数据库、Redis、Nacos、OAuth、XXL-JOB、内部 API 密钥、验证码内容、访问令牌或管理员密码。
- 原开发栈仅作为只读参考，未执行 Liquibase 接管或升级。
- fresh 复验专用的 `omni-mysql-g1-fresh` 容器及匿名卷已在归档证据后删除。
- `omni-g1` 隔离全栈因 S1 UI 运行态复验仍需使用而保留；进入 WP-10 最终清理时只删除明确属于本次验收的容器、卷和临时产物，不操作原数据卷。
